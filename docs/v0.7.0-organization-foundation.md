# Organizations & Research Campaigns — P13 Foundation

P13 adds one standalone ASP.NET Core organization service with one authoritative PostgreSQL database per organization. It is a functional development checkpoint, not a published hosting service or a beginner deployment installer. Personal Research still works offline without an organization account or a running server.

## What works

An operator-configured server provides **Set Up Your Organization → Sign In → Organization Overview → Create Program → Create Campaign → Save Draft → Review & Publish**. Programs and campaigns can be edited, paged and reopened after restart. Campaigns retain their question/objective, description, Scientific Research / Experimental Flight Test / Mixed focus, selected research approach, author, UTC timestamps and revision. Published definitions are immutable snapshots. Editing creates a new draft and retains the prior published revision; **Revision History** shows both. Publication requires a saved objective and supported exact template version. Only administrators publish in this checkpoint; configurable publication/reviewer policy remains future work.

The six existing Personal Research starter definitions and the P10/P11 custom/multi-point contracts are reused, including their original validators and limitations. The server stores definition metadata, not a pilot's personal card identity, telemetry, mission history, scientific datasets or results. Choosing a starting point does not copy personal work, assign a flight, acquire data, grant retrospective credit or evaluate anything. Full organization-side card-parameter authoring and pilot execution are not delivered by this template-selection checkpoint. Saved approach details expose the exact defaults, units and provenance distinctions; the personal builders remain available independently.

## Security and storage boundaries

- ASP.NET Core Identity owns password hashing, lockout and authenticated claims. Passwords require at least 14 characters, uppercase/lowercase, a digit and a symbol; PBKDF2 uses 210,000 iterations. Five failed attempts lock the account for 15 minutes, with an additional per-address identity rate limit. Cookies are HttpOnly, SameSite Strict, securely scoped and separate from desktop pairing. Idle lifetime is 30 minutes with an eight-hour absolute limit. Security stamps are checked on every authenticated request. **Sign Out** revokes this account's organization sessions, including previously issued cookies.
- The first administrator requires a 32–256-byte random operator-provided secret in a protected regular file. Broad user-readable/writable Unix modes or Windows ACLs are rejected. There is no public signup or first-visitor claim. Bootstrap verifies a same-origin antiforgery token and the protected secret; a PostgreSQL transaction/advisory lock makes concurrent setup single-use. Organization creation, roles and administrator identity commit together. After setup, the database permanently rejects another claim. Restart does not need the consumed file and cannot reset the administrator.
- Roles are explicit: Administrator manages and publishes; Manager manages drafts/programs but cannot publish or inspect administrative audit; Reviewer/Pilot have no management access in P13. Nonadministrator account provisioning/enrollment is not implemented. Buttons reflect permissions, and every endpoint independently enforces authorization. Anonymous visitors receive no private organization/program/campaign details. Desktop paired-device tokens are not organization credentials.
- All mutations require the organization antiforgery token and exact Origin. Canonical host/scheme checks, strict JSON/version validation, a 32-KiB request limit, bounded queries and concurrency/rate limits protect the API. No request bodies, passwords, setup secrets or connection strings are written to application diagnostics. CSP blocks external scripts, framing and inline injection. User text renders literally.
- PostgreSQL is the sole organization store; no SQLite, personal-store or ephemeral fallback exists. Initial migration `20261027120617_InitialOrganization` creates the `organization` schema and Identity/key/program/campaign/revision/audit/receipt tables. Unknown future migration histories are refused. Definition/audit/command histories are append-only through the service; exact saved JSON hashes are rechecked when reading revisions. PostgreSQL microsecond UTC precision is used consistently across responses and restart.
- Optimistic revisions protect edits/publication. Resource locks and actor/request-bound, payload-hashed receipts serialize concurrent retries across server processes; a repeated identical command returns the original result, while changed payloads or stale revisions conflict. Browser drafts remain visible after failure. Program/campaign pages contain 20 records, audit pages 100; these are request bounds, not retained-ownership limits.
- Data Protection keys persist in PostgreSQL. Production requires certificate protection for those keys and TLS-verified PostgreSQL; local test keys are explicitly development-only. Preserve the database and certificate together. Production backup/restore, certificate rotation, account recovery and deployment acceptance remain separate gates; no verified backup claim is made here.

## Operator configuration boundary

The common deployable project is `src/AeroScience.Organization`; it does not depend on a particular host/provider. PostgreSQL is an external durable service, not bundled with the Windows companion. This table is an engineering reference, not a request for the owner to perform terminal setup or QA.

| Setting under `Organization` | Required behavior |
| --- | --- |
| `PublicOrigin` | Exact HTTPS scheme/host/port, without a path, query or embedded credentials; all requests must match |
| `ConnectionString` | Protected PostgreSQL settings with explicit host/database/user; production requires `SslMode=VerifyFull`, with sensitive parameter/error-detail logging disabled |
| `BootstrapSecretFile` | Operator/service-account-only regular file for first setup; required while unclaimed, unnecessary after successful bootstrap |
| `KeyCertificateFile`, `KeyCertificatePassword` | Current private PKCS#12 certificate and its protected password for durable production Data Protection; missing/invalid/broadly readable material fails safely |
| `TrustedProxies` | Optional explicit IP list, at most four; only these may supply forwarded client/protocol information. Preserve the canonical Host at the proxy; untrusted forwarded headers are ignored |
| `LocalDevelopment` | Explicit opt-in only in Development/Testing. Requires an HTTP loopback IP origin and forces loopback binding, with remote requests refused. It is not public HTTPS hosting |

Missing database, first-setup secret or production key/TLS configuration refuses startup. Local automated fixtures use port **5193**, independent of the preserved desktop private-validation profile/port **5086**. The portal assets use a separate output folder so they cannot overwrite the desktop web application. New package locks pin Npgsql/EF provider 10.0.3 and Microsoft Identity/EF/Data Protection 10.0.13; upstream provider licenses are retained. No PostgreSQL or organization dependency is added to the desktop runtime graph.

## Technical evidence and remaining scope

Automated tests use actual isolated PostgreSQL 17.6 databases, actual ASP.NET endpoints and the compiled portal process. They cover protected/concurrent bootstrap, passwords/roles, CSRF/Origin/host rejection, stamp revocation, idempotency/stale updates, all eight supported approaches, exact publication/revisions, schema compatibility, restart/session persistence, missing credentials and corrupted history. Browser checks include actual SIGKILL/restart, publication/history, conflict-preserved drafts, literal unsafe-looking text, desktop-token rejection, 375px layout, axe and Escape/focus restoration. Counts and exact completed full CI are recorded in the [development tracker](roadmap/v0.7.0-development-tracker.md).

Full Linux CI provisions a digest-pinned PostgreSQL container. Windows uses a fresh loopback instance if PostgreSQL binaries are installed on that runner; otherwise database-specific cases explicitly skip and Linux supplies genuine database/process acceptance. No in-memory substitute is treated as PostgreSQL acceptance. Existing P01–P12 and scientific/security/recovery tests remain required.

Not implemented: invitations/membership, pilot desktop connections, assignments/claims, evidence uploads/queues/reviews, organizational flight execution, live monitoring, hosting-provider deployment buttons, MFA/recovery or validated production backups. No provider is selected, no price is promised, and no public server/release/installer is published. EMIT genuine-original and owner-installed Windows/MSFS/device acceptance remain separate and unchanged.

## Optional simple check

No owner action is needed for this automated development checkpoint. When an operator has a running server ready:

1. Open its page, use the supplied **Setup code** to **Create Organization**, then **Sign In**. You should see **Organization Overview**.
2. Click **Create Program**, save a name, then **Create Campaign**. Choose **Vertical Atmospheric Profile**, add your question and click **Save Draft**.
3. Click **Review & Publish → Publish Campaign**. Look for **Published**, then sign out and back in. Your program and campaign should still be there. If something looks wrong, send a screenshot and say what you expected.
