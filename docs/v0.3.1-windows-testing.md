# v0.3.1 Windows installed-build testing

Cloud tests, browser fixtures and synthetic aircraft positions do not establish Windows/MSFS acceptance. Use an actual installed v0.3.1 candidate. Keep the published v0.3.0 installer, tag and archives unchanged.

## Build on the gaming PC

Open **PowerShell 7**, not the Visual Studio Command Prompt. Close AeroScience before updating/building source.

```powershell
Set-Location 'C:\Dev\AeroScience-release'
git status --short
git pull --ff-only origin main
git log -1 --oneline
pwsh -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\release\Build-ReleaseCandidate.ps1 -SdkRoot 'C:\MSFS 2024 SDK' -RuntimeApprovalRecord 'C:\AeroScience-Release-Records\runtime-approval.json' -RuntimeRedistributionConfirmed -InnoCompiler 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe' -OutputDirectory 'C:\AeroScience-Builds\Science031-1'
```

The checkout must be clean. Preserve genuine local edits; do not bypass the check or reset them blindly. Reuse the documented runtime authorization only when it matches the actual native DLL. Original correspondence remains private. Use a new output directory if an earlier candidate already exists. No self-hosted Actions runner is needed.

Expected primary final asset after the existing automated technical gates:

`C:\AeroScience-Builds\Science031-1\AeroScience-Setup-v0.3.1.exe`

The directory also contains `.exe.sha256`, `.release.json`, `RELEASE-NOTES.md` and build evidence. A ZIP is an intermediate/optional portable payload. Ordinary pilots run Setup and then AeroScience from Start; they do not run these commands. No additional acceptance questionnaire is introduced.

If a technical gate fails, keep the complete output and `build-evidence` logs. Do not skip SDK/ABI/runtime/licensing checks, fake scientific evidence or rename an unvalidated candidate into a release.

## P0 pattern acceptance

1. Install the newly built v0.3.1 Setup, preserving existing data/settings. Open Mission Planner.
2. Add one manual waypoint and a survey polygon. Confirm Aviation/Metric are the only planning profiles and changing them retains geometry and customized scientific measurement units.
3. For **each** lawnmower, creeping line, expanding square, racetrack, orbit, box, radial spokes and straight transect: choose center/type, see preview, change relevant values, add, save, reopen and export. Confirm the manual waypoint/polygon remain.
4. Fit a parallel pattern to the saved polygon, change heading, then immediately click Add. Confirm it commits once without another manual preview/refresh. Repeat rapid changes and double-click Add; no outdated/duplicate geometry should appear.
5. Enter invalid spacing/orbit count: the relevant field explains the issue in current units and the old preview remains marked outdated. Correct it and verify recovery. Check Fit Preview deliberately changes view; routine edits do not recenter.

## Predictive acquisition and real flight

1. Enable scientific online access with its separate consent. Check OSM consent remains independent. Enable supported remote instruments and record actual flight telemetry.
2. Fly a long saved route: progressive preparation passes its first eight cells. Check queue, prepared/awaiting/unavailable counts, transfer budget and actual source coverage. Pause/Resume/Cancel operate without deleting retained sources.
3. Fly **without a plan** at approximately **400–450 kt groundspeed**. Observe data requested ahead of the aircraft, not just around its current cell. Course/ground track rather than heading should govern wind drift.
4. Turn 90° away from a planned route, then fly reversals, parallel survey passes and an orbit. Watch reprioritization, curved turn predictions and source reuse. Check no aircraft/autopilot-specific integration is required.
5. Pause, slew/teleport, change aircraft, disconnect/reconnect SimConnect and introduce telemetry gaps. Predictions must suspend/reset instead of starting huge false corridors. Normal 1 Hz flight recording remains independent.
6. Exercise slow/unavailable providers, offline operation, unmetered-only with unknown/metered Windows cost, low library capacity and the rolling-hour budget. Science gaps show reasons; other instruments/toolbar/dashboard stay responsive. Do not interpret missing data as a valid observation or later backfill.

## Guided source and settings acceptance

1. In **native Settings → Scientific Data Sources**, inspect the four labeled sections, real counts/providers/dates/status and direct Import/Manage/Coverage/Guide actions. Check 100/125/150% Windows scaling and keyboard use.
2. Independently change source modes; restart. My Datasets Only must not download for that instrument. Excluding a source must preserve its files and completed products.
3. Import a compatible elevation GeoTIFF, Landsat collection with QA/metadata and Sentinel numeric collection with genuine scale/offset information. No hand-written manifest is required. Missing metadata gets an actionable question; unsupported data gets an explanation.
4. Follow [the hyperspectral beginner guide](remote-sensing/using-your-own-hyperspectral-dataset.md) with the actual Cuprite files. Keep native Settings open while opening the browser import wizard and confirm its file picker is correctly owned and repeat requests do not create extra dialogs. Use the native file picker, verify 224 channels and real coverage, confirm import, view a genuine spectrum/product inside coverage and export. Confirm bad bands/nodata are omitted. Try outside coverage and offline reopening.
5. Cancel each dialog/import, try ambiguous/missing binaries, corrupted headers, insufficient space, an unavailable external drive and an exact duplicate. Originals, existing datasets and completed products must remain intact.
6. With no hyperspectral dataset, verify Dataset Required plus import/help actions; terrain/thermal/multispectral continue. No NASA login/download is required.
7. In browser Settings use all eight categories, direct links, Back/Forward and unsaved fields. Only relevant API-key prompts should appear; offline/OSM requires no Esri key. Verify paired mobile layout and unchanged source/privacy preferences across clients.
8. Have a first-time tester follow the guides without verbal coaching. Record the result separately; developer tests are not that acceptance.

## Upgrade, hardware and publication

Review old v0.3.0 plans, source references, mission products, modes, storage paths and offline history after upgrading. Historical products are not rewritten. Legacy ENVI source records retain their old map-reference convention; newly guided imports explicitly use the independently validated ENVI corner/affine convention. To use corrected source metadata for future acquisitions, reimport the original through the new wizard; old products keep their provenance. Exclude an old source from active selection if you want the newly imported corrected source to govern future acquisitions; this does not delete the older source.

Check the official SDK-built full toolbar in MSFS, live recording/history, Quest 3 VR and physical iPad/LAN separately. Test normal uninstall/reinstall preservation and toolbar Keep/Remove choices. Record device/runtime versions and any untested scenarios honestly.
