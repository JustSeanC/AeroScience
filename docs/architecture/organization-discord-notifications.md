# P27-C organization Discord architecture

One organization backend, Identity and PostgreSQL remain authoritative. There is no new recorder, scientific archive, public publisher API, general webhook platform or inbound bot. `DiscordWebhookPolicy` is reused by `DiscordTransport`, `OrganizationNotifications` and the existing portal.

## Authorization and disclosure

Active database membership and the current Identity security stamp are rechecked, including command retries. Administrator settings/test/disclosure/cancellation additionally require recent MFA (ten minutes), enabled authenticator and acknowledged recovery. Existing exact Origin, antiforgery, rate/concurrency limits and cookie protections apply. There is no desktop permission elevation: pilots use their own authenticated organization-browser session to consent to an exact live session, destination identity and settings revision. An Engine portal link carries no bearer or credential.

Live starts schedule only on explicit separate external consent. Stops are read incrementally from authoritative P27-B events, not caller-created announcements. Only pilot-stopped/flight-ended sharing can yield an end announcement, not disconnect, idle expiry, revocation or restart. Both are rechecked against current session/instance, grant, membership, expiry, organization policy and claim restrictions. No coordinates or aircraft payload are persisted by notifications.

Research announcements support `ApprovedCardResult` and `DocumentedExceptionAccepted` only, after an administrator previews and explicitly approves the exact immutable event-derived public text. Current contribution/findings, superseding events, exception revision, active subject, restricted campaign and current disclosure-authorizer authority are rechecked before sending. The disclosure is append-only. Existing accepted historical evidence remains unchanged. No scientific approval is inferred from `AttemptRecorded`, `LocalEvaluationReported`, `EvidenceReceived`, private requirement findings or a client Pass. Public scientific data/measurement publication is not implemented; only minimal explicitly disclosed approval summaries are supported.

## Credential and outbound boundary

Only `https://discord.com/api/[v10/]webhooks/{snowflake}/{token}` is accepted. No alternate hosts, ports, user information, escaped paths, query, fragment or thread parameter. Credentials use the existing persisted Data Protection key ring/certificate, purpose-bound to organization and destination. Current ciphertext is replaced on rotation and removed on deletion. Receipts contain only input hashes and masked responses; revision/audit/history contain no full credential. No saved full URL returns to the browser. Do not enable sensitive HTTP/body tracing in hosting infrastructure.

Production transport has no configurable test endpoint, TLS bypass or custom proxy. Every connection resolves Discord once, rejects the entire answer set if any address is unsafe, connects directly to a selected checked IP and verifies the actual peer IP/port. Default TLS verifies `discord.com` and the certificate chain. The fixed request is HTTP/1.1 POST with `wait=true`, redirects disabled, proxy disabled, no decompression, 5-second connection and 10-second overall bound, bounded headers and 16-KiB acknowledgment body. Content is bounded and sanitized, and `allowed_mentions` explicitly disallows all mentions. Test-only assemblies inject a loopback connector and ephemeral trusted HTTPS fixture certificate; the product contains no runtime switch for that behavior.

Official contracts checked 2026-10-30: [Webhook execution](https://docs.discord.com/developers/resources/webhook), [Allowed mentions](https://docs.discord.com/developers/resources/message), [Rate limits](https://docs.discord.com/developers/topics/rate-limits). `wait=true` requires a returned created-message identity. Numeric `retry_after` seconds on 429 are rounded up. No exactly-once network guarantee is claimed.

## Durable processing

`DiscordDeliveries` stores stable intent/event/destination-revision/consent identities and outcomes, not evidence or message byte archives. Unique indexes enforce event-to-destination scheduling. An indexed cursor scans at most 100 events per tick. At most 500 unfinished intents are retained for dispatch; history is paged without a lifetime cap. Membership/advisory locks cover short state changes, never the HTTP request. The hosted worker is separate from acquisition and live update handling.

`Sending` is committed before HTTP. Explicit valid acknowledgment produces Delivered; definitive 4xx produces Failed and disables the destination. Supported 429 responses impose a destination-wide delay with at most five attempts, including exponential minimum backoff. Unexpected success bodies, redirects, malformed responses, 5xx, connection loss and timeouts become Ambiguous, never automatically retried. A prior process's Sending records, or expired dispatches beyond the HTTP deadline, become Ambiguous. Pending records can resume after restart only after fresh permission checks. Destination revision changes cancel pending work and invalidate old consents/disclosures. Immutable intent identities and unique scheduling prevent duplicate event replay.

One application instance is supported, matching accepted P27-A live-presence limits. This is not a horizontally replicated notification service. Restoring an older disaster backup may rewind external delivery knowledge: keep the restored service isolated and notifications disabled, reconcile Discord posts, then rotate/reapprove the destination before enabling outbound operation. Encrypted backups retain necessary protected settings under existing P26 retention; live account-loss recovery and production rollout remain release gates. A server receipt or Discord acknowledgment is never scientific certification.
