# Organization hosting — P28 implementation

This supersedes the unresolved ingress and sealed-code designs in the historical P26/P28 notes. It does **not** establish live Railway, novice, off-account recovery or release acceptance. The final material Full gate is recorded in [P28 validation](../validation/v0.7.0-p28.md).

## Public networking without forwarded identity

Railway's documented public service path terminates TLS/SNI and redirects plain HTTP at its edge. The application does not authenticate that edge, reconstruct client IPs or grant privileges from its headers. It treats the public listener as an ordinary untrusted internet entrance, including connections from private-network peers.

`OrganizationIngress` is a co-located gateway in the existing ASP.NET process. Port 8080 accepts public requests only for the exact configured native HTTPS authority. Port 9001 binds **IPv4 loopback only** and requires a fresh request-bound HMAC from that process. Other project services cannot access the backend port. A loopback connection alone grants no authority. A port conflict prevents startup rather than falling back to another listener.

The 256-bit per-process key never enters configuration, logs, a browser or a volume. Proofs bind the method, normalized target, exact Host, body SHA-256 and Cookie/Authorization/Origin/CSRF/Content-Type/Accept hashes. Nonces have 128 bits; proofs expire after 30 seconds, allow two seconds of forward clock tolerance, and are single-use in a bounded 4,096-entry cache. Replacement changes the key. The public gateway discards all Forwarded/X-Forwarded/X-Railway/X-Real-IP and supplied proof fields. Split Cookie fields preserve their semicolon semantics; duplicated security fields are refused. The backend uses the configured public HTTPS scheme **only after verifying the local proof**.

Identity, membership, MFA, browser antiforgery and exact Origin checks remain authoritative. Native write routes still reject browser cookies/Origin and validate their existing scoped credentials. No source IP or informational Railway label authenticates a user. Anonymous limits remain conservative and shared behind the gateway; client-IP reconstruction and load capacity are not claimed. Request concurrency and existing 32 KiB/2 MiB dedicated evidence bounds remain enforced. No new flight-recorder work occurs.

This revises the former requirement that every edge socket prove its identity: the **application** has one authenticated local ingress, while its public gateway grants no peer identity. It adds no tunnel, extra provider or central AeroScience service. Trust in Railway's TLS routing and hosting execution is explicit; the same operator already controls the application image, variables and volumes. Arbitrary private peers do not receive that operator authority. The existing advanced finite-proxy configuration remains separate and cannot be mixed with this profile.

Provider acceptance must confirm original Host preservation, HTTPS-only public exposure, no public TCP proxy, private backend refusal, spoofing/Origin negatives, restart/replacement and strict database hostname verification. Documentation and local containers cannot prove those real-provider behaviors. No guessed edge IP, wildcard trust or disabled certificate validation is permitted.

## First ownership

The companion creates a P-256 ownership key in its existing OS vault under a separate `Owner/` purpose/profile/intent target. Ordinary connection tokens retain their 64-hex validation. Only the public verifier and intent are copied to Railway's **required per-deployment** Ownership Key field. A reusable template draft has no author verifier/default; publishing a template with the author's key is prohibited.

The provider-installed verifier is the deployment authority. A browser request supplies the proposed organization and administrator credentials. Only Identity's salted, iterated password hash is retained for five minutes; no private signing key or plaintext password is persisted. The request binds the exact origin, project/environment/service UUIDs, key fingerprint, proposed account/organization, payload hash, random nonce and expiry. The companion reviews that exact request and matching code, then signs it after an explicit approval. It binds its saved intent to that deployment before sending, including lost acknowledgments.

The server serializes ownership with its existing PostgreSQL advisory lock. It accepts one administrator, retains the one outcome on retries, rejects expired/stolen/tampered requests and refuses the legacy setup-secret endpoint in pairing mode. Restart preserves pending records and the configured binding. Another visitor cannot sign, change the approved account or claim ownership. Current deployment identity is pinned; an implicit origin/project/key change stops startup. Recovery uses an explicit audited replacement rather than silently changing ownership. Existing administrator authenticator/recovery requirements follow normal sign-in.

No Railway OAuth identity, project name or viewer scope is misrepresented as ownership. No secret-bearing deployment URL, sealed-secret retrieval, public log, certificate generation or terminal step is required from the ordinary owner. Native composer field/domain behavior still requires authorized provider validation before a launch target can be published.

## Protected replacement and recovery

Original submitted evidence remains PostgreSQL-backed. Native PostgreSQL/restic protect the same authorized records, encrypted Identity tokens, original data-protection material and audit history. They do not access a pilot's unsubmitted archives. Independently scoped storage/encryption credentials remain mandatory for account-loss protection; a native Bucket in the same Railway account does not qualify.

`Prepare Restored Copy` creates a **new** generated database and protected certificate pair. Verification checks the exact compatible schema, organization, original evidence hashes, audit digest, MFA and protected Discord decryption. The application role owns the restored objects, so subsequent compiled upgrades remain possible. The separately privileged recovery role has CREATEDB and explicit SET into the application role, with INHERIT FALSE; the application has neither CREATEDB nor superuser/role-management rights. Candidate-specific connection pools close before cleanup; no backend-termination or superuser permission was added.

`Activate Restored Copy` rechecks integrity/schema and writes an atomic, private database/certificate selection bound to the deployment. The original database is retained. New mutations are held during activation and the process restarts. A missing or mismatched selected certificate fails closed; there is no fallback to the old database or replacement identity. Cancellation deletes only the identified unactivated candidate. Returning to a checkpoint does not merge later changes; the UI discloses that limitation.

Before activation, recovery preserves identities, original claims, receipts, submissions, reviews and scientific outcomes, but quarantines authorization: only the selected original active administrator remains active; other active members are suspended for explicit review, old invitations and device grants are revoked, enrollment returns to invitation-only approval, cookies are invalidated, and live sharing/automatic deletion remain off. Administrative changes append audit/policy history. Old Pending/Sending Discord deliveries become Ambiguous because later acknowledgment cannot be inferred from a snapshot. Restored webhook secrets are removed after decryption verification and need explicit replacement; a deleted credential cannot silently become usable again. Old events and findings are not rewritten or reposted.

`Renew Protected Identity` rewraps existing data-protection keys with a new certificate **on an isolated verified copy**, validates MFA/protected settings and uses the same explicit activation boundary. This is planned renewal, not proof of recovery from a compromised master key. Original checkpoints retain their original paired key material.

## Fresh recovery deployment

`Restore From Private Recovery File` accepts a deliberately chosen key/reference file after current administrator MFA, password and explicit consent. A different organization can replace only a fresh recovery workspace. The worker encrypts the approved input under a job/actor-specific protection purpose, uses separately scoped ephemeral credentials, and clears that input after completion/failure/revocation. No scientific bytes are embedded in the key file or cached in the queue.

Guided production import supports **standard AWS S3 HTTPS endpoints only**. Custom/REST/private endpoints, alternate ports, credentials in URLs, encoded/traversal paths and unrecognized environment fields are rejected. HTTPS certificate verification remains active. Advanced protected repository configuration remains available separately; guided import does not turn it into an arbitrary outbound client. No account, bucket, IAM policy or charges are created automatically. First-time independent-storage provisioning and actual S3/account-loss recovery still need an accepted provider workflow; an owner must not be asked to invent secret files.

The file names an independently verified exact checkpoint. An explicit option can find the newest compatible independent checkpoint using bounded native metadata. New copies use one fixed logical stdin path and bind backup identity, original UTC and bundle hash in authenticated repository tags. Copy/retry time is not treated as a new scientific epoch; ambiguous same-second checkpoints require an exact selection. Original/new addresses and actual checkpoint identity are reviewed before activation. Original claim/evidence origins remain frozen. Old unsent packages bound to a lost address are held rather than rewritten or silently reauthorized.

## Updates

Only a signed official pinned image/source/version and an exact administrator-approved operation can reach the compiled update runner. Railway runtime performs that check before opening listeners. Primary **and independently keyed** restore checkpoints must be freshly verified. Approval is read using original schema columns before new columns exist. Original source-schema evidence, identity, events/outbox and audit digests are protected by exclusive transactional table locks and existing deadlines. Changes after preparation require a new checkpoint; the runner excludes only its own bookkeeping completion from that comparison.

A failed transactional migration rolls back the complete batch. An already applied exact operation is idempotent and does not make future restart depend on a former administrator's membership. Unknown/incompatible schemas, modified scientific/identity/operational records and an unauthenticated image are refused. A container rollback does **not** roll back a changed schema: after a successful incompatible schema change, recovery requires a compatible image/database/key pair.

The actual-process fixture compiles the accepted old source and this source into separate isolated binaries. Its `0.7.1` informational version, publisher key and image string are **synthetic test inputs**, not a published future release or registry attestation. It checks stale history refusal, deliberate PostgreSQL failure, old-binary recovery, successful migration, idempotence and new-process health with original evidence/MFA.

The portal does not advertise an `Apply Safely` provider button. Automatic authenticated Railway image selection/deployment, exact registered callback/project-write authority, production signing/distribution and actual failed provider rollout remain blocked until a genuine authorized provider contract is exercised. No speculative general-purpose Railway client or manual environment-file workaround is substituted. Native source/package preparation is not production update acceptance.

## Publication boundary

The pinned SDK graph, volumes, native references, private verified PostgreSQL, strict image metadata and required-owner prompt are prepared. Generated native domains are not authored by the documented IaC DSL. An authorized publisher must validate the real native composer, required blank owner field, HTTPS domain and accepted immutable registry identities, then publish the verified target. No images, public template IDs, projects or accounts are invented. [P28 handoff](../validation/v0.7.0-p28.md) distinguishes repository acceptance from that publication/provider boundary and real MSFS/Discord acceptance.
