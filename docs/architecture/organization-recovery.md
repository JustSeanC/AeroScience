# Organization security, recovery and update contracts — P26

## P28 integration corrections

Paired restore now validates retained P27 Discord destination credentials using the original restored key ring, certificate and organization/destination protection purpose. It checks the masked endpoint identity, rejects unusable or cross-purpose ciphertext, and requires deleted destinations to contain no credential. Verification neither enables a destination nor sends an HTTP request. Older supported source schemas without P27 tables are not migrated during verification. Real encrypted restore and independent primary-loss tests include disabled protected notification configuration; a separately valid encrypted dump with damaged credential bytes fails verification.

Compiled update verification additionally hashes original source-schema columns of live consent/policy, authoritative events and Discord destinations/consents/disclosures/outbox under the existing exclusive transaction. It streams rows using fixed table names and PostgreSQL-quoted original column metadata. A new additive column/table does not invalidate the original projection; changing original operational records does. A real PostgreSQL trigger that rewrites an event during compiled migration now rolls back the entire batch while preserving received evidence, schema and history. Existing identity/evidence/audit checks and lock/deadline limits remain unchanged.

These checks do not reconcile externally posted messages after a historic backup is promoted. Keep recovery deployments isolated, with delivery disabled, until an authorized operator compares external receipt history and rotates/reapproves destinations. Actual provider promotion, account-loss recovery, certificate/key rotation and failed-image rollback remain [P28 release gates](../validation/v0.7.0-p28.md).

## Completion pass: independent copies and real retention

`Organization:Operations:Independent` optionally configures a different protected repository, private password file, private credentials file, CA and bucket-addressing style. The encryption key must differ from the primary. Production requires independently scoped credentials, not inherited Railway account credentials. Credential files contain only the explicitly allowed AWS or authenticated REST fields. Restic subprocesses clear inherited AWS/restic configuration and password-command variables before applying the selected destination's configuration. Both encrypted repositories use `--no-cache`. An independently controlled account/failure domain remains an operator/provider acceptance requirement; merely using another URL is not proof.

The worker authenticates the exact original snapshot, creates a separately encrypted copy, and restores that copy into isolated PostgreSQL to check original evidence, audit, schema and protected identity. Fixed original-snapshot tags make retries discover the same copy. Only bounded private ephemeral staging exists; it is removed on success/failure. Raw backup material does not remain in an application cache. Repository hashes bind metadata to destinations so a changed configuration cannot silently prune another repository. The explicitly downloaded private recovery kit includes the independent key and scoped credentials; save it outside both provider accounts, with private access. A recovery kit alone is not a copy of the encrypted repository.

Automatic retention defaults **off**, including migrated policies. It requires explicit administrator/MFA/password consent and an independent destination. It retains the newest independently restored checkpoint, all points less than 24 hours old, every unverified point, and the newest point in each selected UTC date/ISO week. Daily/weekly counts refer to nonempty observed date/week buckets, not invented snapshots. Indexed metadata is read in pages of 100; at most 20 expired verified points are deleted per cycle. Both protected surviving copies are freshly authenticated before any pruning, so a historical verification timestamp cannot hide a missing remaining copy. Exact original and independent candidate hashes/manifests are rechecked before an audited deletion intent is committed. Exact snapshot IDs are forgotten, then unused encrypted packs are pruned with bounded repacking. Intent survives interruption and exact deletion can safely retry. Metadata/audit history remains, clearly labeled deleted; the last verified point is never selected for deletion. Storage may not shrink by the logical snapshot size because retained encrypted chunks are deduplicated.

The synthetic infrastructure test removes the disposable primary repository, key, PFX and the entire primary organization database, then discovers/restores the original organization from the separately encrypted repository. It verifies actual evidence and audit identities and cleans temporary material. This is isolated infrastructure recovery, **not** a real Railway account-deletion test or a guided live disaster promotion. Independent credentials/account ownership, destructive cloud-loss recovery, complete guided restoration and retention controls on the destination provider remain external/operational gates.

## Completion pass: controlled compiled schema updates

The operator-only `--apply-prepared-update` runner starts no listener. It requires a valid signed pinned distribution matching this exact binary version/source, the original completed administrator-approved preflight, still-active MFA administrator authority, the approved source schema, and a reverified paired restore checkpoint with the original certificate. It does not download or apply an arbitrary image. It accepts only compiled migrations in this binary; no SQL or script comes from a request/template/distribution file.

The runner has a 15-minute overall cancellation bound, matching the existing operations worker. It rechecks source history, acquires a finite-deadline advisory lock and exclusive locks on organization/history tables, refuses transaction-suppressed migrations, and executes the bounded compiled migration batch in one transaction. Original received-evidence and audit digests must remain identical before committing. Authority is rechecked under the boundary; a successful update appends its own audit event in the same transaction. Concurrent/stale source changes fail closed. A received approval for another binary is refused before opening a database. An actual PostgreSQL trigger fixture fails the final history insertion after compiled DDL ran; all schema changes roll back and original evidence, organization, password/security stamp and decrypted authenticator remain intact. Removing the fixture then permits the same supported compiled migration.

Provider image promotion, draining/replacing old processes, rollback to a prior container, independently staged restore promotion and a beginner update/recovery interface remain **unaccepted**. Existing ordinary production startup still refuses pending migrations. This helper does not bypass that guard, authorize a paid deployment or establish production update readiness.

## Identity and authorization

The same ASP.NET Core Identity user/token tables, existing PostgreSQL key ring and protected PFX remain authoritative. `ProtectedOrganizationUserStore` encrypts Identity token values under user/provider/name-specific Data Protection purposes; authenticators and recovery codes are not plaintext database columns. Unprotected token fallback is refused. Production administrators require enabled MFA, verified saved-code recovery and a signed second-factor session. Primary password authentication uses Identity's two-factor challenge path. TOTP verification additionally rejects reused time steps under the existing membership lock. Failed verification retains lockout behavior; recovery codes are atomically consumed. Successful recovery/replacement changes the security stamp and revokes desktop grants. A refresh preserves the original bounded MFA proof, never invents a new one. Passwords/codes are excluded from command receipts, audits, URLs and logs.

Protection APIs require active Administrator membership plus current security stamp and MFA. Mutations require recent MFA and password confirmation, exact origin/CSRF and existing idempotent command receipts. The singleton schedule is approved organizational processing, not permission to access private pilot archives. Jobs recheck authorization before starting. Concurrent commands use the existing authoritative transaction pattern and a dedicated advisory lock. Stale interrupted operations become visibly failed, not successful. Schedule/backups and operation history survive restart; ordinary page reads are bounded.

## One authoritative data store

Original expressly submitted P17 evidence, receipts, users, immutable claims/publications, reviews and audit remain in PostgreSQL. No attachment migration, desktop science copy or second evidence database exists. A server backup is a disclosed authorized organization-held copy, not a hidden local pilot archive. Unsent/deleted local science never enters this backup.

A backup holds an exported PostgreSQL repeatable-read snapshot while native `pg_dump` creates a consistent custom-format dump. The same snapshot supplies evidence and audit digests. Original received payload hashes must match before backup proceeds. The small versioned envelope also contains the original protected identity PFX, its credential and a manifest (organization/origin, application/source/schema, certificate/dump hashes, received-evidence and audit digests/counts). It uses a strict four-entry layout, no arbitrary extraction paths and bounded streaming. It is an infrastructure recovery envelope, not a competing scientific archive format.

Native restic authenticates/encrypts the envelope into a protected repository using a separate operator/native-generated key. Production repositories require HTTPS S3 or HTTPS REST without embedded URL credentials; local filesystem repositories are explicitly development-only. S3 addressing is validated `auto`/`dns`/`path`; Railway's modern virtual-hosted endpoint needs `dns`, not restic's default custom-endpoint path behavior. TLS remains verified. The optional image copies maintained digest-pinned restic and PostgreSQL clients; native client dependencies are isolated to their subprocesses. No shell, arbitrary user command or executable template is accepted by the API.

Private temporary work is restricted to the system temporary tree; symlinks are refused, files/directories are 0600/0700, writes/reads have package bounds, and cleanup runs on success/failure. A killed worker's exact generated temporary directories are removed after the operation's deadline/stale window. The deployment must provide ephemeral work storage; this is not an approved persistent plaintext spool. Process output is bounded, cancellable and never returned raw to a browser.

## Actual paired restore verification

`Discover` recovers an exact snapshot manifest from the authenticated repository without relying on primary database metadata. Wrong keys, changed hashes, unknown layouts, incompatible schemas or missing original private identity fail closed. `VerifyRestore` provisions only a generated `aeroscience_recovery_<random>` database using a separately configured recovery role; production recovery also requires VerifyFull. Native `pg_restore` restores the package. Verification compares exact organization identity, original payload/audit digests/counts, schema and certificate, and decrypts retained Identity authenticators using the restored key ring and original PFX. It removes only that disposable database and temporary work, never the primary.

Focused fixtures actually submit authorized retained pilot-documentation evidence via P16/P17, create encrypted MFA, back up, delete the disposable source records, discover the repository snapshot and restore independently into another real PostgreSQL database. Corrupt package hashes/wrong keys are rejected. These tests prove the implemented restore interpretation, not provider-loss recovery or novice replacement of a live organization. A full owner-facing disaster-recovery deployment and verified restore after account/project loss remain unimplemented acceptance gates.

## Recovery destination, keys and deletion risk

Railway Buckets are private S3-compatible storage at the officially checked price of $0.015/GB-month (2026-10-29); bucket API/egress are listed free, while service-to-bucket transfer still counts as service egress. They currently lack server-side encryption, object locks, object versioning and lifecycle configuration. Client-side restic encryption protects confidentiality, not deletion by someone who controls the provider credentials. Native variable references can scope bucket credentials; no API secret belongs in a mission/export.

A same-project/account Bucket is **not** protection against deletion/compromise of that project/account. Provider volume snapshots also do not protect the independently held identity dependency. Production needs an independently controlled copy/access path, a separately saved recovery key, retention/deletion enforcement, and tested restoration after loss of the primary account. HTTPS append-only rest-server or an independently controlled S3-compatible destination are supported repository contracts; their actual provider credentials, isolation, immutability and deletion behavior still require acceptance. No destination is auto-purchased.

The explicit Recovery Key download includes the repository encryption key and available scoped S3 credentials. It must be protected outside the source provider account; it is not proof that the owner saved it, nor a substitute for independently accessible objects. The independent recovery-kit section also includes its scoped authenticated REST credentials where configured; legacy primary REST credentials must be recovered separately. Automatic retention is now implemented as described above and remains off until explicitly approved. Storage can still grow; provider retention/immutability compliance is not inferred. No pending local evidence is ever preserved to bypass deletion.

## Updates and failed updates

The existing semantic-version comparator was moved into Shared without changing its rules; desktop update behavior delegates to it. Server update metadata is small strict typed JSON, ECDSA/SHA-256 verified against an operator-protected publisher key, official repository/image **digest**, exact source/schema and mandatory paired-recovery policy. A mutable tag or invalid signature fails. No accepted production distribution/feed has been published.

An authorized **Prepare Verified Update** creates and independently verifies a paired checkpoint before reporting preflight completion. It does **not** invoke a provider API, pull/apply an image, migrate a live schema or claim rollback. Production startup refuses unknown schema and now refuses pending migrations on an existing production database until a supported paired-recovery rollout is accepted. Fresh compatible databases initialize normally. Local fixtures retain their explicit isolated migration behavior for regression validation.

A passing isolated restore after deleting disposable source records is not a full provider failed-rollout rehearsal. The completion pass adds transactional table-write boundaries, actual failed-migration rollback and safe opt-in retention. P26 still needs provider maintenance/rollout, full failed-image paired restoration with original origin/identity, data-loss disclosure and novice recovery. Reverting only a container image is never described as schema rollback.

## Railway trust and privilege boundary

See the [native candidate](../../deploy/organization/railway/README.md). The application never trusts a first visitor, wildcard proxies, `X-Railway-Edge` alone, or unverified PostgreSQL TLS. The private public-CA attestation is challenge/HMAC authenticated with an independent provider-generated shared key and bound to exact private hostname. Only the public CA is transmitted; native VerifyFull still validates the actual server certificate hostname. Rotation is rechecked at startup; uninterrupted live CA rotation is not claimed.

The root-owned-volume initializer touches only `/configuration`, rejects symlinks, sets its owner/mode, discards supplementary groups and permanently sets real/effective/saved UID/GID 1654 with no-new-privileges **before reading deployment secrets or listening**. Production Build refuses a root application. Normal/operations images remain non-root. The temporary bootstrap profile's `USER 0` is not permission to run the organization application as root.

Railway's documented health Host `healthcheck.railway.app` is accepted only for a bounded status-only readiness check in Railway mode, never for identity/domain/API authorization. Other requests retain exact HTTPS-origin and finite trusted-proxy rules. A provider health response is not production acceptance or continuous monitoring.
