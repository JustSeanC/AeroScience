# v0.3.0 Windows build, testing and public alpha

## One command produces the release installer

Maintainer prerequisites: Windows x64, Git, Python 3.11+, Node 22+, pinned .NET SDK (`global.json`), Visual Studio x64 C++ Build Tools, installed official MSFS 2024 SDK and Inno Setup 6.3+ (6.7.3 supported). Pilots need none of these development tools. The full SDK and native Windows/installer checks cannot run in the Linux cloud workspace.

1. Open **Start → x64 Native Tools Command Prompt for Visual Studio**. Enter `pwsh -NoProfile` to switch from Command Prompt into PowerShell 7 while retaining the compiler environment. `Set-Location` works in PowerShell, not Command Prompt.
2. Preserve any local edits before pulling. In PowerShell:

```powershell
Set-Location 'C:\Dev\AeroScience-release'
git status --short
git pull --ff-only origin main
git log -1 --oneline
```

Use a clean committed Git checkout. Do not blindly discard local work to satisfy a clean-source check. Pinned geography/vendor bytes must remain unchanged. If you need a new checkout, clone the existing repository into an unused directory rather than using GitHub's source ZIP.

3. Reuse your existing private-safe runtime attestation `C:\AeroScience-Release-Records\runtime-approval.json` while it matches the installed native `SimConnect.dll` hash. Redistribution authorization was confirmed with **no additional conditions**. Keep original correspondence private. A changed DLL requires a newly hash-bound attestation using the documented [runtime process](runtime-distribution.md), not new publication of correspondence.
4. Build into a fresh versioned output directory:

```powershell
pwsh -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\release\Build-Release.ps1 -SdkRoot 'C:\MSFS 2024 SDK' -RuntimeApprovalRecord 'C:\AeroScience-Release-Records\runtime-approval.json' -RuntimeRedistributionConfirmed -InnoCompiler 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe' -OutputDirectory 'C:\AeroScience-Builds\Remote030-1'
```

This runs locked restore, .NET tests, frozen npm tooling, bundled asset hashes, JavaScript checks, release/helper tests, actual Playwright browser tests, actual-process crash/restart recovery, Windows self-contained publish, native ABI compilation against your SDK, genuine SDK full-toolbar compilation/structural validation, native runtime load/exports/hash/authorization, signed Microsoft VC++ prerequisite and Inno compilation. If Edge/Chrome is present it is used for browser tests; otherwise the maintainer's test Chromium is installed. No development/test browser is a pilot runtime dependency.

**No acceptance questionnaire or ACCEPTANCE.json editing is required.** Generated technical evidence finalizes unchanged compiled installer bytes automatically. A failure stops finalization; do not bypass SDK, runtime, licensing, asset or test validation. `Build-ReleaseCandidate.ps1` remains a compatible entry point and calls the same default automatic flow; `-PrepareOnly` is advanced intermediate troubleshooting. Legacy explicit `New-Release.ps1 -AcceptanceRecord` is retained only for older candidates.

Expected final files **only after this command succeeds**:

```text
C:\AeroScience-Builds\Remote030-1\AeroScience-Setup-v0.3.0.exe
C:\AeroScience-Builds\Remote030-1\AeroScience-Setup-v0.3.0.exe.sha256
C:\AeroScience-Builds\Remote030-1\AeroScience-Setup-v0.3.0.release.json
C:\AeroScience-Builds\Remote030-1\RELEASE-NOTES.md
```

The optional `AeroScience-v0.3.0-win-x64.zip` and checksum are secondary; the CANDIDATE ZIP is internal. `build-evidence/` contains actual test reports and generated technical evidence. The public release record is sanitized and explicitly says **hardware_acceptance: notVerified**, **github_publication: notPublished**. Automated checks do not assert Windows GUI execution, real MSFS/VR/iPad acceptance or public availability.

Rerunning the same command from the same clean source verifies a complete, unchanged final output and returns it without rebuilding/overwriting it. Partial/corrupt/different-source/another-version outputs are distinguished and preserved; choose a new output directory for a new attempt. If an old interrupted candidate is the only output, retain it for diagnosis instead of treating it as finalized.

## Recommended actual Windows/MSFS checks

These are real hardware QA to report honestly, not mandatory manual JSON gates. Prior-version passes do not verify v0.3.0. Use disposable archives for destructive checks and preserve backups.

1. **Installation/upgrade:** run the final setup EXE, check branding/version/path, signed VC++ prerequisite, Start/optional desktop shortcuts, Installed Apps/uninstaller and automatic launch/dashboard. Upgrade a v0.2.2 profile and compare mission IDs/modes/Mach, settings/maps/presets, both locations and source/product references. Existing map/limit choices must stay unchanged.
2. **First-run maps:** in a fresh Windows profile verify no external tiles before privacy choice; choose offline-only. In a separate fresh profile choose OSM, see attribution/recognizable Streets without key. Disconnect internet/provider and confirm offline fallback preserves routes and saved preference. Check visible-only maps, optional own-key Esri and two-browser preference synchronization.
3. **SimConnect/native toolbar:** start MSFS, connect a fixed-wing and rotary-wing/unknown aircraft, compare actual telemetry/Mach, open the installed toolbar and test header drag, every resize edge, scroll, close/pop-out, Mission/Payload/Map and Compact VR toggle. Never use custom window dragging to conceal a native regression.
4. **Science:** follow [quick start](remote-sensing/quick-start.md). Import genuine small Landsat/Sentinel/ENVI/DEM collections with documented license/date/resolution. Fly over valid coverage, enable each payload, inspect actual products/quality/three clocks, tilt and source edges, nodata/clouds, pause/resume while flight continues, and a changed/disconnected source. Confirm ambient temperature is not a thermal image; DEM is not LiDAR. Do not represent a synthetic browser screenshot as this test.
5. **Archive/exports:** end mission, close MSFS and disconnect internet; reopen history/products/spectra/profiles and JSON/CSV/GeoJSON/GPX/KML/PNG/evidence. Compare sample values/units/source dates and hashes with original collection values. Missing Mach in old history remains valid.
6. **Storage:** verify new 25/50 GB defaults, custom/Unlimited persistence, existing limits preserved, usage/free space and 80/95/100 states. Pin mission/dataset, generate previews, inspect table filters/grouping/pages/ages/estimates; cancel then confirm cache cleanup and compare actual result/history with retained originals/backups. Set a deliberately small science cap: flight continues; small flight cap: recording stops with explicit persistent reason and committed samples survive. Restore appropriate limits afterward.
7. **Data safety:** stopped-store migration to another drive/restart and unavailable external-drive recovery; explicit no-backup vs backup Data Management with correct phrases/cancel/wrong phrase; prior backups and unrelated files preserved. Optional compaction must create/verify backup and report actual allocation, not claim deleted observations.
8. **Updates:** offline startup/archive works without GitHub; Check for updates failure is nonblocking, channel/disable/remind choices persist. Release/Download actions open only the official verified GitHub page and never run an installer.
9. **Devices/performance:** actual Quest 3 VR readability/input, physical iPad private-LAN pairing/control/unit sync, source import and multi-payload processing during 1 Hz recording, missing cadence/gaps and CPU/memory. Do not mark passes without those devices.
10. **Uninstall/reinstall:** verify data/settings retained, toolbar Keep/explicit Remove choice, MSFS-running guard, unrelated add-ons untouched and restored archive after reinstall. Record observed results outside release source; no JSON hand editing is required.

## Publish on GitHub manually

1. Open <https://github.com/JustSeanC/AeroScience/releases/new>.
2. Choose/create tag **v0.3.0** at the exact source commit printed by the successful build (use GitHub's commit selector, or confirm main still points there). Never move an existing release tag to different code.
3. Title: **AeroScience v0.3.0 — Remote Sensing & Research Payloads Alpha**. Paste `RELEASE-NOTES.md`. Keep its explicit unverified hardware statement; append only actual gaming-PC results with environment details. Mark **Set as a pre-release**; this is public alpha despite the conventional filename.
4. Attach the **final setup EXE**, matching `.exe.sha256` and `.release.json`. The portable ZIP/checksum are optional. Do not upload CANDIDATE archives, private approval correspondence, personal databases, raw scientific archives or `build-evidence` containing local paths.
5. Publish the release, download the EXE/checksum in an ordinary browser and verify SHA-256 matches the sidecar. Do not claim public availability until this succeeds. Pilots download and run that EXE; they do not extract folders or execute PowerShell.

No self-hosted runner is required for this process. The optional Actions workflow can build on a future authorized Windows SDK runner and publish its already validated artifacts; it has no mandatory acceptance-JSON input.

For build errors share the complete first failing test/error block and relevant `build-evidence`, `installer-prerequisites/inno-build.log` or SDK contract log. The installed app's Collect Feedback gathers local diagnostics; exclude keys, pairing codes, private correspondence and personal research.

## Automatic scientific-data acceptance on the gaming PC

The cloud report covers real public numeric data plus explicitly synthetic flight input. It does not verify Windows networking, native cost detection, onboarding dialogs or real flight sampling. The build checks the recorded genuine-provider evidence against the canonical LF source hashes; a changed provider/reader requires a fresh developer network run, not a manual pass questionnaire.

1. Install the setup normally. Onboarding must offer scientific-data consent independently of map consent, with offline-only available before any scientific query. Existing settings, modes, mission history, sources and library paths must survive upgrade.
2. In Settings → Scientific Data Sources enable scientific access; confirm the default 64 MiB/1 preparation and retained 25/50 GB caps. Toggle unmetered-only and verify the displayed Windows network cost or explicit unknown pause; restore the desired policy.
3. In the Planner enable terrain, thermal and multispectral, create a small real survey/route and save. Preparation should start automatically if background retrieval is on. Try the explicit Prepare scientific data button; check provider, scene date, coverage, QA, transfer bounds and actual status. A larger plan must disclose its eight-cell partial limit.
4. For reproducible initial checks, use an area near 40.005°N, 74.995°W with latest source date 2024-09-10, lookback 120 days and clearest policy. Genuine cloud acceptance found Landsat and Sentinel scenes on 2024-09-03 there. This is a test location/date, not guaranteed provider availability. For global terrain try 46.105°N, 8.105°E and verify the **Copernicus DSM / EGM2008** label.
5. Start an actual MSFS flight in prepared coverage, enable the instruments and record. Verify subsequent valid products in Science Collection, real aircraft position and packet UTC, separate external source UTC, retained band scales/QA and data exports. No product may be recorded merely because the catalog returned a scene.
6. Test an unplanned flight with background retrieval on. Small cells should prepare without interrupting the 1 Hz recorder. Disable background retrieval and confirm explicit preparation still works. Cancel/retry; cancelled or missing intervals must not later appear as live observations.
7. Try unavailable/cloud-masked areas, no internet, a provider outage, a low per-download limit and a science cap/drive-space shortage. Inspect the explicit reason. No fabricated measurements, full-scene fallback or automatic original/product deletion is allowed; history and committed flight samples remain accessible.
8. Close MSFS and disconnect internet. Restart AeroScience and review complete history/products and exports. Retained sources must remain usable for later covered flights without redownloading; unavailable external drives must show an error instead of an empty replacement.
9. Hyperspectral discovery may show actual NASA granules and their dates/formats. It must state **discovery only / automatic preparation unsupported** and must never silently fetch protected multi-GB data, bundle credentials or manufacture spectra. Advanced manual ENVI import remains functional.
10. Recheck native toolbar movement/resize/scroll, source/mission synchronization, Quest 3 and physical iPad. None of these hardware-dependent checks is established by browser fixtures or the public-provider cloud run.

### If genuine-provider evidence is pending

Do not bypass this release hold. A cloud transport failure left the final network rerun pending despite earlier successful real-source runs. Maintainers can finish it on a machine with working provider access (Windows/MSFS is not needed for this isolated data check):

```powershell
Set-Location 'C:\Dev\AeroScience-release'
dotnet run --project .\tests\AeroScience.ProviderAcceptance -- --network --hyperspectral --output 'C:\AeroScience-Builds\Provider030-1'
python .\scripts\release\record_scientific_acceptance.py --folder 'C:\AeroScience-Builds\Provider030-1'
python .\scripts\release\verify_scientific_acceptance.py
```

Use a new empty output directory. Only continue after the real-data run succeeds; never use `--pending-final-rerun` to approve a release. Review/commit the generated non-confidential source evidence with `git add docs/research/v0.3.0-automatic-provider-acceptance.json` and `git commit -m "Record successful final v0.3.0 provider acceptance"`, then use the normal clean-checkout Windows build. No acceptance JSON hand editing is required. The data check explicitly uses synthetic flight positions; Windows/MSFS/device acceptance stays separate.
