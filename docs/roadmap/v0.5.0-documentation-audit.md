## Sustainable organization and navigation

Create **`docs/README.md`** as the central maintained index in the cleanup PR, linked from
root README and INSTALL. Organize by audience/task first; physical moves are optional
and must earn their reference-update cost:

| Area | Maintained entry/content | Protected/current material stays reachable |
|---|---|---|
| Users | INSTALL; one current pilot guide; mission planning; remote-sensing quick start, troubleshooting and advanced manual import | Current v0.4.2 pilot/QA links unchanged; retain separate advanced source instructions |
| Development/architecture | `docs/architecture.md`, setup/build/test workflow and current data contracts | Current source-grounded schema/services plus links to proposed v0.5.0 contracts, clearly marked planned |
| Scientific methods/data | Current source support/method index, existing `remote-sensing/` guides and referenced instrument/geometry/QA/export specifications | Dated reference documents and independent numeric validation retain provenance/limitations |
| Roadmap/specifications | One active scope/architecture/PR/acceptance/decision package plus DOC-01 audit | Original approved backlog and deferred campaign/EMIT scope retained; no repeated minor-version handoffs |
| Release/acceptance | One maintainer release procedure, current QA/testing index and concise release history | All v0.4.2 completion/testing/evidence/before-after paths remain intact during external QA |
| Research/verification | Existing `docs/research/` records and selectively retained visual baselines, indexed by purpose/status | Original hashes, as-of dates, failed/pending limitations and machine consumers preserved |

Optional future `docs/user/`, `docs/development/`, `docs/science/` and `docs/releases/`
directories can be introduced only for useful new/consolidated content. Do not force
a wholesale relocation of accurate scientific specifications or active QA evidence just
to achieve a folder layout. Avoid empty archive trees and duplicate canonical guides.

## Cleanup PR execution and acceptance

1. Refresh the inventory from latest development and inbound references before each batch.
   Freeze the full v0.4.2 QA file set and compare its bytes/paths to the QA baseline;
   include external tester links and relevant v0.4.1 reference material in that review.
2. Establish the index and canonical instructions, extract enduring facts, and prepare a
   concrete old-path → canonical-content/deletion/retention map. No application behavior,
   schema, scientific calculation, SDK/runtime approval or baseline test weakening.
3. Update unprotected docs/navigation, Help/package content references and relevant documentation
   assertions together. Keep required old Help URLs using narrowly justified compatibility
   entries when necessary; do not convert every obsolete file into a permanent redirect.
4. Remove agreed clutter on `chore/v0.5.0-docs-cleanup` only. Preserve root licenses/notices,
   all required scientific JSON/fixtures, active user/source guides, verified scientific
   assumptions and protected QA screenshots/reports at original paths.
5. Check all internal document paths **and anchors**, root/repository/packaged/Help URL
   contexts, code/test/script/workflow references, XML content globs and generated release
   manifests. Publish/cross-publish and inspect bundled Help/portable payload structure;
   run existing documentation/packaging/security/scientific-verifier and affected browser
   checks without changing expected scientific results. No installer publication is needed.
6. Manually review current installation, pilot/developer navigation, source-import Help and
   release instructions. Confirm current supported features and explicit planned scope;
   no claim that guide loading or test fixtures verify hardware behavior.
7. PR description supplies a short **deleted / consolidated / relocated / preserved**
   ledger with reasons, counts/size reduction, old→new paths, test commands/results and
   any outstanding checks. Mark DOC-01 complete only when navigation/link/tooling closure
   and QA/scientific preservation criteria in the acceptance plan pass.
