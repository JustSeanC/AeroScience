## Derivatives and implementation strategy

1. Keep both approved source files and their README untouched. Add a deterministic,
   maintainer-side derivative generator using a pinned, license-reviewed SVG renderer and
   established PNG/ICO encoding. Record input hashes, tool version, dimensions and output
   hashes; do not require testers to install graphics tooling or fetch logos online.
2. Generate source-controlled deliverable resources in a clearly named generated-assets
   location and wire them into the existing web/Desktop/installer package content. Verify
   regeneration in CI so ordinary .NET builds do not depend on a renderer being installed.
   The renderer must support the primary gradients/alpha and toolbar fill/stroke faithfully;
   no hand-optimized small-size redraws are authorized.
3. Proposed primary derivatives: favicon PNG/ICO at 16/32 as needed; multi-frame Windows
   ICO including **16, 24, 32, 48, 64, 128, 256 px**; transparent PNG size variants for
   **180 px Apple touch** and **192/512 px PWA** consumers, plus any measured existing UI
   need. Validate the requested 16/24/32/64/256 sizes rather than assuming larger rasters
   prove small-icon legibility. ICO frames must retain alpha and correct dimensions.
4. Use PWA `purpose:any` unless a separately padded safe-area derivative is actually
   validated without cropping/color/proportion changes. Do not let browser/OS icon masks
   clip the flight arc. Preserve `start_url`, app identity, display/theme/navigation and
   offline behavior; no service worker/cache subsystem is introduced for branding.
5. Preserve aspect ratio with contained image rendering and retain whole-artwork margins.
   Keep transparent master/PNG/ICO resources. If a specific installer canvas lacks alpha,
   composite only the displayed wizard surface as its format requires; do not flatten or
   replace the approved transparent sources. Use the installed Inno version's supported
   dimensions/formats, not guessed universal artwork sizes.
6. Preserve existing URLs where practical and verify Windows/browser icon-cache upgrade
   behavior. The engine already serves static assets with `Cache-Control: no-cache`;
   do not disable existing controls or prescribe deleting user data to refresh an icon.
   Any renamed derivative must have all HTML/manifest/project/installer consumers updated.
7. Generate/compile branding before normal packaging hashes/receipts and before testing
   the installer. Never modify the tested EXE, Community package or release checksum
   afterward to insert a logo. Keep AppId, EXE/shortcut names, storage and uninstall policy.

## MSFS compatibility and verification boundary

Observed repository contract: an SVG at
`html_ui/icons/toolbar/ICON_AEROSCIENCE.svg` is copied into the package and selected
by the `ICON_AEROSCIENCE` SPB definition. The legacy file uses a 64-square viewBox;
the approved reference uses 1254-square scalable coordinates. A viewBox is not a
fixed display-pixel size and is not evidence of a universal SDK-required 64 px asset.

Official references inspected online (HTTP 200, 2026-10-20):

- [MSFS 2024 SDK introduction](https://docs.flightsimulator.com/msfs2024/html/1_Introduction/Introduction.htm).
- [JavaScript / Coherent context](https://docs.flightsimulator.com/msfs2024/html/6_Programming_APIs/JavaScript/JavaScript.htm).
- [Toolbar panel listener reference](https://docs.flightsimulator.com/msfs2024/retail/programming-apis/javascript/coherent-listeners/js_listener_toolbar_panels/).

The inspected public toolbar-listener page does **not** establish custom SVG feature
support or a fixed allowable icon-size list. Compatibility therefore remains an explicit
feature acceptance gate: inspect the actual target SDK's samples/schema and current UI
renderer behavior, confirm permitted icon format/viewBox or explicit dimensions, and build
the genuine SPB/Copy package using the existing official SDK scripts. If format-only size
metadata is required, preserve the original coordinate system and uniform proportions.
Do not guess a supported PNG substitute or silently redraw the black arc if the simulator
tints icons; report and resolve the renderer limitation against the approved design.

Package/layout validation proves resource inclusion, not appearance. Check the actual
toolbar icon and any selected/hover/disabled states at real UI scale, with a dark simulator
toolbar and relevant backgrounds, ensuring the black arc and thin white outline survive.
Inspect light contexts where used; do not substitute this white variant for the primary
application mark. Compile success and browser previews cannot establish MSFS acceptance.

## Dependencies, risks and acceptance

UX-02 is independent of calibration, collection automation, grading and provider engines.
It may run after architecture review in parallel with those PRs. Coordinate shared Help/
project/packaging paths with DOC-01 and shared native/CSS files with UX-01; neither should
overwrite the other's changes or historical QA screenshots. No runtime schema/API change
or scientific-data dependency is required.

Risks are tiny-keyline rasterization, primary gradient fidelity, platform icon masks,
Windows/favicon caching, SVG tint/format differences, invalid ICO resources and omitted
publish paths. Resolve through faithful generation, contained rendering, deterministic
resource/reference tests and actual platform inspection, not redesign. Missing Discord
artwork is explicitly outside scope and is not a blocker.

Acceptance IDs **UX02-SOURCE / UX02-ASSETS / UX02-SURFACES / UX02-PACKAGE /
UX02-CONTRAST / UX02-LIVE / UX02-REGRESSION** are defined in
[the feature acceptance plan](v0.5.0-acceptance.md#ux-02--branding-integration).
All branding-integration criteria remain **Pending**. No active replacement, PNG/ICO
deliverable or Windows/MSFS rendering acceptance is claimed by this planning update.
