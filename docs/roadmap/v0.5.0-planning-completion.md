## Architectural conclusions

- Extend the existing instrument catalog/profiles, two data stores, GeographicLib-based
  geometry, acquisition pipeline and ENVI importer. No duplicate engines are proposed.
- Keep raw simulator measurements, external dataset values/QA, calibration-derived
  channels, modeled geometry, operating compliance, scientific yield and pilot grades
  distinguishable. Freeze effective settings, obligations and versioned rules for replay.
- Collection becomes an independent backend-owned lifecycle: Armed, Collecting, Paused
  and Ended. Manual holds take precedence, End is terminal for that flight, and science
  End does not stop flight recording. Triggers require recorded, continuous evidence.
- Extend current direct-provider acquisition for bounded geographic Library jobs and
  supported AVIRIS assistance. EMIT remains catalog discovery only; native NetCDF-4
  processing stays deferred to v0.6.0 or later.

Important source findings are assigned to focused future PRs:

| Automatic queue dictionaries are not a generic durable Library job store | Extend existing saved-session orchestration and acquisition services with durable approved intents |
| Existing NASA discovery/import does not prove protected downloading or every AVIRIS format | Validate actual access and Classic/NG distributions separately; provide truthful supported/guided/unsupported states |

## Proposed implementation sequence

1. Versioned contracts and durable evidence/persistence.
2. Calibration and documented operating assessments.
3. Collection lifecycle and backend route/boundary triggers.
4. Preflight readiness, scientific yield, live scoring and reproducible final grading.
5. Geographic catalog, durable Library acquisition and map-based selection.
6. NASA discovery, official authorization/handoff and verified AVIRIS import assistance.
7. Dashboard/paired-device/native integration and end-to-end acceptance.

DOC-01 cleanup and UX-02 branding can proceed independently after planning review.
Catalog, instrument and lifecycle work also have parallel opportunities documented in
the PR plan. These are proposed feature branches, not implemented features.
