# AeroScience v0.8.0 — P01 Usability Audit & Risk Register

**Audit:** 2026-11-10. **Method:** static read of the connected repository on `develop/v0.8.0`, the v0.7.0 validator/UX notes and owner-provided previous feedback. **Not** a completed independent human usability study, a browser screenshot audit or a successful Windows/MSFS test. See `v0.8.0-screen-inventory.md` for migration details.

**Approved decisions:** auto dashboard theme; guided first-run; balanced spacious density; en-US/es-ES/fr-FR/de-DE/pt-BR first-wave localization.

## Ranking method

**P0:** can mislead critical recording/science state, evidence truth, permissions or destructive controls. **P1:** blocks a novice's core mission or causes serious repeat task friction. **P2:** makes routine discovery and analysis harder. **P3:** polish/lower-frequency expert workflows. A finding is tagged **owner-reported** if in past validation feedback, **source-demonstrated** if visible in repository source, or **hypothesis** until tested with users.

| Priority | Problem, evidence grade | User-facing harm or risk | v0.8 design resolution / acceptance |
|---|---|---|---|
| P0 | **Recording vs science collection ambiguity** — owner-reported and source-demonstrated (`science-journey.js`, `mission-operations.js`, toolbar `renderCollectionBanner`) | User can believe recording means collecting science; armed/paused/stale messages can be misunderstood | Two persistent statuses; one action for next confirmed phase; explicit Arm/Start; show source and count caveats; independent controller revisions. End-to-end simulator check |
| P0 | **Toolbar and dashboard state mismatch / stale commands** — owner-reported, existing repair documented; source-demonstrated compatibility checks (`AeroScience.js`) | False appearance of data collection or wrong mission plan | Shared read-only state semantics; no new client controller; disable on stale and mismatch; show build/last successful reply. Native SDK acceptance |
| P0 | **Scientific provenance hidden in complexity** — owner-reported and documented v0.7 scientific-interface contract | Historical satellite scenes, modeled readings and simulator observations can look equivalent; bad terrain data may seem valid | Every result/source card labels kind, acquisition date, data QA; critical invalid state visible; exact evidence behind Details; chart only original compatible points |
| P0 | **Deletion/upload/live sharing risk during simplification** — source-demonstrated (`source-deletion.js`, `submission-builder.js`, organization flows) | One-click convenience may delete unrecoverable originals or share without informed consent | Preserve preflight preview/revision, actual deletion, active-use blockers; explicit recipient/contents/retention/approve; opt-in live separate from submission. Negative tests |
| P1 | **Navigation and duplicate task entry** — source-demonstrated (`index.html`, `task-workspaces.js`, `settings-navigation.js`); owner reports duplicate Download Activity / External Data Manager | Users must understand application architecture and multiple labels to find an action | Task-first Home/Missions/Current Flight/Results/conditional Organizations; one Scientific Library utility; deep-link compatibility; navigation parity test |
| P1 | **Overloaded first screen and too much prose/checkboxes** — owner-reported, source-demonstrated many information panels | New users must read instructions before first step; multiple competing CTAs | Guided experiment cards; task-first next action; details on demand; compact real-time states, not verbose technical labels. Independent novice task test |
| P1 | **Instrument setup and collection intervals** — owner-reported; toolbox source-demonstrates interval edit with confirm/cancel and source-specific states | Scientific collection seems complicated; users may configure wrong cadence | Beginner template defaults; short interval presets with explicit confirmed save; actual instrument-specific cadence in advanced settings, no changed engine semantics |
| P1 | **Airport waypoint selection** — owner-reported and specified in v0.7 validator checks | User cannot easily create routes starting at known airports | One searchable Add airport waypoint flow with clear selected facility, coordinates, and Save Waypoint; preserve unresolved search/error states |
| P1 | **Four toolbar views plus technical detail** — source-demonstrated HTML/JS | Pilot has to navigate a miniature dashboard while flying; panel overflows with long translations | Three contextual Flight/Science/Cards areas; Map as clear reachable Flight subview; connection/collection banner persists; native resizable sizes |
| P1 | **No unified first-run Home** — source-demonstrated `#my-research` fallback and mixed experiment/control cards | Start of product is not tailored to simulator connected/active/archive only states | Contextual Home first action; live mission resume or Explore; offline and empty states. Never override explicit pairing/critical errors |
| P2 | **Scientific results feel like navigation rather than an answer** — owner-reported; six existing `science-workspace` pages | Users may not discover useful terrain/altitude plots or understand what was measured | Overview / Explore / Evidence progressive levels, with data-driven default graph and corresponding table; preserve six deep routes |
| P2 | **QA terminology and technical grade labels** — owner-reported and source-demonstrated | `Scientific quality needs review` can sound like failure or validity guarantee, and raw instrument diagnostics dominate | Critical / important / detail hierarchy; precise nonjudgmental descriptions; explain missing, provisional, invalid separately |
| P2 | **Download availability and reuse clarity** — owner-reported and source-demonstrated | Missing sources look like failed missions, duplicate downloads unnecessary | Library Sources/Downloads/Storage with coverage/reuse availability, clear queue steps, no arbitrary cap introduced by UI |
| P2 | **Localization is not yet a holistic architecture** — source-demonstrated hardcoded English in `app.js`, `index.html`, toolbar and native forms; `toLocaleString("en-US")` in both app and toolbar | Mixed languages, overflow, mistranslated scientific/permission messages and missing Windows strings | Catalog-first P02, backend/native adapters, translation context and source identity, pseudo-localization, strict human review of critical text |
| P2 | **Wide and narrow layouts diverge** — hypothesis, source has responsive shell at 1100px but toolbar runtime differs | Toolbars can clip controls; 390px dashboard and high zoom can lose data/action | Consistent spacing and visual design with separate native compact rules; keyboard, zoom, 5-language overflow screenshots |
| P3 | **Specialist diagnostics are surfaced near normal actions** — source-demonstrated | Less relevant information consumes first viewport and makes status harder to scan | Move identities, hashes, source/debug metadata to labeled Advanced Details; critical warning not hidden |
| P3 | **Organization onboarding feels administrative** — hypothesis; source-demonstrated connection, trust/approval and multiple permissions | Potential new contributor finds assignment management intimidating | Role-aware Organizations landing, one next action, human-readable permissions; keep native trust and per-scope authorization |

## Actual evidence from code and prior validation

1. `src/AeroScience.Engine/wwwroot/index.html` displays seven sidebar entries (My Research, Flight Planner, Flight Operations, Results & History, Scientific Library, Settings, Help) and embeds multiple legacy views. The markup has no standalone Home route.
2. `src/AeroScience.Engine/wwwroot/app.js` aliases deep links, renders telemetry/recording, handles session authorization and flight history; some numbers use a hardcoded `"en-US"` locale despite a general locale formatting path elsewhere.
3. `src/AeroScience.Engine/wwwroot/task-workspaces.js` reuses existing control/history/library DOM by reparenting; removal or replacement could break live control callbacks.
4. `src/AeroScience.Engine/wwwroot/science-workspace.js` has six subpages: Map, Compare, Research Analysis, Results & Exports, Replay Flight and Evidence Timeline, with mission/instrument query parameters.
5. `msfs-toolbar/PackageSources/html_ui/InGamePanels/AeroScience/AeroScience.html` contains Mission/Payload/Map/Research tabs, a persistent science-collection banner, payload interval controls, plan pagination, observation inputs, and expandable build diagnostics. `AeroScience.js` uses original `AeroScience.Command.v1` / `Reply.v1` bridge and session-bound science revisions. Real native compatibility must be checked after any structure change.
6. `src/AeroScience.Engine/wwwroot/source-deletion.js` already obtains a server deletion preview and then executes a separately confirmed removal. Improve clarity without assuming the command is safe without a preview or claiming a hidden cache.
7. `src/AeroScience.Engine/wwwroot/submission-builder.js` distinguishes saved draft from authorized submission and queries exact eligible evidence/recipients; redesign must preserve this.
8. `docs/v0.7.0-scientific-interface.md` distinguishes critical, important and informational detail. The P28 corrections already targeted ease of use and may be carried forward rather than rewritten.
9. `docs/v0.7.0-validator-feedback-owner-checks.md` lays out five checks for toolbar handshake, airport waypoint, guided profile, sensor details and results. Documentation does not itself prove every test passed.
10. `docs/roadmap/v0.7.0-development-tracker.md` documents current unresolved native build/packaging and private validation. v0.8 work must not substitute for its acceptance.

## Severity by stage

| Core journey | Most serious novice friction | Critical truth/safety assertion |
|---|---|---|
| Install/first launch | No consistent welcome/connection next step | Distinguish simulator, local companion and optional cloud connections |
| Choose experiment | Template question, instrumentation and plan form intermingled | Recommend only supported template/source combinations |
| Prepare | Readiness, sources, aircraft/route configuration scattered | Never auto-download without permission; unavailable inputs remain unavailable |
| Fly/collect | Recording vs collection status; toolbar overload | Confirmed controller phase and retained actual science originals; fail-closed stale |
| Finish/review | Mission archive vs science views scattered | Original flight timeline, exact science quality and pending processing preserved |
| Participate in organization | Connections/reviews/admin flows can dominate | Explicit upload and live sharing approval; no automatic organization access |
| Delete/manage storage | Source and collected data are distinct | Permanent delete is actually permanent, shows blockers and cannot recover fake outputs |

## Research tasks for P02/P03

- **Five first-time participants minimum per design iteration if feasible:** guided profile on Cessna-equivalent; start recording vs science; finish and identify actual number of saved observations. Capture independently completed steps, hesitations, incorrect expectations, screen-reader/keyboard needs.
- **Expert testers:** create test card with revision and multiple attempts; locate calibration, advanced download and exact evidence; compare two scientifically compatible flights; use custom location.
- **In-flight testers:** open toolbar, begin/arm science, pause/resume, switch Cards, move/resize, use Map, observe connection loss; ensure no dangerous or accidental click.
- **Locale tests:** long German control labels; Spanish and Portuguese accented names; French decimal/date formatting; all consent and deletion dialogs; mixed region/aviation units.
- **Adversarial tests:** stale telemetry, no retained science, deleted library scene, failed download, invalid geometry, permission expired, offline queued submission, source missing, wrong native toolbar build.

## P01 exit and limitations

**Complete for the static P01 planning deliverable:** a traceable initial map and prioritized audit grounded in existing source; no runtime code altered. **Not yet proven:** exhaustive generated controls; browser pixel/keyboard evidence; physical native SDK; representative users; localization quality; scientific regression. These become P02 verification requirements, not excuses to claim UI acceptance.

Do not run Full CI for a docs-only audit. No screenshot, SDK/Windows installer, sensor validation or automated test result is asserted in this document.
