# v0.8.0 P01 usability audit

Status: **source-based audit, not a usability study or runtime acceptance**. Baseline: develop/v0.8.0 at **c62088ab32ad0b76ece710e3a7a26530b327c398**, November 10, 2026. Findings describe that snapshot; later v0.7 beta fixes require a separate carry-forward comparison. No installer, release, owner archive or simulator installation was touched.

The [screen inventory](v0.8.0-screen-inventory.md) assigns preservation IDs D01–D27, L01–L12, S01–S09, O01–O12 and N01–N08. The [handoff](v0.8.0-p01-handoff.md) turns these into staged design and P02 acceptance work. Task scope follows the committed [P01 brief](v0.8.0-p01-codex-brief.md) and its required specifications. This checkpoint adds documentation only.

## What the evidence supports

There is already a useful novice guide, explicit recording control, separate science controller, five grouped workspaces, accessible drawer/focus handling, bounded scientific review, and careful data/permission workflows. The problem is how much knowledge a beginner must carry across those surfaces. A new sidebar alone would not resolve it.

The approved target is **Auto dashboard theme**, optional override, **guided** first-time flow, **balanced** density, and initial **en-US/es-ES/fr-FR/de-DE/pt-BR**. These are decisions, not pending preferences. Native readability remains independent of desktop appearance. Translations, theme implementation, device/font validation and novice task measurements are not complete.

Evidence classes used below:

- **Owner/validator report:** an existing checked-in record of reported behavior. This is historical evidence, not a new reproduction.
- **Confirmed source:** directly observed routing, handlers or presentation structure at the baseline.
- **Inferred design risk:** a plausible task failure from that structure. It needs user/device testing before being called an observed failure.
- **Preservation constraint:** a working safety property or prior correction that redesign must retain.

## Task and status design requirements

The journey to test is **Explore Mission → Prepare → explicit Start Recording → explicit Start/Arm Science → Fly → Finish → Understand Actual Results**. P01 has not measured independent completion, task duration, satisfaction or the implementation plan's eventual 90% target.

A beginner must be able to answer: which plan/aircraft is selected; whether the companion/simulator is current; whether recording is active; whether science is armed, collecting, paused or held; what source each measurement represents; what was retained; and what action can safely happen next. Scientific analysis may require deeper screens, but critical missing/invalid evidence cannot be hidden there.

Use the existing critical/important/information hierarchy. A critical message states **problem, consequence, action**; important operational context stays next to the affected control; method/raw identity remains available in named details. Pending loading, zero retained data, unavailable archive and failed write are different states. New controls cannot infer a successful transition from their own click or timeout.

“Science paused” must not become “flight recording paused.” The current app has simulator paused/invalid telemetry, science-session pause, independent preparation/download pauses, card attempt boundaries and ended recordings. Preserve each meaning and expose no unsupported recording pause.

For source language, use short category names with truthful explanations: simulator-reported at aircraft, historical dataset acquired on its source date, modeled/derived, pilot-entered, unavailable/unsupported, synthetic test fixture. Do not call DEM/DSM LiDAR, historical surface temperature live aircraft air temperature, an aircraft footprint valid-pixel coverage, or a modeled experimental response a physical sensor.

## Planned participant tasks

This is a future study plan, with no P01 participants or measured outcomes. Seek at least five varied first-time participants per useful iteration when practical: choose a supported simple profile, prepare it, distinguish Start Recording from Start Science, finish, and identify what was actually retained. Record independent success, time, incorrect expectations, hesitation and keyboard/access needs. Include expert tasks for card revision/multiple attempts, advanced calibration/imports, exact evidence and compatible comparison; installed in-flight tasks include drag/resize, Map/Cards, interval confirmation and connection loss. Fluent reviewers cover the five approved locales and destructive/consent terminology. These measurements belong to feature/acceptance checkpoints, not a docs-only gate.

## Review method, validation and remaining evidence

Source review covered actual route dispatch, generated DOM, relevant action handlers, read APIs and authority checks; the inventory groups specialized forms/workers by capability. It is not a line-by-line audit of every provider, database migration, server recovery algorithm or existing automated test.

P01 uses static checks for the three documentation paths, internal links, row uniqueness/coverage, required route/native handler coverage, bibliography existence and a three-added-file commit diff. Exact check calls/results are recorded in the handoff. No Full CI, dotnet, Playwright, native build, scientific calculation, protected NASA original-file, owner-data, Windows/MSFS/iPad/Quest or usability study was run. Existing validation documents retain their original source-specific test receipts; their totals are not reused as P01 passes.

Uncertainties requiring later evidence: native runtime/glyph/layout behavior with the final package; actual first-time task completion; accessibility with a screen reader/physical devices; translated safety terminology; representative real-source results; and route behavior after future v0.7 carry-forward. These do not block P02 tokens/catalog/routing groundwork.
