# AeroScience v0.7.0 — Extremely Simple Organization Server Hosting

**Status: design proposal in response to the owner's explicit beginner-install requirement (2026-10-23).** The owner approved v0.7.0 research scope and explicitly wants organization server hosting to be understandable to a nontechnical beginner ("so stupidly easy that a 10 year old could figure it out"). **No server or deployment button is yet implemented, released, validated or provider-approved.** Provider choice and exact UI flow remain proposals, not frozen owner decisions.

## Non-negotiable hosting UX outcome

An ordinary organization administrator must **not need to know Docker, Postgres, SSH, Linux shell commands, IP addresses, DNS records, TLS certificates, cloud load balancers, or migrations** to launch, invite pilots, operate a campaign or check server health on the supported beginner path. The administrator still needs a hosting provider account, payment authorization, and secure owner-account recovery; do not pretend those steps can be eliminated without running an AeroScience-hosted central service.

**Target flow (not a claim of present functionality):**
1. On the AeroScience website/release README choose **Create an Organization Server**.
2. Choose a supported beginner deployment provider; login, review actual recurring provider charges and confirm. Pre-configured resource bundle and application image are provisioned without terminal steps. The default provider-generated HTTPS hostname works immediately; a purchased custom domain is *optional*.
3. Open the newly deployed organization setup page and redeem a secure, short-lived, single-use admin bootstrap credential; choose organization name/logo, create/admin-authenticate account and configure MFA/passkey/recovery. Do not expose an unauthenticated "first visitor becomes admin" URL.
4. Dashboard confirms health; administrator creates a campaign and **copies an expiring invitation link** to send to pilots by Discord/email/other communication. Sending invitations **must not require configuring SMTP**; integrated email delivery can remain optional.
5. Pilot opens organization invite/connection link (or organization URL in AeroScience), reviews identity and permissions, signs in using secure system-browser authentication, and organization appears within **My Research** without replacing local personal/offline mission data.

**Release acceptance:** Pilot/admin with no prior server experience executes install + bootstrap + invite + pilot connection + first campaign + evidence submission/review from a fresh supported provider account using only an official on-screen step-by-step guide. No hidden setup files or shells. A novice should understand error recovery; do not score based on a developer-assisted demonstration. Publish screenshots/video only from an actually working deployment.

## Architectural diagram in words

**Pilot PC / MSFS + AeroScience:** existing local recorder, plans, science source library, evaluated attempts and analysis remain local. Optional org connector downloads permissioned definitions, manages claim/revisions and only transmits explicitly selected pilot-consented evidence or previously approved offline-queue items.

**Internet HTTPS, user-approved delivery:** small manifest + bounded authorized supporting evidence. No continuous simulator telemetry, remote control, automatic source mirror or global AeroScience account.

**Organization's own server:** one standalone cross-platform `AeroScience.OrganizationServer` ASP.NET Core app + browser portal using platform-neutral AeroScience contracts/evidence evaluator; PostgreSQL database for org members/roles/campaigns/claims/submissions/reviews/receipts; protected attachment storage for explicitly received submission bytes; secure, authenticated role-filtered UI. **One organization per deployed instance for v0.7**, unless owner later approves more complexity after testing.

**Not supported:** deploying the Windows SimConnect engine as public server or exposing desktop pairing tokens, reimplementing mission/science archive, forcing users to open a global AeroScience account, uploading source files automatically.

## One backend, two deployment experiences

| | Beginner: managed deploy | Advanced: your own server |
|---|---|---|
| User sees | **Deploy AeroScience Server** → hosting login/billing approval → organization setup | **Install AeroScience Server** guide/wizard on chosen Linux VPS |
| Candidate mechanism | Official pinned-release provider blueprint, initially evaluate **Render Deploy to Render** | Official versioned Docker Compose app + PostgreSQL + Caddy reverse proxy with retained database/attachment/certificate volumes |
| Public website | Provider assigned HTTPS host by default; custom domain optional | Domain owned by organization; guided domain/DNS/TLS checks. Caddy renews certificates when DNS/routes configured |
| Who operates infrastructure? | Hosting provider, in organization's own account | Organization/VPS operator |
| Data | Managed PostgreSQL plus suitably persistent **protected** attachment storage (plan depends on provider). No ephemeral filesystem for authoritative attachment data | PostgreSQL and protected attachment volumes with measured sizing and explicit backup/restore |
| Costs | Provider charges for running services, database, storage/bandwidth; show estimated bill before deploying | VPS plus domain/storage/offsite backup costs; may be cheaper but higher operator responsibility |
| Updates | Use tested pinned release + controlled guided updates/backup/preflight; no unsafe surprise migrations | Same pinned app release, guided update with health check, backup, migration/rollback controls |
| Status | **Deployment concept, not available yet** | **Deployment concept, not available yet** |

**Candidate provider proof, not an endorsement or a final selection:**
- Render's official Deploy to Render button uses `render.yaml`/Blueprint to create interconnected application/database resources after user approval. Render provides a `.onrender.com` hostname and automatic HTTPS. Use **paid durable database and persistent protected attachment storage** for production; unmanaged ephemeral service filesystem is not persistent. Disable automatic redeployment from arbitrary source commits; pin stable tagged releases and make upgrades reversible/tested. Render docs: https://render.com/docs/deploy-to-render, https://render.com/docs/infrastructure-as-code, https://render.com/docs/deploys, https://render.com/docs/tls. Note Render persistent disks' single-instance/zero-downtime limitations: https://render.com/docs/disks.
- DigitalOcean has a Deploy to DigitalOcean App Platform button, but as checked October 2026 its button currently supports only its **Dev Database**, not automatic managed production database integration. Do not deceptively offer that button as zero-work production hosting without solving production database provisioning. See https://docs.digitalocean.com/products/app-platform/how-to/add-deploy-do-button/.
- DigitalOcean Marketplace Droplet 1-Click App images can preconfigure software, but publishing AeroScience to Marketplace requires vendor process/review and a working supported image, not just making up a button. https://docs.digitalocean.com/products/marketplace/ .
- Caddy can provision publicly trusted HTTPS after domain DNS and ports are correctly set: https://caddyserver.com/docs/automatic-https. Docker Compose has officially supported single-server production deployment patterns: https://docs.docker.com/compose/how-tos/production/.
- Optional advanced Cloudflare Tunnel can avoid opening inbound ports for some on-prem/home environments, but adds a Cloudflare account + domain + tunneling security/operational dependencies, so should **not** be a hidden beginner prerequisite. https://developers.cloudflare.com/tunnel/concepts/.

## Security that needs to be automatic, not explained away

- HTTPS only, validated organization/server identity, hardened reverse proxy, secure defaults, access logging/CSRF/rate limits, quotas for submission sizes and denial-of-service abuse; internal database is not exposed.
- Reuse vetted authentication primitives. Admin MFA/recovery required, account invites expire, optional auth via standard system browser for pilots. OAuth authorization code + PKCE needs a real supported OIDC provider/protocol, not the existing local desktop pairing token.
- One organization per deployed instance for first production release; do not promise shared multi-tenant isolation until independently tested. Server-side role checks on **every** object, including submitted attached scientific products.
- Admin bootstrap cannot be claimed by an arbitrary first internet visitor. Use controlled one-time secret, required admin ownership verification and explicit revoke-on-use.
- On-screen Server Health page: reachable/domain/TLS, app version/client compatibility, PostgreSQL/attachment availability, backups last verified, storage/bandwidth usage, active users/queued reviews, update availability and support diagnostics. Provide actionable error labels.
- Self-hosted organizations can shut down, export their own data, remove members and manage their domain without asking AeroScience staff. Maintenance/update risks displayed plainly.

## Data deletion and consent boundary — owner accepted

If the pilot has approved an offline evidence queue but **deletes the underlying scientific data before the package is sent**, **hold or cancel the upload**; do not retain a hidden local backup, cache/archive or silently send a substitute. Prefer a queued immutable approval **manifest/references**, verify exact original source hashes at transmission and require renewed approval if referenced content, selection, org or permissions changed. If an export is ever independently staged, it must be an explicit user-visible retained copy with separate deletion semantics; **not currently approved**. Keep source-science deletion exact.

**After an authorized upload succeeds**, that organization has a separate explicitly disclosed copy of only the selected evidence. Its server data retention, removal requests, scheduled backups and restore suppression must be explained and enforced; local deletion by itself cannot guarantee remote deletion or imply a secret local backup. No organization learns which other organizations may also receive a separate separately approved subset from the same flight.

## Installer/update/backup acceptance checklist

- No-code/terminal-free clean setup using the officially supported beginner path, fresh provider account and actual published release artifact; provider bills/cost shown before confirmation.
- Automatic/generated HTTPS hostname works with no custom domain; custom domain optional. TLS and org identity correctly verified.
- One-time bootstrap owner protected from takeover; invite and pilot system-browser auth work; MFA and lost-device recovery tested.
- Fresh campaign can be created, claimed, flown offline and selected evidence submitted with correct server receipt and reviewer approval; no full-flight upload by default.
- Durable PostgreSQL and authorized attachments **survive restart/redeploy**; no ephemeral production data.
- Failed/partial deploy has understandable retry/resume; no orphaned public database, unsafe default account or unknown costs.
- Pinned release image, schema migration/backup gate, tested restoration and recoverable failed updates; automatic infrastructure/security patches where provider-managed, software update policy disclosed and manageable.
- Simple visible backup check + guided restored instance with real test data; include actual off-server backup storage and documented schedule/retention.
- Security: roles, redirects, server identity, per-org access, invalid credentials, rate/size limits, safe logs, no hidden background uploads and no live telemetry.
- Offline queue evidence deleted before send → held/cancelled with precise warning and no hidden copy. Received authorized server copies follow documented server-specific retention, not retroactive local resurrection.
- Benchmark small and mid-size organizations before publishing hosting specifications or billing estimates; never promise "free forever" or imaginary minimum hardware.

## Confirmed owner decision — beginner deployment default (2026-10-23)

**Owner approved: Official one-click managed cloud deployment is the primary beginner installation path for AeroScience v0.7.0.** An officially supported Docker Compose/Linux VPS deployment remains an advanced option. **This selects the UX/deployment strategy, not a hosting vendor, account/billing model or implemented button.** Evaluate providers for durable application+PostgreSQL+attachment storage, automatic HTTPS/domain, secure setup, migrations, updates, measured cost, production backups and *tested restore* before choosing one. No one-click marketing claim is acceptable unless a novice can actually complete an end-to-end production-grade deployment without command line steps.

**One-click means start deployment with one clearly labeled button**, followed by necessary hosting-account sign-in, explicit price/payment authorization and secure first-admin/organization setup. It does **not** mean secretly creating paid resources, bypassing MFA/security, omitting backups, or claiming deployment is instantaneous. Share an expiring invite link; pilot connects from desktop. Same backend/features for beginner and advanced hosting. Prefer one officially supported beginner provider at launch rather than a provider marketplace with uneven reliability.

## Confirmed owner economics: no developer-paid infrastructure and inexpensive organization hosting (2026-10-23)

**Owner requirement:** Providing AeroScience and its one-click organization-server installer must **not incur a recurring hosting charge to the AeroScience developer solely because others deploy their own servers**. Each independent organization deploys under **its own** provider account, explicitly authorizes its own bill, and pays the hosting provider directly. No centralized AeroScience-run mandatory account, relay, managed database, telemetry gateway, data warehouse or paid domain that would impose cross-org variable expense on the developer. Do not imply personal developer testing/optional demo hosting, development tooling or code-signing are guaranteed cost-free; those costs are separate choices and should be identified if unavoidable.

**Cheap for organizations is an acceptance requirement, not a marketing guarantee.** Aim for an **initial small-organization operator cost roughly $5–15/month where practical**, ideally under $10, and investigate why a production small group would exceed $20/month; **these figures are provisional design targets, not guaranteed quotations or an owner-specified strict maximum**. Include database, durable evidence storage, approved backup/restore, bandwidth, TLS/domain, and recurring provider fees in the calculator. Show total expected provider charges **before** final deployment and warn about usage-driven overage and retention changes. Prefer simple visible storage quotas, cost alerts and spending safeguards with protected scientific evidence; never promise impossible hard caps or delete research automatically to reduce costs.

### Updated vendor evaluation based on official public pricing checked 2026-10-23

- **Railway — potential cost leader, to prototype:** Official Hobby minimum **$5/month**, includes $5 usage credit, with total bill increasing when CPU, memory, bandwidth and storage use exceed that amount. One-click multi-service templates can provision app+Postgres. Free tier has only $1 recurring resource credit and is not a substitute for confirmed durable, resilient production hosting. Official https://railway.com/pricing , https://docs.railway.com/pricing/plans , https://docs.railway.com/templates/deploy and https://docs.railway.com/templates/publish-and-share . **Do not claim an actual AeroScience production server costs $5** before benchmarking separate web/database memory and backup/storage.
- **Render — ease-of-use contender, possibly more expensive:** Official starter web compute **$7/month** (512 MB) with Postgres compute/storage, optional persistent evidence disk and backup cost additional. Render free Postgres expires after **30 days** and lacks backup: **categorically unsuitable as persistent production research database**. Official https://render.com/pricing , https://render.com/docs/free , https://render.com/docs/deploy-to-render and https://render.com/docs/disks . Compare all-in hosted app+paid Postgres+durable evidence retention before adopting as beginner default.
- **DigitalOcean App Platform — alternative:** Official web container begins **$5/month**, production-grade database adds cost. The easy deploy button presently does not automatically provision a managed production DB by default, so a genuinely one-click production setup needs a custom solution. Official https://www.digitalocean.com/pricing/app-platform , https://docs.digitalocean.com/products/app-platform/how-to/add-deploy-do-button/ .
- **Advanced VPS** may offer lower predictable service+DB cost but requires more responsibility and cannot replace the officially supported no-terminal beginner one-click path.

**Design implication:** Do **not** lock Render merely because it was recommended earlier. Evaluate Railway versus Render and other practical providers on all-in low-volume cost, persistence, real backup+restore, secure admin bootstrap, provider-based one-click deployment, predictable spending, update/rollback and no-cost-to-developer distribution. Choose the provider after working benchmarks/tests, not starter sticker price alone.

**Product boundaries stay unchanged:** One shared ASP.NET Core organization server backend across provider deployments and advanced VPS; personal research offline without login; scientific source deletion prevents any not-yet-sent queued upload that referenced it, with no hidden local file copies; submitted server copies governed by disclosed remote retention policy.

## Owner proposal — present all three managed deployment providers (2026-10-23)

**Owner asked whether AeroScience should present all three investigated choices—Railway, Render and DigitalOcean—in the beginner deployment experience.** The proposed answer is **yes: one neutral provider chooser, followed by one consistent AeroScience setup/onboarding workflow**. This is a newly favored UX direction, subject to proving each provider's truly production-ready one-click path; it is not a claim that all three are currently deployable, price-verified or already officially supported.

**Provider selection UX:** A simple three-card "Choose your hosting provider" page, each card giving estimated *total* monthly cost for a representative small organization (app + database + evidence storage + backups + network), billing responsibility, standout tradeoffs, and precisely one accurate action: "Deploy with Railway / Render / DigitalOcean" only if full provision works; otherwise "Guided setup" with honest visible extra steps or "Not yet available." No claim a basic web-instance sticker price is an AeroScience all-in production quote. Admin may choose any provider; no dependency on a central AeroScience paid relay/account. Existing official VPS/Docker Compose method lives separately under **Advanced Self-Hosting**, not a confusing fourth beginner card.

**One software architecture:** one versioned ASP.NET Core organization application, shared PostgreSQL/schema/auth/security/reviewer contracts, backend-scoped evidence/attachment APIs, server manifest, admin portal and pilot connector. Three *deployment adapters/configurations*, not three backend forks. All providers generate HTTPS addresses by default, manage secrets/admin bootstrapping securely, store authorized submitted evidence durably and pass install/update/restore tests. Each provider must show actual billing/usage warnings and straightforward exit/export.

**Current technical asymmetry (official docs checked 2026-10-23):**
- Railway has multi-service deploy templates and easy PostgreSQL provisioning with its own persistent service volumes; Hobby starts at $5/month with $5 resource credit, usage can rise beyond. Do not treat database backups/restore as automatic unless configured and tested. https://docs.railway.com/templates/deploy , https://docs.railway.com/databases/postgresql , https://docs.railway.com/pricing/plans
- Render Blueprint/Deploy to Render can declare web/database infrastructure; filesystems are ephemeral unless externalized or explicitly persisted. A free PostgreSQL instance expires after 30 days; choose verified paid durable DB+attachment retention. https://render.com/docs/blueprint-spec , https://render.com/docs/your-first-deploy , https://render.com/docs/deploys
- DigitalOcean's stock "Deploy to DO" button currently provisions only **Dev Databases**, not production Managed Databases; App Platform itself can attach a managed production database and use Spaces object storage. To honestly advertise **one-click production** in the chooser, **design/verify an extra provider-specific orchestration path** that safely provisions managed Postgres + durable attachments with explicit billing approval; otherwise call it **guided deployment** or mark not yet verified. https://docs.digitalocean.com/products/app-platform/how-to/add-deploy-do-button/ , https://docs.digitalocean.com/products/app-platform/how-to/manage-databases/ , https://docs.digitalocean.com/products/app-platform/how-to/store-data/

**Release gating:** Each advertised "one-click" provider must pass a clean end-to-end novice deployment with database/attachment persistence, backups and tested restore, secure admin first claim, invite/pilot login, compatible client, transfer limits, upgrades/rollbacks, cost transparency and independent account billing. Publish comparative measured costs and support tier/limitations; don't overcommit to maintaining three platforms if one fails the gate. Previous owner economic rule remains: developer isn't billed for third-party organizations, organizations pay own provider, and personal/offline work remains free of hosting.

**Local science deletion rule remains:** Deleting scientific source evidence while an offline approved submission has not yet been transmitted holds/cancels the upload with no secret retained copy or substitution. Provider choice does not modify this consent/retention boundary.

## Cloudflare zero-dollar hosting feasibility question (2026-10-23)

**User explicitly raised Cloudflare's free hosting options after considering Railway/Render/DigitalOcean.** Investigate Cloudflare as a **fourth candidate/free-tier research track**, but **do not** label it an implemented, approved or one-click-compatible production server until a real feasibility test verifies backend parity, user auth, evidence review, backups/restore, deletion, cost and UX.

**Verified official Cloudflare offerings current October 2026:**
- Workers Free: 100,000 requests/day and **10 milliseconds CPU per invocation**; daily quota failure can stop a research API; https://developers.cloudflare.com/workers/platform/limits/ .
- D1 Free: 5 million rows read/day, 100,000 rows written/day, **5 GB total storage across DBs but only 500 MB per individual database**, 7-day point-in-time restoration; SQLite-compatible SQL semantics, **not PostgreSQL**; https://developers.cloudflare.com/d1/platform/pricing/ and https://developers.cloudflare.com/d1/platform/limits/ .
- R2 Standard: **10 GB-month** included storage, 1 million Class A and 10 million Class B operations/month, free egress; activating R2 requires accepting an R2 subscription/checkout and usage above included quota is billable; https://developers.cloudflare.com/r2/pricing/ and https://developers.cloudflare.com/r2/get-started/ .
- Pages static requests are free/unlimited; dynamic Functions consume Workers allowance; Cloudflare currently recommends Workers for new full-stack applications; https://developers.cloudflare.com/pages/functions/pricing/ and https://developers.cloudflare.com/pages/ .
- Cloudflare Tunnel can publish an **already operating server** without a paid Access plan; Tunnel is a secure exposure/connectivity product, **not** a free compute/database host. Permanent hostname/domain, always-on local VPS/hardware, administration and backups are still the organization's responsibility; https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/ .
- Cloudflare Containers can run ordinary application images including .NET/Linux server processes, but **Containers is Workers Paid only** with **$5/month minimum** and metered compute/storage, while PostgreSQL/durable attachment storage still must be solved; https://developers.cloudflare.com/containers/ and https://developers.cloudflare.com/containers/platform/pricing/ .
- Workers primary first-class languages are JS/TS, Python and Rust, plus WebAssembly; existing ASP.NET Core/.NET 10 application plus PostgreSQL **cannot be assumed to run unchanged** in free Workers + D1. https://developers.cloudflare.com/workers/languages/ .

**Reuse-first architectural consequence:** A complete $0 Cloudflare-native organization backend could require **significant rework of the planned C# ASP.NET Core/Postgres service into a Workers+D1 model** and migration/portability/reliability audits. Do **not** create a second independently maintained server codebase just to advertise a free host or break the owner’s backend-reuse-first requirement. First assess whether a **single service/domain contract and shared evaluator implementation** can run safely in all target environments without duplicating science/evidence policy and without imposing hidden operating costs. A cheaper immediate integration could use R2 free allowance for *authorized uploaded organization evidence* with the existing .NET server hosted elsewhere, or free Tunnel for advanced own-machine servers; both are add-ons, not automatically free complete managed hosting.

**Four-choice display policy if feasible:** Cloudflare `Potentially $0 — compatibility/production suitability under research`, Railway, Render, DigitalOcean; only enable a one-click cloud card once actually production-validated. Require real cost/security/backup/load testing under representative campaigns, evidence size, concurrent pilots and membership/review events. Do not promise a $0 24/7 full production service until proven. Pilot deletion before offline queued upload still cancels/holds original selected data with no hidden retained local copy.
