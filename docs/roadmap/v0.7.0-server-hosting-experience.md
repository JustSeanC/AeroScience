## Non-negotiable hosting UX outcome

An ordinary organization administrator must **not need to know Docker, Postgres, SSH, Linux shell commands, IP addresses, DNS records, TLS certificates, cloud load balancers, or migrations** to launch, invite pilots, operate a campaign or check server health on the supported beginner path. The administrator still needs a hosting provider account, payment authorization, and secure owner-account recovery; do not pretend those steps can be eliminated without running an AeroScience-hosted central service.

**Target flow (not a claim of present functionality):**
1. On the AeroScience website/release README choose **Create an Organization Server**.
2. Choose a supported beginner deployment provider; login, review actual recurring provider charges and confirm. Pre-configured resource bundle and application image are provisioned without terminal steps. The default provider-generated HTTPS hostname works immediately; a purchased custom domain is *optional*.
3. Open the newly deployed organization setup page and redeem a secure, short-lived, single-use admin bootstrap credential; choose organization name/logo, create/admin-authenticate account and configure MFA/passkey/recovery. Do not expose an unauthenticated "first visitor becomes admin" URL.
4. Dashboard confirms health; administrator creates a campaign and **copies an expiring invitation link** to send to pilots by Discord/email/other communication. Sending invitations **must not require configuring SMTP**; integrated email delivery can remain optional.
5. Pilot opens organization invite/connection link (or organization URL in AeroScience), reviews identity and permissions, signs in using secure system-browser authentication, and organization appears within **My Research** without replacing local personal/offline mission data.

**Release acceptance:** Pilot/admin with no prior server experience executes install + bootstrap + invite + pilot connection + first campaign + evidence submission/review from a fresh supported provider account using only an official on-screen step-by-step guide. No hidden setup files or shells. A novice should understand error recovery; do not score based on a developer-assisted demonstration. Publish screenshots/video only from an actually working deployment.

## Architectural diagram in words

**Pilot PC / MSFS + AeroScience:** existing local recorder, plans, science source library, evaluated attempts and analysis remain local. Optional org connector downloads permissioned definitions, manages claim/revisions and only transmits explicitly selected pilot-consented evidence or previously approved offline-queue items.

**Internet HTTPS, user-approved delivery:** small manifest + bounded authorized supporting evidence. No continuous simulator telemetry, remote control, automatic source mirror or global AeroScience account.

**Organization's own server:** one standalone cross-platform `AeroScience.OrganizationServer` ASP.NET Core app + browser portal using platform-neutral AeroScience contracts/evidence evaluator; PostgreSQL database for org members/roles/campaigns/claims/submissions/reviews/receipts; protected attachment storage for explicitly received submission bytes; secure, authenticated role-filtered UI. **One organization per deployed instance for v0.7**, unless owner later approves more complexity after testing.

**Not supported:** deploying the Windows SimConnect engine as public server or exposing desktop pairing tokens, reimplementing mission/science archive, forcing users to open a global AeroScience account, uploading source files automatically.

## Security that needs to be automatic, not explained away

- HTTPS only, validated organization/server identity, hardened reverse proxy, secure defaults, access logging/CSRF/rate limits, quotas for submission sizes and denial-of-service abuse; internal database is not exposed.
- Reuse vetted authentication primitives. Admin MFA/recovery required, account invites expire, optional auth via standard system browser for pilots. OAuth authorization code + PKCE needs a real supported OIDC provider/protocol, not the existing local desktop pairing token.
- One organization per deployed instance for first production release; do not promise shared multi-tenant isolation until independently tested. Server-side role checks on **every** object, including submitted attached scientific products.
- Admin bootstrap cannot be claimed by an arbitrary first internet visitor. Use controlled one-time secret, required admin ownership verification and explicit revoke-on-use.
- On-screen Server Health page: reachable/domain/TLS, app version/client compatibility, PostgreSQL/attachment availability, backups last verified, storage/bandwidth usage, active users/queued reviews, update availability and support diagnostics. Provide actionable error labels.
- Self-hosted organizations can shut down, export their own data, remove members and manage their domain without asking AeroScience staff. Maintenance/update risks displayed plainly.

## Data deletion and consent boundary — owner accepted

If the pilot has approved an offline evidence queue but **deletes the underlying scientific data before the package is sent**, **hold or cancel the upload**; do not retain a hidden local backup, cache/archive or silently send a substitute. Prefer a queued immutable approval **manifest/references**, verify exact original source hashes at transmission and require renewed approval if referenced content, selection, org or permissions changed. If an export is ever independently staged, it must be an explicit user-visible retained copy with separate deletion semantics; **not currently approved**. Keep source-science deletion exact.

**After an authorized upload succeeds**, that organization has a separate explicitly disclosed copy of only the selected evidence. Its server data retention, removal requests, scheduled backups and restore suppression must be explained and enforced; local deletion by itself cannot guarantee remote deletion or imply a secret local backup. No organization learns which other organizations may also receive a separate separately approved subset from the same flight.

## Installer/update/backup acceptance checklist

- No-code/terminal-free clean setup using the officially supported beginner path, fresh provider account and actual published release artifact; provider bills/cost shown before confirmation.
- Automatic/generated HTTPS hostname works with no custom domain; custom domain optional. TLS and org identity correctly verified.
- One-time bootstrap owner protected from takeover; invite and pilot system-browser auth work; MFA and lost-device recovery tested.
- Fresh campaign can be created, claimed, flown offline and selected evidence submitted with correct server receipt and reviewer approval; no full-flight upload by default.
- Durable PostgreSQL and authorized attachments **survive restart/redeploy**; no ephemeral production data.
- Failed/partial deploy has understandable retry/resume; no orphaned public database, unsafe default account or unknown costs.
- Pinned release image, schema migration/backup gate, tested restoration and recoverable failed updates; automatic infrastructure/security patches where provider-managed, software update policy disclosed and manageable.
- Simple visible backup check + guided restored instance with real test data; include actual off-server backup storage and documented schedule/retention.
- Security: roles, redirects, server identity, per-org access, invalid credentials, rate/size limits, safe logs, no hidden background uploads and no live telemetry.
- Offline queue evidence deleted before send → held/cancelled with precise warning and no hidden copy. Received authorized server copies follow documented server-specific retention, not retroactive local resurrection.
- Benchmark small and mid-size organizations before publishing hosting specifications or billing estimates; never promise "free forever" or imaginary minimum hardware.
