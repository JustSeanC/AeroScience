# AeroScience v0.7.0 — Human-Friendly Validation Instructions

**Confirmed owner requirement, 2026-10-25. Research/planning document only.**

## Non-negotiable audience rule

**Every manual validation instruction that an AeroScience owner, pilot, friend, or ordinary tester is asked to follow must be clear enough for a 10-year-old to understand.** Prior update instructions had grown too long, technical, intense and intimidating. Reverse that trend. Testers should not need to understand source code, API routes, command-line syntax, test frameworks, database internals or developer terminology just to establish that a feature works.

This changes **presentation and ownership of validation**, not the rigor of engineering verification.

## Two distinct layers

**Layer A — automatic/developer validation (Codex/CI owns it):**
- Code compilation, unit/integration/regression/security checks, authentication/tenant isolation, scientific evidence identity and deletion integrity, migrations, server backups/restores, full log inspection and protocol behavior.
- Codex performs the technical checks, reports pass/fail concisely, and fixes problems without sending a wall of low-level procedures to the user.
- Clearly separate what automation proves from what requires a real MSFS build, human UI assessment, hosting-provider account or hardware.
- Never describe unperformed manual tests as validated or automated test success as user acceptance.

**Layer B — user/manual acceptance (actual human tester owns it):**
- Short, guided, task-based checklist using actual visible button/menu/page names and clear observable outcomes.
- Default **one printable page or less for a focused feature**, ideally **3–8 short tests** with 2–5 simple actions each. Use a second page only when demonstrably necessary for a full release checklist.
- Start with the one-line goal and a simple prerequisite, e.g., `Open AeroScience and MSFS 2024`. Avoid formal introductions, long background, repeated caveats, appendices and exhaustive edge-case lists.
- Format: **Do this → You should see this → Pass / Problem** (checkboxes acceptable). Include a place for one screenshot or plain-language comment on failure.
- Show exactly how to reach the feature, which button to click, what should appear, and how to reset/finish. State an obvious example if setup data is necessary. No unexplained jargon or generic `verify`/`validate`/`confirm expected response`.
- For multi-step user journeys, check **create/plan → fly/collect → review results → submit/approve** with ordinary simulated examples, rather than testing internal plumbing.
- Do not require running a terminal, modifying JSON/SQL, editing configuration, finding Git branches, reading console logs, using external debugging tools or copying long commands **unless absolutely unavoidable**; any advanced diagnostic belongs in a separate clearly labeled optional developer appendix, not the default instructions.
- If an expected result does not appear, instruct the tester to **stop that test**, note what happened and share a screenshot or simple message in Discord. Do not burden them with debugging.
- Accessibility: plain reading level, short sentences, generous white space, scannable checkboxes, controls as actually labeled, no double negatives.

## Example of desired wording

### Test — Collect science during a flight

- [ ] **1.** Open AeroScience and start a mission in MSFS.
- [ ] **2.** Open the AeroScience toolbar. Choose **Start Science** (or the actual current control label).
- [ ] **3.** Fly for about a minute, then end the mission.
- [ ] **4.** Open **Science Results** and select the flight.
- [ ] **Pass:** You can see recorded science data for that flight.
- [ ] **Problem:** Write what you saw instead, or send a screenshot.

**The labels above are illustrative, not a claim that the exact buttons or workflow are currently implemented.** Before publishing any real checklist, check the actual build and use the visible controls verbatim.

## Release and scope checklist for Codex

- Every v0.7.0 implementation/acceptance prompt must explicitly request **both** (a) automated technical test evidence and (b) a **separately authored simple human tester guide** if manual validation is required.
- The human guide must contain only things the user can really do on their PC or in the supported hosted setup; if user action is **not** required, say **"No manual test needed — automated checks completed"** instead of inventing a test.
- For any real-PC-only action, give one simple exact navigation path and the visible expected behavior. Handle build/installer instructions in a separate concise prerequisite; do not mix build systems into feature testing.
- Codex should first do all safe checks it can on its own and identify genuine manual test dependencies, not offload development QA onto pilots.
- Human guidance must be no longer than necessary, avoid multiple alternate procedures, and remain amendable if the build's labels/flows change.
- The code security, data integrity, science quality and multi-organization privacy gates stay just as strict behind the scenes.

**UX rubric gate:** A test fails its usability acceptance when an uncoached tester cannot understand the test's instructions or locate the requested action, even if the automated implementation tests passed. Distinguish unclear instructions from actual app UX confusion; address both.
