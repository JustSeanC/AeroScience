## Cross-cutting correctness and privacy

- **Never conflate** a local `ScientificReview` or postflight downlink status with an organizational human review, claim acceptance or program-completion waiver.
- A pilot's scientific source and flight remain on their computer by default. Organization submission is a separately authorized **selected subset**; sending to a second organization requires a second independent evidence preview and approval.
- An incomplete scientific result never becomes a pass merely because the campaign permits submitting partial evidence or a manager records a completion waiver. Store original attempt outcome alongside organizational review/waiver status.
- Pilot may deactivate incompatible card monitoring and activate another card during a single flight; keep science session and flight recording untouched. Only mutually incompatible *concurrently active* card requirements cause blocking.
- A recorded attempt's original claim time and frozen card revision determine eligibility, even if a released claim slot is later taken by another pilot. Accepted **unique contributors**, not concurrent slots or attempted runs, fulfill participant quotas.
- Backend-first reuse is a constraint; UI layout, design system, navigation and touch/VR interactions may be extensively refactored when measured against the established UX rubric. Existing tools and endpoints named here are not automatic acceptance proof.

### Important release and trust boundaries

- The existing scientific download job queue has approval, persistence and resume logic **for downloads**. It is not an upload subsystem, and cannot be assumed to meet organizational confidentiality/recipient consent/review requirements; treat it as an implementation *pattern* to reuse, not an API to retrofit indiscriminately.
- A newly authorized outbound package must bind original evidence identities, content hash, card revision, organization/account destination, consent timestamp and idempotency key. If an approved package mutates, require a new consent; independently cancel before remote receipt is confirmed. Receiving a byte stream is not accepting scientific results.
- A submitted incomplete scientific result can be reviewed when allowed by campaign policy, but does not become `PASS` because submission was permitted. Reviewers can grant separately labeled program exceptions according to existing owner decision.
- Do not create a parallel science-recording/replay pipeline, scientific acquisition manager, scientific-data store, or scientific map/computation backend. UI overhaul is within v0.7.0 scope when it improves the rubric.
- Risk of hidden stale artifact: if the user permanently deletes science/source files before a queued packet is transmitted, no undisclosed staged data copy should survive. Hold/review/cancel based on actual availability unless the user later expressly chooses a disclosed independent export/retention policy; that retention decision is **not approved**.

## Hosting economics checkpoint — 2026-10-23 owner requirement

**Owner:** Developer must not be responsible for recurring server bills incurred by unrelated organizations; beginner hosting must remain very cheap for organizations, with one-click setup confirmed. Each organization deploys the same optional server under and bills its own hosting account, and local solo research has no hosting requirement. Architecture must not depend on a central AeroScience-operated payment/auth/data service.

**Provider benchmark gate:** Compare all-in real deployment using Railway ($5 Hobby minimum, further charges by actual usage), Render ($7 base web service plus paid Postgres, disk/attachments and backup; free Postgres 30-day expiration is unsafe for production), and DigitalOcean ($5 base app but more complex production database one-click provisioning). **Design aspiration** $5–15/month for small, low-activity group, not a proven invoice or a strict promised cap; explain any scenario >$20. Use measured app/DB CPU+RAM, sample scientific submitted evidence byte budget, outbound bandwidth, backup+restore, HTTPS, updates and security. Ensure hosting provider account owns charges and exposed cost warnings/quota options before deployment.

**No misleading cheap mode:** Do not default to expiring DB, insecure accounts, backup-free operational data, ephemeral uploaded evidence, unbounded meter billing or stealth cached/deleted evidence. A selected candidate must prove real one-click app+durable DB+evidence storage plus documented inexpensive backup strategy before release.

## Cloudflare free-tier feasibility added to provider comparison (2026-10-23)

Cloudflare has substantive free tiers: Workers (100k requests/day, 10ms CPU/request), D1 (5GB account storage but 500MB **per database** on free, daily row-operation quotas), R2 (10 GB-month Standard storage and bounded operations), free static Pages hosting and a Tunnel product to expose **already-hosted** apps. **Cloudflare Containers for an ordinary ASP.NET Core server image are paid-tier**, starting with $5/month Workers Paid plus metered usage. D1 is not PostgreSQL; vanilla ASP.NET Core + PostgreSQL cannot simply deploy unchanged to Cloudflare's free Workers runtime.

**Engineering gate:** Investigate viable single-codebase Cloudflare execution or optional Cloudflare R2 storage/advanced Tunnel only; avoid producing a separate Workers/D1 org backend that duplicates core evaluation, authorization, schema logic and requires 2 independent codebases. Treat `Cloudflare $0` as a **promising research hypothesis** for very small organizations, not a validated deployed alternative. Evaluate full review workload, durable evidence, backup/restore, security, claims and optional tenant isolation, service limits and true one-click cost before promoting to a fourth beginner card. Official links: https://developers.cloudflare.com/workers/platform/limits/ ; https://developers.cloudflare.com/d1/platform/limits/ ; https://developers.cloudflare.com/r2/pricing/ ; https://developers.cloudflare.com/containers/platform/pricing/ .

Retain user goal: $0 developer-hosting charges, cheapest safely usable per-organization hosting, exact local-deletion/queued-evidence behavior.
