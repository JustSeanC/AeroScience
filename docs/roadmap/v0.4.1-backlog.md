# AeroScience v0.4.1 — UI/UX and Mission Data Readiness Backlog

Status: **Proposed backlog, not implemented or accepted.**
Created following early v0.4.0 visual QA feedback on 2026-10-19. These are post-v0.4.0 improvements, not retrospective claims that the v0.4.0 Windows/MSFS acceptance gate has passed. Do not create GitHub issues from this document without an explicit request.

## Goals

Make the installed app feel like a cohesive research workstation. Prioritize simple navigation, understandable mission-scoped scientific preparation, and usable source-library organization. Preserve scientific provenance, retention, operating modes, and all v0.4.0 mission/data integrity guarantees.

## 0.4.1-UX-01 — One integrated Help & Support center
**Priority:** P1 | **Type:** Navigation, documentation, support

**Observed:** Main sidebar currently exposes both `Help & Support` (which routes to Settings > Support) and `Help & Guides` (which opens a raw `.md` file in a browser tab). The two destinations are redundant and the raw Markdown display looks broken.

**Desired experience**
- Replace the two sidebar entries with **one** `Help & Support` destination that opens a dedicated, styled in-app Help workspace rather than merely navigating to Settings.
- The page should have clear subsections: Getting Started, Mission Planning, Scientific Data & Downloads, Instruments, Replay/Coverage/Imagery, Troubleshooting, and Contact & Community.
- Render existing bundled Markdown guides as readable HTML with consistent AeroScience typography, tables, links, code blocks, anchored headings and internal navigation. Do not display source Markdown markup as the ordinary help experience.
- Maintain offline documentation, readable on desktop and physical tablet-sized browser layouts; guide links must not require public internet except explicitly external references.
- Show actionable `Join our Discord` (https://discord.gg/mpYyazCqvJ), existing GitHub reporting, and `Collect Feedback / Logs`; open external sites explicitly in the browser without requiring Discord membership.
- Contextual help links from Settings/Planner/Science should deep-link into the relevant Help subsection. Any existing Settings support item should link to the same destination, not create another disconnected support screen.
- Main navigation, browser back/forward, keyboard focus, scrolling, screen reader labels and responsive width must work.

**Acceptance**
- Only one Help entry in primary navigation.
- Opening it reveals a real Help page, not Settings or a raw `.md` tab.
- Internal guide links/headings work offline; external links behave appropriately.
- Discord, GitHub and feedback/log collection remain reachable.
- Tested on desktop/browser and physical iPad before calling device acceptance complete.

## 0.4.1-UX-02 — Mission-scoped Queued / Downloading / Ready visibility
**Priority:** P1 | **Type:** Science preparation, mission planning, live status

**Observed:** The system has queue and job status fields, and Download Activity already distinguishes active/queued/completed items, but the mission/preflight experience lacks an easy, unified explanation of which required geographic datasets are **Queued**, **Downloading**, and **Ready**. Global download counts should not be mistaken for one mission's preparation progress.

**Desired experience**
- Show an obvious **Scientific Data Preparation** panel when a saved mission plan is selected or its preflight is started. Also provide a compact linked view from Science Collection/Mission Control during a flight.
- Display a mission-specific summary: `Ready X · Downloading Y · Queued Z · Unavailable N`, with an accurate total denominator of required **instrument × geographic region** work. Explain the unit of counting to users and avoid double-counting duplicates or reused sources.
- Render each stage with text, a clear icon/visual treatment, count, and individual rows grouped by scientific instrument and geographic region. Never rely on color alone.
- Show geographic coverage on the plan map using the same truthful states; selecting a row highlights the relevant source/region, and selecting a map region reveals its status.
- **Queued**: requested preparation work exists but no network transfer is currently underway. Differentiate `waiting for turn`, `offline`, `paused`, `allowance exhausted`, `no permission`, or `waiting for source discovery` with a reason/substatus where applicable. Merely saving a plan is **not** equivalent to queuing downloads.
- **Downloading**: an actual network transfer is in progress; display verified bytes transferred, measured throughput/known total only if available, and a real bounded progress percentage only when the denominator is established. If discovery, metadata lookup, processing, hash verification or import is occurring without active transfer, show a separate `Finding source` / `Validating` / `Preparing` substatus, not a false ongoing download.
- **Ready**: at least the required compatible source assets are present locally, verified, indexed and usable for the relevant requested area/source type. Retained-data reuse may transition directly to Ready without downloading; mark `Reused locally` rather than indicating a fresh transfer. Ready is **not** guaranteed cloud-free or full valid-pixel survey coverage: show separate `partial coverage` / QA cautions and the actual coverage evidence.
- Include explicit `Partially ready`, `Unavailable/Failed`, `Paused`, and `Cancelled` outcome/reason states as needed, never forcing them misleadingly into one of the three positive stages.
- Keep counts and readiness **per mission plan and enabled instrument**; permit a global cross-mission Download Activity drill-down, but label it as global. Show plan name, session state, completed/remaining regions, relevant storage/network limits, last update time and a clear link to diagnostics.
- Provide useful Pause / Resume / Cancel / Retry actions only where supported; do not accidentally initiate extra downloads by merely opening a status view. Honor separate preflight and in-flight transfer budgets, flight priority, cancellation and storage constraints.
- Refresh while visible and maintain stable rows/sorting, so status changes do not cause excessive layout jumping. Handle disconnections, app restart, changed plan, reused original data and unavailable external drives without false Ready status.
- Keep detailed provider errors and technical diagnostics expandable for advanced users rather than overwhelming ordinary pilots.
- Prefer reusing existing `ScientificDataReadiness`, `ScientificPlanReadiness`, queue/session states and `Download Activity` endpoints. Ensure back-end truth is authoritative rather than guessing status on the client.

**Acceptance**
- Saving a new mission plan without pressing Prepare does **not** show work falsely queued.
- After explicit preparation starts, a real item moves Queued -> Downloading -> Validating/Preparing -> Ready **as supported by observed events**; transition sequence may omit stages for retained source reuse.
- During a network pause/outage, queued and active states show truthful reasons, and no phantom progress or premature Ready.
- Per-mission total and per-instrument/region counts reconcile with underlying actual work and do not show unrelated global jobs.
- Completion includes source QA/coverage caveats; partial/no-data areas never appear 100% scientifically ready.
- Settings, Mission Planner, Science Collection, desktop, tablet and relevant toolbar summaries agree on state.
- Automated lifecycle tests plus real Windows/preflight and MSFS installed acceptance checks.

## 0.4.1-UX-03 — Scientific Source Library grouping and repeated-item clarity
**Priority:** P2 | **Type:** Data-management usability

**Observed:** Science > Settings exposes many nearly identical `USGS 3DEP bare-earth numeric elevation subset` entries with repeated `View Dataset Details`, `View Coverage` and `Exclude from active selection` controls. These may represent genuinely distinct geographical subsets and must not be deleted or silently deduplicated.

**Desired experience**
- Present source inventory as **Provider > Product / Scientific Collection > Geographic Regions**. Default to a concise collection-level summary: unique providers/collections, number of regions, retained size, actual extent and available capabilities.
- Collapse individual regions by default; support search/filter by provider, product, location, instrument type, status and optionally source date.
- Show a combined collection coverage map without merging incompatible numeric values, scenes, dates, calibration or vertical references.
- Clearly differentiate same-label but distinct source regions from exact same-source or identical-hash duplication. Investigate actual reuse behavior and report wasted network/storage only if substantiated.
- Preserve individual source IDs, exclusions, QA, original scene/date, stored files, hashes, provenance and source-compatibility policy.
- Collection-level actions must have transparent scope. Keep per-region inspect/manage available behind expansion.
- Consider summarizing larger library counts in the Science Library before exposing management actions.

**Acceptance**
- A multi-region USGS 3DEP library initially shows one concise provider/collection overview instead of a wall of visually identical entries.
- Expansion, pagination, per-region controls and source detail still work.
- Grouped presentation changes never delete originals or change scientific source selection without a user action.
- Distinct date/datum/calibration products are preserved and clearly differentiated.

## UI/UX quality bar applying to all three items

- Use consistent headings, spacing, typography, status words and navigation placement.
- Be legible and navigable at typical desktop widths, browser zoom and physical iPad Safari resolutions.
- Keep ordinary actions obvious; move technical explanations into progressive disclosure, not into anonymous repeated warnings.
- Provide clear no-data, loading, error and completed states; keyboard and screen-reader accessibility.
- Do not move complex geographic map/raster management into the small native in-sim toolbar.
- Include visual regression tests and real-device usability verification; browser emulation alone is insufficient.
- Preserve existing data safety, scientific provenance, original-source immutability and release acceptance gating.

## Notes / scope

- Backlog only. No v0.4.1 implementation, test results or release publication are implied.
- v0.4.0 real Windows/MSFS acceptance remains independently pending.
- This document intentionally avoids creating GitHub issues for future-release ideas.

## 0.4.1-UX-04 — Estimated scientific data preparation time
**Priority:** P1 | **Type:** Download activity and mission readiness

**Request:** While scientific source preparation runs, show an estimated remaining transfer time beside Queued / Downloading / Ready in the mission-level status and detailed Download Activity.

**Desired experience**
- For an active, size-known transfer with defensible observed throughput, show e.g. `Approximately 2–4 minutes remaining` and bytes downloaded/total plus a progress bar.
- Estimate using actual bytes received, reliable total remaining source bytes where known, and a smoothed recent observed transfer rate; guard against startup transients, stalls and extreme variation. Prefer a useful range/approximately rather than a misleading second-by-second countdown.
- For the full **selected mission preparation**, show a total ETA only where the work denominator is known and remaining tasks can be reasonably modeled; account for concurrency, retained-source reuse, queue wait and processing/verification only when measurable. Distinguish `Estimated download time` from `Additional processing/verification time not yet estimated`.
- Before provider discovery or when transfer size/rate is unknown, say `Calculating estimate` or `Time remaining unknown`. Never invent a file size, source response time or completion time.
- Queued work may display `Waiting for download slot` or `Waiting for allowance`; do **not** promise an ETA if no slot is available, bandwidth policy blocks it, network is offline or download permission is missing.
- Pause/cancel/retry/offline/allowance exhaustion/reuse must reset or suspend the estimate appropriately. If no downloading is occurring, do not show a false live rate.
- Make the presentation stable and readable at desktop/iPad widths, do not rely on color, provide a timestamp/label such as `Estimate based on recent transfer speed`, and avoid rapid ETA oscillation.
- Reuse source/job state fields `downloadedBytes`, `estimatedDownloadBytes`, `seconds`, observed transfer bytes, actual `Stage`, queue status and session budgets. Do not confuse application-level total historical network usage with this job's remaining bytes.
- Keep a compact mission-level estimate with a `View Download Activity` drill-down; advanced diagnostics remain accessible without filling the primary planning panel with verbose transfer metadata.

**Acceptance**
- A known-size bounded transfer reports a defensible, changing estimate after adequate rate samples, using independently testable throughput math.
- Unknown-size work shows Unknown/Calculating rather than 0% or an invented duration.
- Stalled, paused, rate-changing, failed and reused-local workflows produce truthful ETA changes, no negative time and no premature Ready.
- Mission-level ETA corresponds only to the selected mission work and agrees with its Queued/Downloading/Ready counters.
- Browser tests cover ETA math/state transitions and desktop/tablet layouts; installed Windows behavior requires actual testing.

## QA investigation — Saved dashboard plan not visible in in-sim app
**Priority:** P0 if reproduced on the same v0.4.0 installed build | **Type:** Integration and navigation defect, **not automatically deferred to v0.4.1**

**Report:** User has a mission planned in the desktop dashboard but does not see it in the app. Need establish that the plan was explicitly saved (rather than remaining an unsaved draft), identify the affected surface/build, and attempt `Mission > Saved Mission Plan > Refresh Plans` on the in-sim toolbar.

**Current intended behavior:** The toolbar's saved-plan selector uses `map-plans` requests through the CommBus, `RouteMapService.Plans(offset)` and the shared mission store; an explicitly saved plan should be selectable independently of an active recording. Selecting it does not itself start a mission. The toolbar paginates ten plans at a time and also has `Next plans`.

**Investigation/acceptance**
- On the same installed app/engine instance, save a named plan in the dashboard, confirm it appears in the saved-plan list and `GET /api/plans`, then click the toolbar `Refresh Plans` and verify the same name/ID appears.
- Check whether the toolbar is showing `Unplanned Mission`, a stale older plan, no selector, a communication error, or a different profile/data folder; record exact screen/build/version and any CommBus status.
- Test plan selector response paging (especially more than ten plans), refresh after a new plan save, toolbar reopen, MSFS restart and companion restart. Verify saved plan versus started recording distinctions are clearly explained in both UI surfaces.
- Selecting the plan must show an accurate route preview and instrument summary, and `Start Recording` must use the correct immutable plan snapshot without a hidden fallback to unplanned mode.
- If a saved plan cannot be retrieved by the installed toolbar on v0.4.0, treat it as a **v0.4.0 release-acceptance blocker** rather than relegating a broken core mission-selection workflow to v0.4.1.
- Only after confirming v0.4.0 behavior may cosmetic auto-refresh/plan discoverability improvements be scheduled for v0.4.1.


## 0.4.1-UX-05 — Mission Control: select saved research plans before recording
**Priority:** P1 | **Type:** Mission selection, unified workflow, route preview

**Observed on 2026-10-19:** Mission Planner has named saved plans and a `Record this plan` action, but the dashboard's Mission Control idle form only offers operating mode, a free-text mission name and `Start mission`. Current `app.js` `start-form` submits `name`/`mode` without `planId`. The live Mission Control map reads the active mission's plan snapshot after recording begins and has no independent selected-plan preview in standby. A user can thus have a prepared mission and scientific downloads in progress while seeing only the aircraft on the main Mission Control map.

**Desired experience**
- Add a prominent `Choose Mission` control to Mission Control: saved missions, searchable where practical, plus an explicit `Unplanned Flight` option. List actual plan names, template, science mode, aircraft preference (if any), survey area, route and selected payload summary. Treat saved plans as ready to **select**, not necessarily scientifically data-ready.
- Selecting a saved plan before recording displays its saved waypoints, polygons, generated patterns and current instrument configuration on the existing Mission Control map. Mark these as `Planned` distinct from actual `Recorded` track. Allow preview/fit/zoom before flight. The route must not require starting collection or recording.
- Show the **selected mission's** Queued/Downloading/Ready preparation summary, download ETA where defensible, local source coverage and a link to its detailed Download Activity; account for actively preparing plans and truly unprepared plans. Do not automatically start remote downloads by selection alone.
- For a saved plan, the Start Mission action must submit the plan ID and preserve the plan's immutable saved snapshot, mode, equipment and route, without silently reverting to an unplanned flight. For an unplanned flight, preserve the existing name/mode workflow.
- Provide `Edit in Mission Planner`, `View on Map`, `Prepare Science Data` (explicit opt-in), `Refresh Missions` when needed and `Start Mission`. Keep status text clear: `Plan selected` is not `Recording`, and scientific source preparation is not flight recording.
- The sidebar Mission Planner and Mission Control use the same underlying saved-plan records; changes reflect after save and refresh, including reopening after app restarts. No duplicate mission records from selection.
- Provide a compact preview/synchronized selected plan in the native MSFS toolbar where feasible, but do not add heavy map-processing UX or require it to change the aircraft FMS/autopilot.

**Acceptance**
- Save a named research plan in Planner; without starting recording, choose it in Mission Control and see its exact stored route and survey boundary on the map.
- Preflight preparation for that plan can be seen while on standby, and data can become Ready without an active flight.
- Starting the chosen plan records under the correct ID with the correct immutable plan snapshot and science mode; it never unexpectedly creates an unplanned mission.
- Unplanned flights remain available, and switching among saved plans changes preview/readiness without losing saved definitions.
- Map works during preflight and continues with planned-vs-actual overlays after recording starts; handles no route, missing drives, changing plans and incomplete preparations honestly.
- Confirm real Windows/desktop + physical iPad layout, keyboard navigation, and connection to native toolbar where supported.

## 0.4.1-PERF-01 — Increase science download concurrency safely
**Priority:** P1 | **Type:** Settings, throughput, resource management

**Observed:** Scientific access UI `scientific-access.js` restricts `Concurrent preparations` to max 2, `AutomaticScientificData.Validate` refuses values above 2, and the job scheduler uses this hard cap. Large multi-instrument missions can accumulate many queued preparation areas while the user waits.

**Desired experience**
- Raise the **proposed ordinary default to 4** concurrent preparations and offer user-configurable **up to 8**, subject to actual provider, bandwidth and storage validation. Assess whether an `Automatic (recommended)` mode or resource-adaptive limit is preferable to a fixed default; never assert that 8 always increases total throughput.
- Change **UI validation, backend preference validation, scheduler semantics and documentation consistently**. Existing saved preferences (including 1 or 2) must be preserved unless the user deliberately changes them; avoid silently overriding customization.
- Apply reasonable *per-provider/per-host* fairness, limits, retry/backoff, service 429/503 handling, bounded transport/reservations and CPU/disk memory caps. Prevent eight simultaneous science tasks from exhausting RAM, disk or network transfer budgets.
- Preserve flight-priority preparation, preflight/in-flight budgets, existing privacy/consent, source identity reuse and idempotent storage writes. Failed/paused jobs must not strand transfer reservations.
- The UI should make configurable `Concurrent downloads` distinct from `total queued regions`, `source provider request rate`, `data ready`, and `overall preparation ETA`. Warn that higher concurrency can saturate the connection or trigger provider rate limits.
- Instrument download queues should not starve each other solely because one provider is slow; queued/waiting reasons remain visible.

**Acceptance**
- Validate real multi-provider preparation at 1, 2, 4 and (if safe) 8 active slots, with timings and memory/disk/CPU/network measurements; compare completed valid work, not just concurrently open requests.
- Verify server rate limiting/error handling, retry/backoff, cancellation, interruption, restart, duplicate reuse, preemption and accurate budget ledgers under concurrency.
- Verify no loss/corruption of source data and no interruptions to active flight recording.
- Choose a defensible shipped default based on the measurements (4 proposed), document exceptions and cap; permit a lower limit on constrained connections.

## v0.4.0 acceptance: Native toolbar does not load saved missions / no engine response
**Priority:** P0 pending reproduction | **Type:** Installed runtime/CommBus blocker, not merely a 0.4.1 enhancement

**Evidence reported:** In the screenshot of the native toolbar, the header says `WAITING FOR ENGINE` and status says `Loading simulator communication service...`; the selector displays only `Unplanned Mission`. User reports `Refresh Plans` and the dropdown do not work, while the separate desktop dashboard shows valid MSFS aircraft telemetry. This implies the engine may be operating but the *toolbar-to-engine CommBus handshake* is not established, or the native package/version may be out of sync. It does not prove which cause is responsible; pending an actual live diagnostic.

**Expected implementation:** Toolbar `AeroScience.js` loads the SDK CommBus and requests `state` and `map-plans`; `ToolbarCommandHandler` forwards the latter to `RouteMapService.Plans`. These requests should be served from the same mission store as the desktop's `GET /api/plans`.

**Acceptance / investigation**
- First check if the toolbar ever transitions from `WAITING FOR ENGINE` to a connected state. Verify the correct native toolbar package was installed, exact source/build/SDK/runtime match, SimConnect/CommBus loading, engine-running state, replies and any reported timeouts/errors. Do not infer that a working browser dashboard proves the toolbar has a working CommBus channel.
- Compare `GET /api/plans` from the installed dashboard to the toolbar response. Distinguish an unsaved draft, an empty plan store, stale toolbar pagination, and a communication failure.
- With a fresh named saved plan, verify the toolbar `Refresh Plans` populates the exact ID/name, selected-route preview and instrument/mode summary, and that recording starts with the intended saved plan.
- Confirm recovery after toolbar close/reopen, simulator load, companion restart, and SDK package repair without destroying mission data.
- Do not mark v0.4.0 native-toolbar/Missions A–E acceptance passed while this current reported behavior persists.
