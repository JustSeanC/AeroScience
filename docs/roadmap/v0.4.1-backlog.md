# AeroScience v0.4.1 — UI/UX and Mission Data Readiness Backlog

Status: **Proposed backlog, not implemented or accepted.**
Created following early v0.4.0 visual QA feedback on 2026-10-19. These are post-v0.4.0 improvements, not retrospective claims that the v0.4.0 Windows/MSFS acceptance gate has passed. Do not create GitHub issues from this document without an explicit request.

## Goals

Make the installed app feel like a cohesive research workstation. Prioritize simple navigation, understandable mission-scoped scientific preparation, and usable source-library organization. Preserve scientific provenance, retention, operating modes, and all v0.4.0 mission/data integrity guarantees.

## 0.4.1-UX-01 — One integrated Help & Support center
**Priority:** P1 | **Type:** Navigation, documentation, support

**Observed:** Main sidebar currently exposes both `Help & Support` (which routes to Settings > Support) and `Help & Guides` (which opens a raw `.md` file in a browser tab). The two destinations are redundant and the raw Markdown display looks broken.

**Desired experience**
- Replace the two sidebar entries with **one** `Help & Support` destination that opens a dedicated, styled in-app Help workspace rather than merely navigating to Settings.
- The page should have clear subsections: Getting Started, Mission Planning, Scientific Data & Downloads, Instruments, Replay/Coverage/Imagery, Troubleshooting, and Contact & Community.
- Render existing bundled Markdown guides as readable HTML with consistent AeroScience typography, tables, links, code blocks, anchored headings and internal navigation. Do not display source Markdown markup as the ordinary help experience.
- Maintain offline documentation, readable on desktop and physical tablet-sized browser layouts; guide links must not require public internet except explicitly external references.
- Show actionable `Join our Discord` (https://discord.gg/mpYyazCqvJ), existing GitHub reporting, and `Collect Feedback / Logs`; open external sites explicitly in the browser without requiring Discord membership.
- Contextual help links from Settings/Planner/Science should deep-link into the relevant Help subsection. Any existing Settings support item should link to the same destination, not create another disconnected support screen.
- Main navigation, browser back/forward, keyboard focus, scrolling, screen reader labels and responsive width must work.

**Acceptance**
- Only one Help entry in primary navigation.
- Opening it reveals a real Help page, not Settings or a raw `.md` tab.
- Internal guide links/headings work offline; external links behave appropriately.
- Discord, GitHub and feedback/log collection remain reachable.
- Tested on desktop/browser and physical iPad before calling device acceptance complete.

## 0.4.1-UX-02 — Mission-scoped Queued / Downloading / Ready visibility
**Priority:** P1 | **Type:** Science preparation, mission planning, live status

**Observed:** The system has queue and job status fields, and Download Activity already distinguishes active/queued/completed items, but the mission/preflight experience lacks an easy, unified explanation of which required geographic datasets are **Queued**, **Downloading**, and **Ready**. Global download counts should not be mistaken for one mission's preparation progress.

**Desired experience**
- Show an obvious **Scientific Data Preparation** panel when a saved mission plan is selected or its preflight is started. Also provide a compact linked view from Science Collection/Mission Control during a flight.
- Display one concise **per-instrument summary**, e.g. `Thermal — Downloading; remaining regions pending`, plus a compact overall mission preparation status. Advanced counts must use the accurate total denominator of unique required **instrument × geographic region** work, not raw provider download attempts. Explain counted units and avoid double-counting retries or reused sources.
- Render each instrument with one status card/row showing name, effective sensor profile, current phase, ready/awaiting/blocked regional counts if useful and ETA if defensible. Never rely on color alone. Individual source tiles, retry attempts and geographic regions must be **collapsed under Advanced / View Regions**, not shown repeatedly by default.
- Show geographic coverage on the plan map using the same truthful states; selecting a row highlights the relevant source/region, and selecting a map region reveals its status.
- **Queued**: requested preparation work exists but no network transfer is currently underway. Differentiate `waiting for turn`, `offline`, `paused`, `allowance exhausted`, `no permission`, or `waiting for source discovery` with a reason/substatus where applicable. Merely saving a plan is **not** equivalent to queuing downloads.
- **Downloading**: an actual network transfer is in progress; display verified bytes transferred, measured throughput/known total only if available, and a real bounded progress percentage only when the denominator is established. If discovery, metadata lookup, processing, hash verification or import is occurring without active transfer, show a separate `Finding source` / `Validating` / `Preparing` substatus, not a false ongoing download.
- **Ready**: at least the required compatible source assets are present locally, verified, indexed and usable for the relevant requested area/source type. Retained-data reuse may transition directly to Ready without downloading; mark `Reused locally` rather than indicating a fresh transfer. Ready is **not** guaranteed cloud-free or full valid-pixel survey coverage: show separate `partial coverage` / QA cautions and the actual coverage evidence.
- Include explicit `Partially ready`, `Unavailable/Failed`, `Paused`, and `Cancelled` outcome/reason states as needed, never forcing them misleadingly into one of the three positive stages. A mixed-ready instrument must not be labeled wholly Ready.
- Keep counts and readiness **per mission plan and enabled instrument**; permit a global cross-mission Download Activity drill-down, but label it as global. Show plan name, session state, completed/remaining regions, relevant storage/network limits, last update time and a clear link to diagnostics.
- Provide useful Pause / Resume / Cancel / Retry actions only where supported; do not accidentally initiate extra downloads by merely opening a status view. Honor separate preflight and in-flight transfer budgets, flight priority, cancellation and storage constraints.
- Refresh while visible and maintain stable rows/sorting, so status changes do not cause excessive layout jumping. Handle disconnections, app restart, changed plan, reused original data and unavailable external drives without false Ready status.
- Keep detailed provider errors and technical diagnostics expandable for advanced users rather than overwhelming ordinary pilots.
- Prefer reusing existing `ScientificDataReadiness`, `ScientificPlanReadiness`, queue/session states and `Download Activity` endpoints. Ensure back-end truth is authoritative rather than guessing status on the client.

**Acceptance**
- Saving a new mission plan without pressing Prepare does **not** show work falsely queued.
- After explicit preparation starts, a real item moves Queued -> Downloading -> Validating/Preparing -> Ready **as supported by observed events**; transition sequence may omit stages for retained source reuse.
- During a network pause/outage, queued and active states show truthful reasons, and no phantom progress or premature Ready.
- Per-mission total and per-instrument/region counts reconcile with underlying actual work and do not show unrelated global jobs.
- Completion includes source QA/coverage caveats; partial/no-data areas never appear 100% scientifically ready.
- Settings, Mission Planner, Science Collection, desktop, tablet and relevant toolbar summaries agree on state.
- Automated lifecycle tests plus real Windows/preflight and MSFS installed acceptance checks.

## 0.4.1-UX-04 — Estimated scientific data preparation time
**Priority:** P1 | **Type:** Download activity and mission readiness

**Request:** While scientific source preparation runs, show an estimated remaining transfer time beside Queued / Downloading / Ready in the mission-level status and detailed Download Activity.

**Desired experience**
- For an active, size-known transfer with defensible observed throughput, show e.g. `Approximately 2–4 minutes remaining` and bytes downloaded/total plus a progress bar.
- Estimate using actual bytes received, reliable total remaining source bytes where known, and a smoothed recent observed transfer rate; guard against startup transients, stalls and extreme variation. Prefer a useful range/approximately rather than a misleading second-by-second countdown.
- For the full **selected mission preparation**, show a total ETA only where the work denominator is known and remaining tasks can be reasonably modeled; account for concurrency, retained-source reuse, queue wait and processing/verification only when measurable. Distinguish `Estimated download time` from `Additional processing/verification time not yet estimated`.
- Before provider discovery or when transfer size/rate is unknown, say `Calculating estimate` or `Time remaining unknown`. Never invent a file size, source response time or completion time.
- Queued work may display `Waiting for download slot` or `Waiting for allowance`; do **not** promise an ETA if no slot is available, bandwidth policy blocks it, network is offline or download permission is missing.
- Pause/cancel/retry/offline/allowance exhaustion/reuse must reset or suspend the estimate appropriately. If no downloading is occurring, do not show a false live rate.
- Make the presentation stable and readable at desktop/iPad widths, do not rely on color, provide a timestamp/label such as `Estimate based on recent transfer speed`, and avoid rapid ETA oscillation.
- Reuse source/job state fields `downloadedBytes`, `estimatedDownloadBytes`, `seconds`, observed transfer bytes, actual `Stage`, queue status and session budgets. Do not confuse application-level total historical network usage with this job's remaining bytes.
- Keep a compact mission-level estimate with a `View Download Activity` drill-down; advanced diagnostics remain accessible without filling the primary planning panel with verbose transfer metadata.

**Acceptance**
- A known-size bounded transfer reports a defensible, changing estimate after adequate rate samples, using independently testable throughput math.
- Unknown-size work shows Unknown/Calculating rather than 0% or an invented duration.
- Stalled, paused, rate-changing, failed and reused-local workflows produce truthful ETA changes, no negative time and no premature Ready.
- Per-instrument and mission-level ETA corresponds only to selected mission work and agrees with actual preparation state; advanced regional counts reconcile with each top-level instrument.
- Browser tests cover ETA math/state transitions and desktop/tablet layouts; installed Windows behavior requires actual testing.

## 0.4.1-UX-05 — Mission Control: select saved research plans before recording
**Priority:** P1 | **Type:** Mission selection, unified workflow, route preview

**Observed on 2026-10-19:** Mission Planner has named saved plans and a `Record this plan` action, but the dashboard's Mission Control idle form only offers operating mode, a free-text mission name and `Start mission`. Current `app.js` `start-form` submits `name`/`mode` without `planId`. The live Mission Control map reads the active mission's plan snapshot after recording begins and has no independent selected-plan preview in standby. The Planner's `Record this plan` button actually starts recording, which is not obvious from its wording. A user can thus have a prepared mission and scientific downloads in progress while seeing only the aircraft on the main Mission Control map.

**Desired experience**
- Add a prominent `Choose Mission` control to Mission Control: saved missions, searchable where practical, plus an explicit `Unplanned Flight` option. List actual plan names, template, science mode, aircraft preference (if any), survey area, route and selected payload summary. Treat saved plans as ready to **select**, not necessarily scientifically data-ready.
- Selecting a saved plan before recording displays its saved waypoints, polygons, generated patterns and current instrument configuration on the existing Mission Control map. Mark these as `Planned` distinct from actual `Recorded` track. Allow preview/fit/zoom before flight. The route must not require starting collection or recording.
- Show the **selected mission's** Queued/Downloading/Ready preparation summary, download ETA where defensible, local source coverage and a link to its detailed Download Activity; account for actively preparing plans and truly unprepared plans. Do not automatically start remote downloads by selection alone.
- For a saved plan, the Start Mission action must submit the plan ID and preserve the plan's immutable saved snapshot, mode, equipment and route, without silently reverting to an unplanned flight. For an unplanned flight, preserve the existing name/mode workflow.
- Replace Planner's ambiguous `Record this plan` label with **`Select for Flight`** as the ordinary action. It must only select/stage the plan and navigate to Mission Control with route/readiness preview; it must not start recording, automatically download, or manipulate aircraft navigation.
- Put an explicit **`Start Mission`** primary action on Mission Control, which starts recording the selected saved plan. If Planner retains a one-click immediate launch action, label it **`Start Recording Now`**, with an unambiguous confirmation if appropriate.
- Provide `Edit in Mission Planner`, `View on Map`, `Prepare Science Data` (explicit opt-in) and `Refresh Missions`. Keep status text clear: `Plan selected` is not `Recording`, and scientific preparation is not flight recording.
- The sidebar Mission Planner and Mission Control use the same underlying saved-plan records; changes reflect after save and refresh, including reopening after app restarts. No duplicate mission records from selection.
- Provide a compact preview/synchronized selected plan in the native MSFS toolbar where feasible, but do not add heavy map-processing UX or require it to change the aircraft FMS/autopilot.

**Acceptance**
- Save a named research plan in Planner; click `Select for Flight`, confirm that recording is still stopped, and see its exact stored route and survey boundary on the Mission Control map.
- Preflight preparation for that plan can be seen while on standby, and data can become Ready without an active flight.
- Starting the chosen plan records under the correct ID with the correct immutable plan snapshot and science mode; it never unexpectedly creates an unplanned mission.
- Unplanned flights remain available, and switching among saved plans changes preview/readiness without losing saved definitions.
- Map works during preflight and continues with planned-vs-actual overlays after recording starts; handles no route, missing drives, changing plans and incomplete preparations honestly.
- Confirm real Windows/desktop + physical iPad layout, keyboard navigation, and connection to native toolbar where supported.

## 0.4.1-PERF-01 — Increase science download concurrency safely
**Priority:** P1 | **Type:** Settings, throughput, resource management

**Observed:** Scientific access UI `scientific-access.js` restricts `Concurrent preparations` to max 2, `AutomaticScientificData.Validate` refuses values above 2, and the job scheduler uses this hard cap. Large multi-instrument missions can accumulate many queued preparation areas while the user waits.

**Desired experience**
- Raise the **proposed ordinary default to 4** concurrent preparations and offer user-configurable **up to 8**, subject to actual provider, bandwidth and storage validation. Assess whether an `Automatic (recommended)` mode or resource-adaptive limit is preferable to a fixed default; never assert that 8 always increases total throughput.
- Change **UI validation, backend preference validation, scheduler semantics and documentation consistently**. Existing saved preferences (including 1 or 2) must be preserved unless the user deliberately changes them; avoid silently overriding customization.
- Apply reasonable *per-provider/per-host* fairness, limits, retry/backoff, service 429/503 handling, bounded transport/reservations and CPU/disk memory caps. Prevent eight simultaneous science tasks from exhausting RAM, disk or network transfer budgets.
- Preserve flight-priority preparation, preflight/in-flight budgets, existing privacy/consent, source identity reuse and idempotent storage writes. Failed/paused jobs must not strand transfer reservations.
- The UI should make configurable `Concurrent downloads` distinct from `total queued regions`, `source provider request rate`, `data ready`, and `overall preparation ETA`. Warn that higher concurrency can saturate the connection or trigger provider rate limits.
- Instrument download queues should not starve each other solely because one provider is slow; queued/waiting reasons remain visible.

**Acceptance**
- Validate real multi-provider preparation at 1, 2, 4 and (if safe) 8 active slots, with timings and memory/disk/CPU/network measurements; compare completed valid work, not just concurrently open requests.
- Verify server rate limiting/error handling, retry/backoff, cancellation, interruption, restart, duplicate reuse, preemption and accurate budget ledgers under concurrency.
- Verify no loss/corruption of source data and no interruptions to active flight recording.
- Choose a defensible shipped default based on the measurements (4 proposed), document exceptions and cap; permit a lower limit on constrained connections.

**User feedback:** The v0.4.0 dashboard has numerous redundant controls, repeated explanations, cumbersome formatting and inconsistent design decisions across Mission Control, Mission Planner, Science, data sources and Settings. This is a *systemic presentation problem*, not a request to fix only a few isolated buttons. Use the user's October 19 v0.4.0 screenshots/QA observations as the baseline.

**Core principle:** The interface should feel like a cohesive airborne-research workstation organized around **Plan → Prepare → Fly → Analyze**, not a collection of separate technical utilities. Preserve the genuine scientific depth but put it behind purposeful drill-down.

**Required design/interaction audit**

Define the role and scope of each; remove duplicate pathways and ambiguous workflows without breaking existing deep links. An ordinary pilot should know where to create a mission, select it, prepare data, start/stop collection, inspect status, and review results.

- **Consistency/accessibility:** Responsive desktop, laptop/tablet and physical iPad layouts; coherent keyboard/focus/scroll behavior, color-independent status symbols, accessibility labels, readable contrast, understandable actions, no repeated huge layout shifts during live polling.
- **No visual-only fake completion:** Every primary button must work. UI consolidation must not discard archive/source data, privacy/consent, real transfer limits, instrument detail, warnings or scientific source provenance. Do not reduce actual scientific rigor for superficial styling.

**Design deliverables before implementation**

2. Provide practical low-fidelity wireframes or layout specifications for Mission Control, Planner, Scientific Data Preparation, Science/Results, Data Sources and Settings.
3. Propose one compact component/typography/status/action hierarchy reused across these pages, rather than building a second incompatible design system.
4. Implement the changes in small testable stages and provide **before/after screenshots** at typical Windows desktop width and physical iPad/tablet width, or clearly distinguish emulated captures until hardware test.
5. Perform five-minute first-use discovery and end-to-end pilot flow QA: **select/create mission → prepare data → preview → start → monitor → finish → replay/analysis**.

## 0.4.1-SCI-01 — Post-flight scientific downlink and bounded backfill
**Priority:** P1 investigation/implementation candidate | **Type:** Post-flight scientific preparation and derived analysis

**Product concept:** A mission recording may finish before external geographic datasets are fully prepared. If actual recorded aircraft telemetry and instrument state permit recovery, show **`Downlinking Science Data`** while remaining datasets download and eligible historical geographic samples are reconstructed *after* the flight. The title is a user-facing research-aircraft metaphor, **not a claim that the simulated aircraft transmitted a new captured satellite/LiDAR observation**.

**Current limitation:** v0.4.0 `RemoteAcquisition` attempts remote source sampling during the flight and records a missing interval if a compatible retained source was unavailable. Its own message states `this interval is not backfilled`. Mission telemetry is recorded separately, but failed acquisition attempts do not yet form a complete persistent replayable work queue. `MissionCoordinator.End` marks the flight completed and ends research independently of any post-flight regeneration. The existing archive replay/analysis services must be extended carefully, not assumed sufficient.

**Desired lifecycle**
1. When science collection ends or the flight recording is completed, evaluate whether required remote-source samples were missed specifically because prepared external datasets were unavailable, still queued/downloading, or outrun by the aircraft. Differentiate unrecoverable telemetry gaps, paused/disabled instruments, queue overflow, invalid source coverage, failed QA and genuine source unavailability.
2. Preserve separate statuses: **Flight: Completed** and **Scientific review: Ready / Downlink Pending / Downloading / Reconstructing / Partial / Blocked / Failed / Cancelled**. Do not mark a mission archive corrupted or the flight incomplete merely because final scientific analysis is delayed.
3. If recoverable work exists, offer or initiate a bounded, explicit post-flight preparation workflow subject to previously granted online science permissions, stored mission/plan identity, retention and transfer policies. No surprise network consent or unlimited download. Show **`Downlinking Science Data`** with one progress item per instrument and the download viewer; expand to original geographic units/attempts in Advanced.
4. After verified source files are available, reconstruct only scientifically supportable geographic values from **actual saved flight positions/timestamps, sensor profile and applicable instrument configuration/mount at that time**. Preserve historical source scene time separately from the flight packet and post-flight processing time. Clearly classify outputs as **post-flight derived reconstruction**, not an observation newly acquired in-flight.
5. Persist a durable, idempotent recovery job/manifest tied to immutable mission and configuration snapshots. Record eligible slots and exact reasons they were skipped; do not replay an approximate fixed interval over missing packets and claim those unrecorded positions actually existed. Prevent duplicate products and accidental replacement of original in-flight acquisitions. Handle crash/restart, pause/resume/cancel/retry, changed source selection, unavailable drives, cancellation, budget limits and source quality failures.
6. Allow **immediate flight replay**, but mark final coverage percentages, mosaics, reports and research-package exports **Pending / Provisional** while eligible backfill work remains. Once complete, recompute derived science products/coverage with proper invalidation and source/processing provenance; show the actual fraction recovered and unrecoverable gaps. Do not misrepresent a mission with unrecoverable data as fully Ready.
7. Use `Downloading Science Data`/ `Downlinking Science Data` for user-facing transfer progress, and `Processing Scientific Results` for actual local reconstruction/validation. If bytes or remaining jobs are unknown, ETA is **Unknown**, not a fake countdown. Do not block flight recording, other missions, local review, or existing stored science when external services fail.
8. Explicitly **exclude simulator atmosphere/cloud/temperature values that were never recorded, missing aircraft telemetry, unsaved physical scanner returns, and masked/nodata source pixels** from post-flight backfill. Historical external rasters can support reproducible geographical resampling, not an invented new observation. Respect intentional science pauses and disabled instrument periods.

**Release scoping:** Prototype end-to-end with one real retained-source provider/instrument and a known outrun geographic area, then expand if scientific/instrument config and archive integrity permit. If full post-flight reconstruction is not defensible in v0.4.1, still provide clear **flight complete / science still preparing** states and downloadable backlog progress without claiming regenerated observations. ## 0.4.1-PLAN-01 — Repeated identical straight transects, pilot-managed turnarounds
**Priority:** P1 | **Type:** Scientific survey planning, repeated track analysis, export compatibility

**Clarified user intent:** Straight Transect must use **the exact same two geographic endpoints and line on every pass**, with **NO step forward/backward, side-offset, or parallel sweep**. Lawnmower/creeping-line patterns already handle geographic progression. For repeated traversals, leave actual turn-around maneuvers to the **aircraft/pilot**, rather than hardcoding a turning radius that may be unsuitable for the chosen aircraft.

**Current implementation:** `FlightPatternKind.StraightTransect` in `FlightPatterns.Generate` generates just A→B; the existing `PatternDefinition.Legs` field is used by other patterns, not by straight transects. Current route export uses ordered waypoints for GPX/KML/PLN/CSV and may not behave identically in every EFB/FMS importer.

**Proposed user workflow**
- Add **Number of passes**, default 1 for old-plan compatibility (initial bounded 1–20), and clear **Repeat same line — alternating directions** wording.
- Set pass 1 A→B, pass 2 B→A, pass 3 A→B, etc.; all science passes are collinear and reuse **the same WGS84 endpoints**, no geographic step. The route may contain the ordered reference endpoints A,B,A,B while its native scientific metadata retains explicit distinct pass IDs, direction, expected order and optional per-pass target altitude. Avoid ever confusing repeated endpoints with duplicate-source records.
- Turnaround execution is **Pilot-managed**, outside the actual scientific transect. Do **not** generate a universal U-turn arc, assume an aircraft turn radius, add bogus survey mileage or issue autopilot/FMS commands. On map, show `Turn around / rejoin at endpoint B` (or A) as an instruction/callout rather than a completed or straight-line scientific leg. A pilot may use a procedure turn or wider maneuver appropriate for their aircraft.
- For estimated science length, `pass count × transect length` (e.g. 3 × 25 NM = 75 NM); additional turnaround distance and time are **not determined**. Display nominal science distance separately from unknown maneuvering distance; do not present the total route-distance estimate as complete when turnaround geometry is omitted.
- Optional **target altitude per pass** is valuable for atmospheric profiling; retain same horizontal line even when pass altitude changes. Altitudes are flight-plan references, not instructions to aircraft systems.
- Allow pilot to begin reentry on the outbound/inbound line; actual completed-pass analysis must use **recorded positions/times**, both endpoint proximity and direction/track consistency with appropriate tolerances, plus continuity and order checks. The pilot need not hit an infinitely precise coordinate, but merely turning at B does not automatically count a completed reverse pass.
- Map renders **one route line**, with directional arrows/pass labels and turnaround indicators at endpoints, not three offset lines. Preview/regenerate/save/reopen/history/replay retain all pass intent without changing v0.4.0 one-pass plans.

**Export strategy (pilot-managed, instrument-agnostic)**
- **Native AeroScience plan** keeps A/B endpoints, explicit pass count, directions, pass-specific altitude and `pilot-managed turnaround` semantics as the authoritative scientific mission plan.
- **GPX/KML/CSV** may export the ordered repeated endpoint sequence (A→B→A→B) with distinct pass labels/instructions and optional descriptive transition markers, **without inventing intermediate turnaround coordinates**. Include clear indication that between passes the aircraft must turn around and rejoin; do not count this maneuver as part of the scientific straight transect.
- **MSFS PLN and other external EFB/FMS consumers:** test actual repeated waypoint handling. If importing A,B,A,B produces problematic automatic routing or impossible turn depiction, provide a conservative **navigation export A→B only** plus a **separate pass instruction card/CSV** containing required repeat count, direction and target altitudes. Never promise an imported FMS will execute a safe turnaround. Make full repeated-waypoint export optional and compatibility-flagged only when tested.
- Distinguish **survey waypoints** from **navigation flight plan**. AeroScience should not force the EFB route to be a flight-control program; pilots fly their own aircraft.

**Acceptance**
- 1 pass matches existing simple A→B exact WGS84 geodesic geometry.
- 3 passes yield A→B→A→B as **three passes of exactly the same transect** with one visible geographic line, reliable pass sequence and no offset.
- No fabricated turn arcs, instant navigation jumps, extra geographic scan legs, auto-commands or misleading science duration. Turnaround clearly labeled pilot-managed.
- Native replay and pass analysis do not award completion for endpoint-only proximity or for skipped/missing telemetry.
- Export exact endpoint/direction instructions correctly, verify GPX/KML/CSV, test actual MSFS PLN import and document conservative fallback.
- Test units, true bearing, saved-plan migrations, patterns editing/regeneration, per-pass altitude, all-aircraft agnosticism, and atmospheric transect analysis.
