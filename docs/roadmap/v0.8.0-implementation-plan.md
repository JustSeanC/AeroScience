# AeroScience v0.8.0 — Implementation & UX Contract

**Status:** initial implementation specification for `develop/v0.8.0`; not a claim of shipping or acceptance. Read `v0.8.0-scope.md` before work.
**Base:** initial branch from `develop/v0.7.0` while its tester fixes continue separately.

## Approach

Reuse the .NET engine, mission coordinator, collection controller, source and provenance contracts, organization permissions, mission and science archives, and existing native MSFS toolbar bridge. No parallel new source of truth. Use the existing ES module/browser and SDK-compatible toolbar boundaries. Design from actual functional routes and controls rather than deleting screens before inventory.

Current relevant code: `src/AeroScience.Engine/wwwroot/index.html`, `app.js`, `task-workspaces.js`, `workstation-shell.js`, `workstation-ui.js`, `mission-operations.js`, `science-journey.js`, `personal-research*.js`, `science-workspace.js`, `science-analysis.js`, `science-compare.js`, `scientific-library.js`, `download-workspace.js`, `research-organizations.js`, `settings-navigation.js`, `app.css`, `workstation.css`; native `msfs-toolbar/PackageSources/html_ui/InGamePanels/AeroScience`. Verify file paths and actual handler ownership before touching code.

## P01 — inventory and audit (first Codex checkpoint)

1. Enumerate all top-level routes and deep-link aliases, visible panels, dialogs, controls, state owners, network calls, flight/collection/campaign command handlers and data safety boundaries. Include HTML-generated views and toolbar pages; do not assume the top navigation list is the complete application.
2. Build `docs/roadmap/v0.8.0-screen-inventory.md`: `old route / audience / main task / controller / critical status & errors / consent or deletion / new entry / obsolete-only-if-proven`. Include first-run connection, offline/no network, paused recording, mission ended, invalid science, organization no membership, data deletion and inaccessible download states.
3. Build `docs/roadmap/v0.8.0-usability-audit.md`: top problems ranked by task frequency, severity, and risk. Include validator-reported navigation clutter, manual collection ambiguity, mismatched toolbar state, duplicate downloads management, awkward interval edits, source/QA language, route waypoint entry, results visualization, and translation expansion hazards. Distinguish confirmed issues from new hypotheses.
4. Document current production/validation state boundaries, no-code touch policy for 0.7, tests available, exact source SHA, screenshots where available; use synthetic browser fixtures only with explicit labels. Do not claim actual SDK/flight validation from cloud/Linux.
5. Produce a traceable feature migration map. Mark each feature `prominent`, `contextual`, `advanced`, or `separate utility`; NOTHING removed without demonstrated redundancy and explicit owner approval.
6. Add small focused tests only where needed to preserve existing routing and critical status commands; do not demand Full CI on each planning checkpoint.

Exit: complete navigational/control inventory and approved migration proposal; no main/0.7 updates, no installer, no UI mass rewrite.

## P02 — shared foundation

Deliver:
- Shared visual tokens: accessible dark/light semantic colors, neutral surfaces, primary/secondary/danger, warning with text, font sizes and line heights, spacing/radii/shadows, 44-48px preferred major controls, minimum narrow panel behavior.
- Common primitives: button, status pill (text+icon), empty-state, next-action, dialog, disclosure, notification, form field, loading/error/refresh, source badge and evidence badge. Avoid decorative badges for routine statuses in overloaded pages.
- Navigation and routing contract: home/missions/flight/results/org and utility sections; old URLs stay resolvable; keyboard focus restored; no event handler leaks from view reparenting.
- Localization contract/locale selector and catalogs BEFORE feature screens; no unnecessary dependence on newer browser APIs in native MSFS.
- Screenshot and a11y baselines; keyboard, focus, reduced motion, high zoom, narrow MSFS layout and pseudo-locale validation.

Do not introduce React/Vue/etc solely to achieve appearance; justify any new dependency against packaging, offline support, Coherent GT and tests.

## P03 — Home and Missions

### Home states
- **Active flight:** active research name and actionable current state; link Current Flight; connection/permission and critical warnings.
- **Prepared/unfinished plan:** resume setup or choose another mission.
- **No mission, connected:** Start a Science Flight CTA, suggested simple templates and recent results.
- **Disconnected/offline:** status and recoverable connection steps; saved records remain accessible.
- **No data:** guidance without synthetic success/collection claims.

### Experiment card
Question, expected observation, prerequisites and source/aircraft compatibility, difficulty, `Fly Now` and `Customize`. Source text must reflect the real source category and readiness; no implicit historical/live equivalence.

### Readiness and execution
Guided defaults select only templates and sensor configurations actually supported. Existing preflight readiness service decides whether flight/collection is allowed; required downloads ask separately. Explicit start recording, then explicit science start/arm and actual auto-trigger explanation; make status and retained counts visible. Advanced planning preserves geometry, patterns, payload selection, multi-session, versions and saving modes.

## P04 — Current Flight and native toolbar

### Shared authoritative state model
Define a read-only presentation mapping from existing current flight, telemetry freshness, recording phase, science collection phase, instrument health/receipts, active card and focus, and organization live-sharing consent. The UI must not derive confirmed collection from a button click alone. Only confirmed command reply + refreshed server authority changes display. Stale/failed responses never enable an unsafe command.

### Dashboard primary layout
Mission name and current phase; connection banner; visible recorder and science collection separately; progress only from retained originals; map and current objective; compact instrument health; card actions when applicable. Show one primary next action relevant to controller state. Advanced telemetry, method, acquisition, calibration and evidence timeline one-level accessible behind clear disclosure/navigation, not hidden behind ambiguous glyphs.

### Toolbar
Three contextual tabs: Flight / Science / Cards (Cards when supported). Connection and two status indicators remain visible. Use short but translatable labels; avoid tiny tap targets; preserve native panel drag/resize/title and ES2017 tooling. Use original CommBus commands and strict build/flight/revision matching; do not assume desktop/browser JS support in MSFS runtime. Deep detailed analysis remains dashboard-only.

### Acceptance matrix
preflight -> recording -> science armed -> collecting -> paused -> resumed -> ended; auto gate waiting; session switching; cards focused vs activated, multiple compatible/incompatible; stale connection; incorrect build; no permission; invalid calibration/ground intersection; no observed samples; flight ends mid-science; local offline; queued org delivery. Test dash and toolbar status agreement for each.

## P05 — Results and Scientific Library

- Results `Overview`: what was actually saved, mission objectives and qualifications, summary charts only from compatible valid points, immediate critical source/QA warnings.
- `Explore`: chart defaults by collection type (profile, transect, terrain, survey); synchronized original selections in table and map; layer/source/date controls; no fabricated relationships or interpolated measurements.
- `Evidence`: original verified sample and selection, precise timestamps, units, dates, QA, provenance, methods, attempts, exports. Keep exact identity/compatibility checks and pagination.
- Scientific Library `Sources / Downloads / Storage`: unified discoverable shell; existing download queue/authorization/storage accounting/reuse logic; open data folder where supported; original permanent delete behavior and active-use checks. Do not turn permanent delete into archival/cached retention.
- Preserve every advanced import and inspection feature, including EMIT experimental status and source warnings; move, do not silently delete.

## P06 — Organizations and help

One clear entry for relevant assignment/claim, active campaign, optional live member flights, review/submission queue, and organization administration; maintain role-specific affordances. Pilot permission for ephemeral live sharing remains independent of any submission. Submitting evidence always shows recipient, original selected content/size, permission and disclosure. Help uses contextual task language and offline guides; links to detailed science definitions when needed.

## P07 — localization rollout

Implement first-wave catalogs and reviewed text for `en-US`, `es-ES`, `fr-FR`, `de-DE`, `pt-BR`, with fallback and translated completeness dashboard for developer review. Language picker uses the language's native name and makes current locale accessible. Keep scientific data and units independent. Pseudolocale, extreme-length strings, accented and non-Latin glyph smoke tests, and native build support.

Progressively translate all user-visible prose and native Windows dialogues; do not claim full localization with browser navigation only. See dedicated localization specification.

## P08 — acceptance and launch readiness

- Run fast targeted tests for each feature checkpoint; full integration suite at significant merge/release gates. Preserve >= v0.7 test coverage; do not relax assertions to make UI pass.
- Functional browser tests: routes/deep links, play flows, offline/simulation states, error and consent boundaries, screen sizes 1920/1440/1280/1024/820/768/390, zoom/reflow and map/table parity.
- Real installed Windows + MSFS 2024 native acceptance: toolbar packaged from proper SDK and matching companion, x64, drag, resize, controls, overlay, locale/special characters, build identity, persist recording after closure, no stale authorization.
- Novice usability study: at least 5 diverse first-time testers per useful iteration when practical, with independent task success/time and friction notes; target >=90% eventual success across a representative cohort, not based on one person.
- Localization acceptance: critical commands/consent/recovery in all advertised locales; fallback documented; functional browser and native long-text validation.
- Accessibility: automated audit + hands-on keyboard/screen-reader testing; WCAG 2.2 AA goals for browser, native exceptions explicitly recorded.
- No full release until source/provenance validity, storage/privacy, and 0.7 carry-forward regressions remain intact. Separate private validation from actual public release approval.

## Implementation checkpoints and merges

- P01/P02 can proceed while 0.7 beta testers are active.
- Avoid cherry-pick drift where possible: periodically forward merge accepted 0.7 changes into 0.8, with file-level conflict inspection and focused test matrix.

- Nothing on 0.8 should publish a public release, alter stable install settings/data, or modify 0.7 validator source without a separate explicit release decision.
