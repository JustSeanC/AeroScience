# AeroScience v0.8.0 — Simplicity, Usability & Localization

**Status:** proposed product and UX baseline, created during v0.7.0 external testing. **Not released; not validated in MSFS.**
**Development branch:** `develop/v0.8.0` (initially branched from `develop/v0.7.0`).
**Independence:** do not modify the active v0.7.0 validation branch, validator identities, installers, existing releases, production user data, or published release documentation as part of this design effort. Bring confirmed v0.7.0 corrections forward at controlled checkpoints, with conflict review and regression testing.

## Product promise

A person new to AeroScience can discover an experiment, prepare an aircraft, start recording, **explicitly** activate or arm scientific collection, fly, and understand the supported observations without a manual. Experienced users retain instrument configuration, mission planning, scientific evidence inspection, flight-test cards, organizations, and offline data management.

This is a **reuse-first frontend and interaction project**. The existing science engine, evidence contracts, mission/session/attempt controllers, scientific provenance, storage and privacy restrictions remain authoritative. Do not swap UI frameworks, clone controllers, create new stores of truth, or change scientific calculations merely to simplify presentation.

## Experience rules

1. **One primary next action:** each main screen has an obvious action appropriate to the authoritative current state, with clear secondary and optional advanced actions.
2. **Progressive disclosure:** display critical safety/validity blockers prominently, important operational status plainly, and specialist method/identity/diagnostic detail on demand. Explanations do not start operations or change permissions.
3. **No guessing about science:** visually distinguish simulator-reported observations, historically sourced data (with acquisition dates), modeled output, pilot entry, unavailable/unsupported inputs, and synthetic test fixtures. Flight track is not a measured swath.
4. **Flight recording and science collection are separate:** pause/resume/end controls do not imply synchronized state transitions; a research card focus is not a card activation; review is not approval.
5. **Consistent but appropriate surfaces:** dashboard owns planning, detailed review and management; toolbar emphasizes in-flight status, science controls and next objectives without reproducing the dashboard.
6. **Privacy first:** offline/local-first; downloading, live sharing, organization submission, authorization changes and permanent deletion always require the original explicit consent/review controls.
7. **Accessible and international:** readable text, keyboard/focus support, control sizes, responsive layouts, locale-independent scientific source values and unit preferences.
8. **No dark patterns:** no hidden active-science claims, background downloads without approval, or warning dismissal that makes an invalid state appear valid.

## Proposed information architecture

### Main dashboard navigation

- **Home** — contextual landing: simulator connection, active flight or unfinished plan, start experiment, recent results, next action. Not a static feature catalog.
- **Missions** — explore research templates, beginner `Fly Now`, customizable missions, geographic/route planning, experiment and instrument setup. Retain multiple cards and personal templates.
- **Current Flight** — authoritative recording/science status, concise controls, objective and active test cards, map, clear errors. Only flight-related controls by default; telemetry and method disclosures secondary.
- **Results** — recorded flights and analyses; summary -> maps/charts/comparisons -> verified evidence/exports. Maintain full original record access.
- **Organizations** — conditional when configured/used; assignment, approved evidence, submission/review, opt-in live map and org setup. Do not expose public upload implicitly.
- **Utilities** — Scientific Library (sources, downloads, retained storage, location, delete/manage), Settings, Help/Support. Preserve discoverable access to advanced functions.

The exact number of primary items may adapt to small screens. Preserve existing URL/bookmark behavior with a tested route map, accessible redirects and focus. Do not strand features behind a navigation simplification.

## Principal user journeys

### A. First-time independent scientist

1. On first launch, choose language, confirm local connection/setup status. No forced cloud account.
2. Home: **Explore science missions**. Select a plain-language experiment card (question, capabilities, aircraft suitability, extra sources and offline needs).
3. Choose **Fly Now**; recommend sensible configuration from the original template/instrument rules. Offer **Customize** for full configuration.
4. Show short readiness summary: selected aircraft/mission, science configuration, source availability, connection quality; authorized preparation/downloads are separately approved.
5. **Start Recording** explicitly. **Start Science Collection** or **Arm Collection** with actual trigger described; do not silently conflate the two.
6. Current Flight shows status and retained counts (not inferred scientific success), next objective and relevant controls. Stale controls fail closed with recovery guidance.
7. **End Mission** with appropriate review; open Results overview for the actual saved flight, preserving invalid/missing-data explanations.
8. Overview -> Explore -> Original Evidence -> export, as needed.

### B. Experienced experimenter

Use direct links to custom mission planning, payload calibration and mode, source preparation, test cards, multi-session automation, precise analysis, original evidence, geographic library and downloads. No capability disappears; fewer things demand attention at once.

### C. Organization participant

Assignments and research cards -> prepare locally -> opt in to temporary live sharing if desired -> explicitly review evidence and recipient before submission -> monitor independent review status. Existing upload, sharing, membership, retention, and role permissions remain separate and authoritative.

## Toolbar — native in-simulator control

Designed for small resizable native MSFS panel. Use three contextual areas: **Flight**, **Science**, **Cards** (only show Cards when relevant). Persistent, readable connection/build identity and recording/science state; prioritized action based on authoritative phase. Preserve native SDK drag/resize, ES2017/coherent compatibility, DOM fallbacks, and the removed VR compact toggle staying removed.

- Flight: mission identity, connection/freshness, recorder status, elapsed time, start/end recording and simple telemetry.
- Science: ready/armed/collecting/paused/ended/unavailable state, saved/rejected/missed counts correctly separated, collection next action, automation trigger when relevant, sensor details on demand.
- Cards: focused objective, active cards count, evidence/attempt state, manual observation and supported card focus/switching without confusing focus and activation.
- No toolbar-only new command authority; use original bridge commands and revisions. Disconnected or stale state disables unsafe actions.
- Responsive no-overflow typography; don't let translations obscure state, labels or controls. Preserve existing native title bar behavior.

## Results presentation

1. **Overview:** real retained readings or products, supported mission objectives, map/flight path, top findings with qualified provenance and visible critical quality limitations.
2. **Explore:** meaningful chart/map/table defaults chosen by actual data type and valid source; altitude profiles, terrain and temperature where supported. No interpolated observations or inferred coverage/sensor swaths.
3. **Evidence:** original readings, UTC/source dates, units, scientific QA, source/calibration method, uncertainty, identifiers, exact associations, attempts and exports. Legacy and missing identity paths retain warnings. Numeric and tabular alternatives to map required.

## Localization baseline

Target first wave: `en-US` source/fallback, `es-ES`, `fr-FR`, `de-DE`, `pt-BR`. These are **proposed release targets**, not already-translated interfaces. Prioritize verified critical, normal and advanced strings by workflow. Follow-on candidate languages: `ja-JP`, `zh-CN`, `it-IT`, `pl-PL` after proof of font/runtime support and translation review.

Locale selection applies to local dashboard + toolbar + native companion when technically viable; org portal can honor per-user locale, with an explicit precedence policy. Keep language, measurement units, timezone/time formatting and coordinates independent. Original scientific numeric values, UTC identifiers, source dates and hashes are never translated or mutated. Use a shared message catalog contract, localization helpers adapted to native/Coherent runtimes, accessible language-name picker (no flag-as-language UI), and English fallback for missing strings.

See `docs/roadmap/v0.8.0-localization.md`.

## Phases and gates

- **P01: Evidence-first UX inventory.** Every route/dialog/toolbar control and workflow; usability pain register, migration table, screenshots and test baselines. No removal of functionality.
- **P02: Design foundations.** Navigation and components contract, typography/theme/tokens, mobile/native sizing, localization infrastructure, accessible interaction standards.
- **P03: Home + Missions.** Dynamic Home, approachable experiment cards, friendly guided preparation, optional Customize, existing readiness authoritative.
- **P04: Current Flight + Toolbar.** One operational task-first experience, live synchronized status, obvious recording/science distinction and native ergonomic controls.
- **P05: Results + Scientific Library.** Overview/Explore/Evidence and unified sources/downloads/storage, preservation of all expert tools.
- **P06: Organizations + Help.** Guided assignments/review/live opt-in, contextual help and error recovery, no loss of permission barriers.
- **P07: Internationalization/locale rollout.** Finish first-wave strings, reviewed language coverage, pseudo-localization, number/date/units distinction and runtime native validation.
- **P08: Release validation.** Usability, science integrity, accessibility, large datasets, offline, update/migration and installed Windows/MSFS acceptance.

Build P02 locale contract **before** new UI features; P07 should not be a last-minute hardcoded string replacement.

## Non-goals and boundaries

- No scientific measurement/model changes, new sensors/providers, or backend rewrite as a UI requirement.
- No remote aircraft control, new automatic sharing, unreviewed uploads, changed deletion semantics, or forced sign-in.
- No quiet changes to Universal/Realistic operating/assessment logic, card evaluations, controller cadence or DB migrations.
- No claim that real-user research, native MSFS acceptance, source validation or WCAG conformance have passed before observed evidence.
- No modifying stable v0.6.0 or v0.7.0 release/validator artifacts.

## Success measures (targets, not results)

- >=90% of representative first-time testers complete an eligible guided experiment/record/collect/review workflow independently (with support requirements and availability noted); log failure stage and time.
- All primary task states have one intelligible next action; major entrypoints aim for <=3 UI actions from relevant workspace, excluding explicit readiness/consent and safety steps.
- No lost/mislabeled original scientific evidence, unintended recording/collection state change, silent download or consent regression; preserve 0.7 regression tests.
- WCAG 2.2 AA review target for supported browser surfaces and equivalent best-effort keyboard/readability in native MSFS; automated scans alone do not prove conformance.
- Every first-wave locale has reviewed critical actions and safety language before being marked release-ready, with translated UI, overflow and missing-key tests.
- Full and expensive suites run at meaningful integration/release gates; fast targeted suites on intermediate implementation checkpoints.
