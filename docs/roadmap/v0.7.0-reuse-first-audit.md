# AeroScience v0.7.0 — Reuse-First Architecture and Baseline Audit

**Owner directive, October 23, 2026: mandatory planning rule.** No product code changes or premature refactors authorized. This document is a **research gate**, not a mandate to create another framework, layer or feature subsystem.

> **Updated owner rule (2026-10-23): Backend reuse is the priority; UI reuse is not a constraint.** AeroScience v0.7.0 can *substantially redesign* dashboard, Mission Planner, Science Results, Research hub, organization portal and native toolbar interfaces whenever the change improves the established UX rubric. Retain and integrate functioning **backend services, scientific/flight data pipelines, source preparation, persistence, APIs and collection logic** wherever they meet the requirement; propose entirely new backend components only after a verified functional gap. Existing UI components are reuse candidates, not mandatory layouts. Maintain product behavior, data contracts, scientific integrity, privacy and backward compatibility. This clarification supersedes any earlier wording implying that v0.7.0 must preserve current page structures or markup.

## Release truth and working sequence

- **v0.5.0 is the current release** and should be treated as the shipped/user-tested baseline.
- **v0.6.0 is actively being developed by Codex**, with significant progress and moving implementation; do not freeze architecture assumptions based solely on stale snapshots or earlier backlog documents.
- **v0.7.0 is planning/technical research**, not authorized for implementation, merges into main/develop/v0.6.0, release publishing or competing parallel reimplementation.
- **Before authoring a v0.7.0 Codex implementation prompt or feature architecture:** re-inspect the latest `develop/v0.6.0` and actual feature contracts, compare with v0.5.0 behavior, identify shipped vs merged vs underway vs not yet implemented. A release/in-progress feature must not be falsely described as missing merely because earlier design notes predate it.

## Owner's highest-priority constraint: reuse existing AeroScience

**Avoid duplicating backend systems:** do not create a parallel instrument pipeline, mission-plan storage/evaluation engine, data downloader, telemetry recorder, science results data store, scientific acquisition worker, analysis computation core or scientific library when a usable implementation already exists. **UI presentation is explicitly redesignable.** Reuse existing front-end modules when useful, but do not preserve confusing layouts, interaction models or navigation solely for code reuse. Integrate, expose, simplify, extend and test the established backend first.

For every proposed v0.7 feature/UX change, answer **in this order**, with links to current source files and test evidence:

1. **Already works:** Which v0.5/v0.6 modules already implement the exact capability? Use as-is (potentially with copy/labels), not a redesign.
2. **Needs adjustment:** Is the intended outcome achievable through settings, templates, more helpful progress/error UI, workflow defaults, additional metadata, or a small extension within an existing module?
3. **Needs integration:** Can two or more existing subsystems be wired together into the requested workflow without a parallel queue, separate store, or duplicative state machine? If so, use the existing contracts/services.
4. **Genuine functional gap:** Only if the capability is missing, substantiate why the existing extension points cannot meet it, the minimum new addition required, its integration boundary, compatibility and regression acceptance.
5. **Release/ownership check:** Confirm whether work is already landing in v0.6.0, still slated for v0.6.0, or owned by a later planned release before duplicating it in v0.7.0.

No architecture proposal should say "build a new X" unless step 4 is demonstrated. An infrastructure proposal in older research docs is **provisional and subject to this audit**, not a finalized instruction.

## Interaction/UX priorities (reuse-first)

- When user selects a personal/scanning research template, prepopulate existing **Mission Planner**, instrument setup, science sessions and patterns. `Fly Now` is a shortcut into existing capabilities, not an independent second planner or pipeline.
- Surface preparation **Ready / Preparing / Awaiting Source / Not Available / Paused** and why, pulling real existing state rather than fabricating optimistic status. Keep existing online/offline, budget, privacy and user setting behavior.
- When existing local data is scientifically compatible, reuse it as the current v0.6 subsystem intends. Avoid duplicate downloads or generating parallel copies because a test card references the data.
- Compare repeated-flight results using existing flight/science results and analysis where possible; add links/filters/summaries before designing new parallel databases or chart engines.
- Link local test-card attempts to existing recorded flight/sample/observation identities. Only genuinely missing organizational assignment, claim, review and optional submission lifecycle should require new backend functionality.

## Owner clarification — backend reuse, interface redesign freedom and established UX rubric (2026-10-23)

**Do not conflate backend reuse with a visual/UI freeze.** v0.7.0 is explicitly **allowed to redesign screens and user journeys**. A refreshed dashboard navigation, redesigned Mission Planner pages, visual science analysis, organization portal and MSFS toolbar may change significantly—even replace existing front-end composition—when justified by measurable usability improvement. Keep backend integration contracts, persistent scientific data, existing scientific worker/flight processes, data provenance and compatibility intact whenever the underlying system already provides the behavior. A new visual component is not automatically a forbidden new *system*. Conversely, a pretty interface is not grounds to duplicate scientific pipelines or mission storage.

**Historical UX baseline:** an earlier provisional AeroScience UI assessment was approximately **5.9/10** and aimed for **9–10/10**. This is a prior assessment, *not a verified score for the changing v0.6.0 code*. Reassess the current baseline before claiming progress.

**Previously agreed UX rubric dimensions:**
1. **Navigation and workflow organization** — clear task flow and information hierarchy; personal and organizational work accessible without navigating irrelevant surfaces.
2. **Scientific visualization and interpretation** — map/chart clarity, meaningful labels, valid results and science context; users can understand what they collected.
3. **Visual design and consistency** — readable typography, coherent spacing, panel hierarchy, purposefully organized content and reduced clutter.
4. **Status, feedback and error handling** — collection vs flight recorder vs science availability distinctly shown; actions confirm completion/failure and offer actionable recovery.
5. **Accessibility and responsive behavior** — keyboard, screen-reader labels, contrast, zoom, adaptable desktop/tablet layout, touch targets and resizable MSFS toolbar/VR constraints.
6. **Performance and reliability** — no expensive work blocking flight recording or toolbar redraw; responsive maps, bounded datasets, offline/error stability.
7. **Discoverability, guidance and documentation** — a first-time user can identify how to plan, prepare, collect, pause, finish and review science without personal coaching.

**Companion previously used QA scoring dimensions:** Learnability; Navigation/discoverability; Clarity of scientific results; Visual readability/polish; Responsiveness/feedback; iPad/VR usability. Preserve these as observable test domains (1–5 per domain is acceptable for historical comparison), without inventing untested numeric scores.

**Primary usability acceptance question:** "Can someone who has never used AeroScience successfully plan a research flight, collect science, and understand their results without needing the developer to explain the process?" For v0.7 extend this to **claiming/activating/reviewing organizational test cards** without degrading the original independent pilot flow.

**UX delivery gate:** before/after visual assessment on current v0.6 baseline, novice uncoached task walkthroughs, tablet/VR/toolbar resize checks, keyboard/accessibility checks and quantitative/qualitative rubric scoring. Prioritize the highest-friction workflow even when it requires comprehensive UI replacement. Avoid scoring on mockups alone: inspect actual running build, real simulator data states and realistic errors. Regression test old missions, downloads, manual import, source reuse/deletion, science sessions and analysis. UX redesign is authorized *in planning*, not yet an instruction to ship code.

**Implementation prompt format:** Each recommendation should list (A) existing backend to reuse, (B) screen/user journey being redesigned or improved, (C) UX rubric issue it resolves, (D) measurable task/visual acceptance, and (E) any substantiated missing backend work. Front-end reuse is an optimization only where it supports (C) and (D).
