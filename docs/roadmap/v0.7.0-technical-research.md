## 1. Confirmed product boundaries

- Release theme: optional Research Campaigns, including independent self-hosted organizations, manager-authored or assisted campaign objectives/test cards, assignment to pilots, explicit evidence submission, evaluation/review and progress synchronization.
- AeroScience remains a local-first scientific flight application. No AeroScience-wide account, required network connection, centralized service, background scientific-library upload, hosted MSFS telemetry receiver, simulator controls, or dependence on a particular organization.
- Users explicitly select a trusted organization URL, sign in, choose what to submit and can leave the organization without losing their own missions.
- Preserve Universal and Realistic modes, independent flight/science sessions, immutable start/configuration snapshots, provenance and uncertainty, offline results, and read-only simulator integration.
- The existing roadmap [research-campaigns-self-hosting.md](research-campaigns-self-hosting.md) is an architecture proposal, not shipped functionality. Its 16 required self-hosting-guide topics are part of release completion.

## 3. Recommended reference architecture (proposed)

1. **Desktop connector (opt-in):** a new organization tab/section in the existing Windows dashboard. Independent organization entries, server URL + verified TLS identity, login in system browser, explicitly downloaded campaign definitions, locally queued drafts, user-confirmed submission, logout/disconnect and conflict states. Don't couple to mission recorder's 1-second processing path.
2. **Shared contracts/evaluator:** platform-neutral versioned DTOs and pure, deterministic evaluation library. No network/Windows dependency. Preserve old observation models; make evaluator versions and mission-evidence cutoff explicit.
3. **Organization API:** a separate cross-platform ASP.NET Core (net10.0) project with authenticated endpoints, organization-scoped authorization, rate/size limits, audit records, review workflow, OpenAPI, health/ready endpoints, and migration verification.
4. **Persistent server data:** PostgreSQL as preferred operational DB for multi-user transactions, identity/membership, campaigns, submission/review history, dedupe keys and outbox. For first release, allow bounded attachment storage on a protected Docker volume, not mandatory S3/MinIO. Store content digests; scan/validate attachments. Object-storage adapters are optional future expansion only after measured need.
5. **Deployment:** one tested Docker Compose stack: organization API, PostgreSQL, TLS reverse proxy such as Caddy; persistent database, attachment and TLS state volumes. Only HTTPS proxy exposed publicly; database internal. Pin image versions/digests for released examples. Explicit external backups plus restore drill. Only document a Windows-host option if tested end-to-end.

Why: existing Windows/SimConnect process and its local paired-browser permissions cannot safely double as a public organizational service. A single-organization-per-install deployment limits v0.7.0 complexity; model organization IDs in contracts to permit later migration without implying that multi-tenant hosting has been implemented.

## 4. Identity and access: research decision required before code

Use established account management rather than inventing password storage, refresh-token formats or encryption. The organization-server browser may use ASP.NET Core Identity with secure HttpOnly/SameSite cookies, MFA and invitation-only registration. For the desktop client, prefer **system-browser authorization code + PKCE with a standards-compliant OAuth/OIDC provider**; prototype whether embedding OpenIddict within the server meets minimum security and operator complexity. Never reuse the local dashboard pairing identity.

Important limitation: the built-in ASP.NET Core Identity API bearer tokens are **proprietary non-JWT tokens** and Microsoft explicitly does not present them as a full OIDC provider. Do not claim they implement OAuth Authorization Code/PKCE. Document and test the actual chosen desktop login flow before publishing security guidance.

Sources:
- https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0
- https://datatracker.ietf.org/doc/html/rfc8252
- https://documentation.openiddict.com/guides/choosing-the-right-flow.html

Authorization: owner/admin, campaign manager, reviewer, pilot and observer, with default-deny authorization on **every** campaign, objective, assignment, submission, evaluation, attachment and review endpoint. Check both action permission and concrete resource ownership/membership; a UUID is not proof of access. Prevent reviewer self-approval unless campaign policy explicitly permits and audits it. Test invitation expiry, role removal, token revocation, membership changes mid-sync, cross-user ID substitution, CSRF, brute-force/login throttling, hostile organization URLs, HTTP downgrade, credential leaks, and malicious attachment names/bodies.

## 5. Campaign contract sketch (proposed, not implemented)

Every record has stable UUID, schemaVersion, createdUtc, revision/updatedUtc, owning organization, actor/audit context and optional immutable policy hash where applicable.

- Organization: identity, display name, discovery/API schema bounds, registration/invitation policy and storage rules.
- Campaign: description, status Draft/Open/Closed/Archived, scientific goals, baseline evaluator policy + date, required objectives, revision.
- Objective/TestCard: observable condition(s) in canonical units, tolerances and inclusive/exclusive boundaries, required instruments/source quality, repeat-count, coverage/cadence thresholds, allowed collection time window and *explicit* unknown handling. A generated objective is a reviewed draft until manager approval.
- Assignment: objective/card, pilot or team, due/time window if provided, work status, revision.
- Submission: assigned objective/card, pilot, immutable local mission and session IDs, snapshot/evidence manifest, explicit included observation/sample ranges, checksum, redactions, idempotency key, submitted UTC, attachments metadata, server receipt UTC.
- Evaluation: evaluator algorithm/version/hash, criteria results Pass/Fail/InsufficientEvidence/NotApplicable/NeedsHumanReview; values+units, coverage denominator, basis and human-readable findings. Never treat simulated-local data integrity hashes as proof a real aircraft flew.
- Review: reviewer identity, timestamp, decision Pending/Approved/Rejected/NeedsChanges, notes, link to exact immutable submission revision/evaluation. Review approval never mutates local science history.
- AuditEvent: action, actor, target/revision, UTC, reason, policy version; avoid dumping telemetry, credentials or sensitive science values into logs.

Use authoritative **canonical units** in evaluators, convert only for display. A missing datum is Unknown/InsufficientEvidence, not a fabricated pass. Distinguish flight-collected simulator readings from original dated external scientific scenes and reconstructed postflight products. The server may independently recompute only when the included source/calibration inputs suffice. A server-provided evaluation is organization policy, not a validated real scientific instrument measurement.

## 6. Minimum API/sync outline (proposed)

Version the service and each payload independently; negotiate a supported client/server compatibility window. Proposed endpoint families:
- GET /.well-known/aeroscience-organization : signed/HTTPS-bound server metadata and API compatibility (metadata alone is not authentication).
- GET /api/v1/me, /organizations/current, /campaigns, /campaigns/{id}/cards, /assignments/mine with bounded cursors and revision/ETag.
- POST/PATCH campaign and card definitions behind manager role, with If-Match optimistic concurrency.
- POST /api/v1/submissions/intents : preview/hash/consent scope and server policy check; server returns an upload intent with max total bytes/expiry.
- POST /api/v1/submissions : idempotency key and manifest, staged attachments only when expressly selected; commit only after hash/authorization validation.
- GET /api/v1/submissions/{id}/status and review/evaluation routes; GET progress with bounded paging and change cursor.
- DELETE/revoke routes governed by documented campaign retention; no implicit deletion of personal local missions.

Offline contract: cache only explicitly selected campaign definitions. Record locally as before. Submissions are a **user-confirmed durable queue** with visible Unsynced, WaitingForConfirmation, Uploading, Submitted, Conflict, Rejected, Revoked or NeedsReview states. Use idempotency keys and immutable submission revisions; retry with exponential bounded backoff; ETag/If-Match to prevent last-writer overwrite. On changed card criteria, show a conflict and require the pilot/manager to choose a resolution; never silently regrade previously submitted evidence against an unrelated policy revision. Network disconnect/server closure never blocks flight or overwrites local data.

Concurrency reference: https://learn.microsoft.com/en-us/aspnet/core/data/ef-rp/concurrency?view=aspnetcore-10.0

## 7. Scientific storage, reuse and deletion boundaries

- The **local scientific library** remains local. Never upload downloaded terrain, EMIT scenes, original external files, unselected mission histories, or high-rate flight telemetry automatically.
- Submit a **small, human-inspectable evidence package** with only mission/objective evidence needed; include provenance hashes and actual included observed samples. Optional large attachments require another specific size/licensing/consent action.
- Already-retained scientifically compatible local elevation/source data should be reused rather than downloaded again; this is a v0.6.0 library requirement, not a reason for organizational servers to centralize user's original datasets.
- Local user deletion of external/scientific collection data must truly delete user-selected data with no hidden local archive/cache/backup; no organization feature may secretly resurrect it. Retain only other independently saved results the user has chosen to preserve and that are sufficient for their own display.
- **Independent submitted copies on an organization server** must be explicitly disclosed as separate copies subject to that organization's published retention/deletion rules. Deleting one's local data cannot pretend to delete remote submissions/backups. Provide a request-to-remove/delete submission flow and defined server backup expiration/restore suppression so a removed submission is not silently resurrected in live storage.
- The existing self-hosting roadmap requires disaster-recovery database and attachment backups. This is distinct from forbidden stealth *local science-data* backups. Document exact scopes, retention limits, deletion semantics and restore rules before implementing hosting.
- The science recorder retains its priority; uploads/metadata operations are rate/bandwidth/capacity bounded and cannot block normal science recording.

## 10. Proposed first end-to-end pilot scenario

A virtual research organization manager creates one **aircraft-agnostic experimental sensor campaign** with three scientific test cards: (A) altitude/airspeed hold within explicit unit/tolerance; (B) ambient temperature sampled over a defined time window; (C) an instrument/survey sampling task with provenance and minimum valid acquisitions. Assign two pilots compatible fast-jet test cards; one pilot may execute more than one card within one sortie while each card retains independent evidence and evaluation. Each pilot downloads a definition, disconnects internet, flies a normal MSFS 2024 mission in the desktop app, previews/redacts included evidence, explicitly submits only that evidence after reconnection; reviewer sees each criterion and uncertainty, approves one and requests changes on another. Campaign progress includes Approved, Pending and Insufficient Evidence accurately. Reopening offline archives, deleting unrelated local external data and losing server connection must not damage flight data.

**Non-acceptance:** passing CI without real Linux Compose install/restore, server load measurements, pilot/instructor UI testing, security tests, and Windows/MSFS regressions is insufficient.

## 14. Owner-defined scientific research and flight-test evaluation requirements (2026-10-23)

See [owner design decisions](v0.7.0-product-decisions.md) for complete Round 1–3 selections and the authoritative **local science + explicit postflight submission** boundary.

- **One framework, graduated complexity:** Standard research campaigns are simple; developmental MSFS aircraft/add-on test programs optionally add phase hierarchy, test-card series, explicit test points, configuration snapshots, repeated attempts and milestone/gate policies. Templates-first setup remains preferred. These are capabilities on top of existing Universal/Realistic science modes, not new operating modes.
- **Evaluation sources are typed:** Auto-check conditions only from reliable recorded simulator observations or separately supported imported evidence with explicit provenance, units, quality, temporal continuity and evaluator version. Unsupported simulated avionics or structural parameters become human observation / insufficient evidence rather than fictional automated measurements. Approved review policy may require both automated criteria and human authorization.
- **Configurable administrative clearance:** Phases/test cards may depend on earlier reviewed results or manager waiver; record immutable authorization policy revisions, reviewer, timestamp, overrides/reasons. Clearance is **only** authorization to conduct/claim organizational tests and does not lock MSFS controls, aircraft usage, local missions or flight recording.
- **Target — clarified after Round 4:** Mostly **aircraft-agnostic fictional technology-validation and airborne science campaigns**. The research subject can be simulated experimental hardware sensors, avionics/software/system concepts or scientific payloads flown on any eligible MSFS aircraft within specified flight regimes. XB-1/X-plane inspiration concerns **test methodology**, not aircraft-specific development or certification. Record aircraft/add-on provenance but prioritize observed regime and declared compatible instrument capability. Real hardware certification and external physical hardware testing are outside v0.7.0.
- **Future live-operations vision:** Eventually support a non-controlling test director who monitors flights, coordinates, manages test points, records anomalies and recommends hold/abort. **Never ship or enable a live team console/telemetry streaming in v0.7.0**; asynchronous submitted anomalies, reports and reviewer decisions may exist in v0.7.0. Keep the future-ready seam described in section 12, without preemptive operational infrastructure.

### Acceptance cases that now need tests
1. Basic research mission completes without exposing test-program complexity.
2. Advanced program has dependent phases; an incomplete/insufficient-evidence prerequisite remains blocked in organizational workflow without blocking actual MSFS flight.
3. A test point held at a recorded Mach/altitude for a required duration verifies cadence and gaps; a missing/invalid sample cannot silently count as continuous success.
4. An unavailable simulator system variable is visibly marked unsupported and a pilot observation is labeled and routed for review.
5. Failure, partial success and a repeat flight retain separate immutable attempts and the exact evaluator/policy versions.
6. Switching an organization to human-review policy cannot retroactively rewrite historic approved evaluation snapshots.
7. No local recorder/API start/end flow is affected by an offline organization or an unapproved flight-test phase.
8. Neither pilot membership nor submission consent silently creates live telemetry sessions.

**Subsequent Round 4 resolved:** multiple test cards may belong to a single flight, evaluated independently. Remaining: overlapping evidence policy, optional re-flight/waiver mechanics, template catalog, custom modeled-sensor authoring depth, and future live release/version.

## 15. Round 4 — independent cards per sortie and aircraft-agnostic test subjects

Owner selected **multiple independently evaluated test cards per one recorded flight**. A campaign manager may define an abstract 'fast jet capable of flight regime X' eligibility criterion instead of pinning a test card to the F-15, XB-1 or another named type. Example: simulated new sensor tested at different Mach/altitude/temperature conditions across multiple cards. Require accurate applicability, not a hardcoded aircraft whitelist.

Architectural implications:
1. Store one authoritative flight/telemetry archive and attach many card-attempt evidence pointers (windows, sample sequences, science session IDs) rather than duplicating entire flight recordings for each card. Preserve card-definition version/hash and recorded aircraft/source/provenance for reproducibility.
2. Allow cards to overlap in time only when independently eligible; evaluate acceptance, gaps and missing source on each card separately. A shared flight is not a shared pass. An incomplete card remains incomplete even if other cards pass.
3. Describe eligibility as requested flight conditions, verified measurements, selected simulated instrument/capability and explicit exceptions. Do not assume a label like 'fast jet' proves Mach/altitude capability; judge measured regimes from eligible flight evidence.
4. Separate real simulator-reported measurements, documented modeled/derived fictional sensor outputs, manual pilot/test-engineer observations and unsupported parameters. **No fictional source reading invented without an approved sensor model/source.**
5. Keep multi-card preparation, local acquisition and explicit postflight submissions independent of live organization streaming. The server receives chosen evidence and per-card evaluation/review, not automatic full flight telemetry.
6. Acceptance test: one sortie reaches 3 distinct cards; two pass, one lacks valid science/source or misses duration. Show two eligible passes and one insufficient/failed card, with immutable attempts, bounded uploads and independent reviews. Re-test later without rewriting original flight or evidence.

## 16. Hybrid sensor modeling decision — research and acceptance (2026-10-23)

Owner approved **both flight-condition verification and simulated experimental-sensor modeling**, selectable by campaign/test card. **Manager-facing sensor authoring is configurable supported templates**; no unrestricted custom model code. Templates-first remains preferred.

**Proposed v0.7.0 implementation pattern:** Represent a card criterion as either a direct recorded-signal predicate (e.g. altitude or Mach regime) or an evaluation of a separately defined `ExperimentalSensorModel` channel. Integrate with existing ScientificEvidenceContext/instrument profile/calibration/provenance records; do **not** create a parallel flight recorder or pretend a sensor has physical measurements without actual support. Model definitions should specify source channel IDs, applicability, parameter values with canonical units, deterministic transform, optional declared stochastic error/seed, output units/range/uncertainty, version/hash and source observations. Explicit labels must distinguish SimulatorReported, Derived/InstrumentModeled, ExternalDataset and UserReported. Freeze complete effective definitions per attempt and preserve original inputs. Invalid/unavailable inputs yield Unsupported or InsufficientEvidence, not an invented passing value. If a model uses dated satellite data, preserve observation date vs simulated flight time.

**Tests:**
1. One local flight satisfies two independent direct flight-regime test cards and a separate modeled sensor card; all three maintain distinct status/evidence.
2. A published model reproduces outputs from identical inputs and version/configuration (including stochastic seed if used); revised model never silently mutates historic evaluations.
3. Bad units, unavailable source channels, missing external data and gaps yield understandable failure/insufficiency without interpolating untrusted data into an automatic pass.
4. Submission preview separates source observations, modeled derivations and pilot notes, and sends no unselected original external files or telemetry.
5. Simulated sensor measurements carry clear origin/limitations in pilot display, exports, server evaluation and reviewer UI.

**Updated decision:** configurable supported experimental-sensor templates with validated parameters and traceable model revisions; arbitrary user-defined model code and executable scripts are not in the approved v0.7.0 scope. Still research the supported parameter vocabulary, example scientific models, sources, reproducibility and error behavior.

## 17. Additional aircraft-validation campaign template and configurable sensor authoring (2026-10-23)

Owner clarified: **Most experiments are aircraft-agnostic**, but support optional **fictional experimental aircraft validation test programs and cards** as a first-class use case alongside science and modeled-sensor trials. XB-1/X-programs inspire card and phase design, not real-aircraft type certification. Reuse one configurable program/card/evidence backbone with template families such as scientific survey, experimental sensor/payload, aircraft flight-test and mixed campaign; do not add a new global science mode or force every research manager into a complex aircraft-development workflow.

**Sensor authoring selected:** guided configuration of supported experimental instrument models only. Manager edits safe typed parameters (input signal(s), valid operating domain, sampling cadence, response, sensitivity, bounds, declared uncertainty/noise model, output channels), previews expected modeled behavior, and publishes frozen version/hash. Reject unrecognized parameters, unsatisfied dependencies and invalid units. Never execute arbitrary user-supplied scripts or pretend a modeled fictional hardware reading is simulator-provided. Reuse the existing instrument/payload calibration and evidence contracts.

**Aircraft test template:** card conditions may assess available Mach/IAS/TAS/altitude/VS/temperature etc. against explicit regimes, hold durations, timing gaps, tolerances, and support metadata/unknowns; manual reports may assess pilot-observed handling, simulated systems, or declared add-on behaviors. Fictional model-based avionics/system results require explicitly supported model inputs and cannot masquerade as native simulator telemetry. Multiple independent cards can be satisfied on one locally recorded sortie. Phase clearances remain **organizational only**, not simulator controls or real safety authorizations. Campaigns remain aircraft-agnostic unless an explicit, defensible eligibility criterion is chosen; **managers are now permitted to restrict to specific aircraft types/configurations, when their test requires it**, while the default remains any qualifying aircraft.

**Suggested acceptance cases:** (a) a survey aircraft with configured modeled sensor plus flight regime cards, (b) an experimental aircraft test campaign with sustained-speed/altitude and human handling observations, (c) both programs using one evidence submission/review mechanism, (d) changed sensor template parameters do not rewrite historic attempt results, (e) unsupported flight-dynamics variables are visibly not measurable, and (f) no live telemetry traffic occurs absent explicit user-submitted evidence.

## 18. Aircraft eligibility: optional class/type/configuration constraints (2026-10-23)

**Owner decision:** Most v0.7 campaigns accept any aircraft satisfying scientific/flight-regime criteria, but a manager may optionally declare aircraft class/capability, exact type/add-on, or documented configuration as an eligibility requirement. Applied to generic science, fictional sensor validation, and fictional aircraft-development cards alike, without making every campaign aircraft-specific.

**Proposed technical model:** immutable `AircraftEligibilityPolicy` snapshot within the versioned card/campaign definition, with default `AnyCapableAircraft`, optional capability/class requirements and optional exact type/configuration constraints. Define its source/proof requirements and separate tri-state applicability `Eligible/NotEligible/Unverified` from independent test-point scoring `Passed/Failed/InsufficientEvidence/NeedsReview`. Never treat the string 'fast jet' or an aircraft model label as proof of actual achievable Mach/altitude. Use observed recorded conditions for measurement-based criteria. Record MSFS aircraft identity and version/configuration only when accessible; otherwise retain a user-declared/attested provenance label and offer human verification as policy allows. The original sortie and each card attempt retain card policy revision/hash and aircraft identification evidence.

**Required tests:** a generic altitude/sensor card passes for two different compatible airplanes when supported evidence satisfies conditions; a class-restricted card shows rejected/unknown eligibility clearly; exact-type restriction matches reliably identified aircraft if available and sends unverifiable add-on versions to manual review; no aircraft policy stops a local flight, interferes with one-second recording, forces a download, or turns test submission into live telemetry. For multiple cards on one sortie, eligibility may differ independently per card.

**Open design:** the manager-facing test-card creation workflow, compound conditions, observation requirement, time-window selection and reflight attempt handling. No new certification claims or simulator-control commands.

## 19. Round 6 — test-card authoring and attempt evaluation research (2026-10-23)

**Confirmed owner choices:** shared-schema guided wizard and advanced editor; standard and expressive criteria with AND/OR, ordered sequences and repeats; automatic qualifying-interval discovery **and** manual pilot-marked attempts; unlimited historical attempts across and within flights (bounded storage/processing, no arbitrary count limit).

### Proposed contract responsibilities — research, not implementation authorization

- `TestCardDefinition` immutable published revision with referenced `CriterionTree`, eligibility policy, sensor-model revision, evidence requirements, durations, tolerances and review policy. Draft-to-published has explicit validation; changing a published card creates another revision.
- `CriterionTree` uses a safe typed expression tree, not custom executed code: numeric comparisons/ranges with canonical units, simultaneous ALL/ANY, ordered sequence, sustained duration with explicit max allowed data gap, repeated successes, manual observation requirements, and scoped condition windows. Validate tree depth/node count and surface unsupported input dependencies. Avoid misleading accuracy from sparsely sampled points.
- `Attempt` with stable ID, origin `PilotMarked` or `DetectedCandidate` (and confirmed/discarded state if adopted), flight ID, card and point revision/hash, optional science session IDs, bounded exact evidence/sample start/end reference, data quality, algorithm/model revision and human annotations. Model multiple attempts for one card/point in same flight and later flights without overwriting.
- Separate `AttemptEvaluation`, `TestPointAggregation`, `CardEvaluation` and `CampaignReview`; do not pass a card solely because a pilot manually asserted a period of Mach/altitude. Keep eligibility, factual condition evidence, modeled sensor results and reviewer approval independently visible.
- Pure local candidate extraction scans retained telemetry by indexed ranges with consistent gaps/clock semantics and deterministic matching; organization server receives **only selected submitted evidence**, performs server-side verification where evidence suffices, and distinguishes local preliminary estimates from official reviewed status.
- Unlimited attempts means no product cap on attempts, but practical disk use, computation time, resource quotas and pagination; no silent deletion or rewriting of historic attempts.

### Test and UX gates

1. A simple science card round-trips wizard/edit/save without exposing advanced complexity unnecessarily; a complex advanced card opened in guided builder must remain intact and clearly identified as containing advanced criteria.
2. AND/OR and ordered/repeated predicates support consistent unit conversion, missing/null inputs, source quality and fixed-duration sustained checks; invalid/missing points cannot manufacture a pass.
3. Automatic candidate intervals are deterministic over the same immutable telemetry; manual attempt markers and automatic candidates do not duplicate the same attempt inadvertently or overwrite each other.
4. A single sortie produces several independently scored cards and several attempts; a later sortie can add attempts without modifying earlier evidence.
5. Each retained failed, abandoned, insufficient and successful attempt is discoverable in reports and audit history, with bounded server data usage and pagination.
6. A documented modeled experimental-sensor criterion remains distinct from simulator-reported flight signals and human-attested avionics/handling.
7. Submissions are opt-in postflight, respect chosen data scope, and do not start live monitoring or disrupt recording.
8. Revised card criteria or sensor configurations produce new versions and explicit historical comparability warnings rather than retroactive pass/fail changes.

**Not decided:** Which candidate intervals are automatically selected, whether telemetry from a single instant may satisfy several cards, how much on-flight local test progress the pilot sees, and who can accept/waive partial criteria.
