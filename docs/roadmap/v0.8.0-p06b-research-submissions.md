## Guided workflow

Results Overview / Explore / Evidence and My Research open the same `openSubmissionBuilder`. The builder shows completed flight and selected local result identities/outcomes, the frozen organization/server/campaign/card revisions, exact item contents/size, policy, disclosure and browser-authorized scope/expiry. A selected Results product opens the supporting-reference chooser; it **does not select or share it automatically**. Draft saving grants no upload permission. Policy review transfers metadata only. Final consent still binds the exact manifest/payload hashes, original references, recipient, pilot, revisions and bytes.

Draft / ready for the pilot's approval review / approved queued / sending / held / retry / server received remain distinct. Ready for review is presentation, not a new server decision. Receipt is separate from the attributed scientific review. If a send request fails after confirmed approval, the dialog shows its known approved state and reads authoritative status; it cannot invent a receipt. Revoked/expired/wrong-organization grants, missing evidence and stale revisions retain the original guards. Approval and delivery remain loopback-only, paired/CSRF protected and browser-grant bound. Read/claim/live grants cannot upload.

## Narrow backward-compatible extension

The original transport does **not** carry complete P05 terrain/LiDAR products. P06 adds **version-2 documents containing explicitly selected version-1 supporting-product references**. This is intentionally reference-only: **no DEM/DSM cells, point XYZ/attributes, original binaries, profile arrays, screenshots or viewer caches are attached**. Source metadata may identify a research region and is disclosed before approval. The receiver can verify received bytes/reference integrity; it cannot verify an unshared original source merely from a supplied hash. Complete terrain/raster/model-product approval remains unsupported under the original scientific review policy.

Eligible contexts are original issued survey cards, or observation cards explicitly using the terrain instrument. Only the three existing durable artifact kinds are candidates: modeled corridor, source-backed elevation index and historical LiDAR index. Explicit selection reuses P05 `RequireCurrent`, original source binding/hash verification, input/geometry identity, source policy and analysis leases. No arbitrary viewer export, user path, URL fetch or artifact substitution is accepted. A source exclusion, permanent deletion, changed original/index/tile or unavailable dependency prevents re-materialization and holds delivery. Unknown dates, units and vertical references remain unknown.

Each reference retains product/geometry/input/algorithm identities, distinct scientific class, actual descriptive retained/missing counts, source/project/date/CRS/height-reference declarations, delivered dimension names, original-file ordinal/size/SHA, source-manifest SHA and exact tile identities. Managed filesystem paths and original file-name fields are omitted; source/project display names and citations are expressly disclosed. Historical LiDAR is explicitly historical; modeled geometry never becomes measured terrain. Reference records count **zero original observations** and are excluded from original requirement assessment/coverage credit. Local outcomes, acquisition counts, grades, review findings and campaign progress are unchanged. Unsupported scientific requirements remain unapprovable even after their metadata is received.

Bounds: at most **three** references, **256 tile identities** per product, **16 sources / 64 original file identities per source**, **256 KiB** per reference and the original **512 items / 2 MiB document** limit. Oversized references are refused rather than truncated. The existing mission queue stores selected IDs/hashes only; no attachment spool, numerical cache or new collaboration database is introduced. The existing server atomically stores only the separately approved received payload under its original quota and retention policy. Local deletion cannot erase an already expressly received remote copy.

The server advertises `supportingProductsVersion: 1` on the original scoped policy response. Missing/unknown capability prevents approval or delivery; no automatic downgrade is allowed. Users can explicitly remove reference attachments and review a new original-evidence-only selection. Version-1 payloads retain their original serialization/hashes; new null/default fields are omitted. The original client response codec tolerates the additive capability field. No database migration, changed grant, new upload endpoint or weakened size/rate limit is needed.

## Reviewer and accessibility

The shared `supportingProductEvidence` presentation is used in the pilot's exact item/final approval, manager inventory and reviewer received-evidence pane. It identifies reference-only content, original hashes and source limitations, distinguishes processing time from historical acquisition time, and uses Unknown without a flight/import-date fallback. Sources and exact references remain keyboard-readable; the original per-requirement decisions, evidence requests/replies, review history, role/campaign grants and audit chain remain in use. The viewer never retrieves the pilot's source files or turns local results into optimistic approvals.

New labels use English source catalog **version 15 / 639 messages**, retaining all five locales and four preview/fallback catalogs. Existing Auto/manual theme and display-unit/scientific-unit boundaries remain intact. Desktop/390px, light/dark, keyboard, verified 200% text, safe French preview fallback and zero axe violations are checked. Numerical source arrays are not silently rendered into DOM/storage or sent to external hosts.
