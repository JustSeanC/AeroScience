# AeroScience v0.8.0 — Revised Development Path (UX + Continuous Terrain & Real LiDAR Point Clouds)

**Owner-approved planning revision:** 2026-11-10. **Status:** design/scope contract, **not proof of implementation**. **Branch:** `develop/v0.8.0`. Preserve the accepted `develop/v0.7.0` tester workflow and forward-port verified fixes later. This file supplements `v0.8.0-implementation-plan.md`; do not edit P03b's active files merely to implement the terrain scope.

## Product commitments and boundaries

**Core release:** A dramatically simpler AeroScience dashboard and MSFS 2024 toolbar, guided beginner workflows, balanced density, automatic light/dark dashboard theme, and reviewed translations in `en-US`, `es-ES`, `fr-FR`, `de-DE`, `pt-BR`.

**Expanded terrain requirement:** User can run a flight with an active Terrain Scanner and view a visually **continuous airborne scanning strip** along scientifically eligible parts of their actual recorded path. Two **genuine source-backed** products:
1. **DEM/DSM surface mode:** original valid elevations from existing USGS 3DEP / compatible retained DEM and DSM sources, displayed in a derived, continuous-looking corridor and supported terrain profile.
2. **Real LiDAR point-cloud mode:** actual **historical LAS/LAZ/EPT/COPC returns** selected inside the same modeled flight corridor, rendered as inspectable 2D and 3D point clouds. Users may select ground / vegetation / buildings / intensity / return data only where supported by source attributes. **Real point cloud functionality is required in v0.8.0's expanded scope, not an explicitly deferred future enhancement.** If no genuine point-cloud source covers a flight, the DEM/DSM mode remains available and the gap/absence is made visible.

**Scientific truth:** AeroScience has not flown a real laser. Show accurate source points/elevations **revealed using the simulated aircraft's scan corridor**; do not relabel historical measurements as new returns fired in MSFS. Keep original saved in-flight 24×24 acquisitions immutable; derived post-flight corridor products must have a separate evidence/provenance class, source time, processing time, source quality and compatible horizontal/vertical datum. Derived coverage cannot fabricate original acquisitions or automatically increase collection yield, flight-test grading or organization scientific approval.

**Constraints:** no new internet access without explicit existing consent; no hidden permanent backup after user deletes a dataset; source reuse and storage/accounting required; no silent change to existing session/mission/automation/permission state machines. Preserve native MSFS Coherent GT/ES2017 compatibility and authenticated desktop/organization flows.

## Revised checkpoints

### P03b — Missions and guided setup (finish current work)

Explain science question, source requirements, expected observable result, aircraft/instrument compatibility, difficulty, and readiness. Fly Now prepares a mission but does not silently record/collect. Preserve advanced planning, waypoints, test cards, calibration, version/revision, source selection, multi-session/gates and existing controllers. **Forward-compatible interface:** terrain mission cards may later show “continuous scan + LiDAR point clouds, where available” but no claim of actual point-cloud readiness until P05c. Run focused checks and milestone CI.

### P04a — Current Flight dashboard

A single understandable screen with **Recording** and **Science Collection** as separate authoritative statuses; current objective, clear next action, concise instrument status, actual retained counts and warnings, map, observation, card attempts and manual controls. Add **nonblocking** source-aware spacing/coverage guidance (speed × time between accepted acquisitions vs modeled footprint; predicted is not measured coverage). Never infer science success from active recording.

### P04b — Native toolbar redesign

Responsive tabs **Flight / Science / Cards (when relevant)** plus reachable Map subview. Persistent connection, recording and science indicators; safe start/arm/pause/resume/end; concise collection/spacing/status; clear active session and card focus, no duplicate controller. Preserve build identity/revision checks, native move/resize and keyboard, original map/waypoint controls, small panel overflow behavior. Use genuine Windows/MSFS test gate separately.

### P05a — Continuous corridor geometry and evidence contracts

**Dedicated backend/science checkpoint, separate from P03 UI.** Reconstruct a swept scanner corridor from **archived exact telemetry, valid fresh position/AGL/attitude, selected scanner profile and collection-active session intervals**. Segment at pauses/stops/disconnects/stale packets/teleports/genuine missing trajectory data; don't bridge uncertain path with fake observations. Derive suitable bounded area windows for source querying and record geometry uncertainty/temporal fidelity. Support generic 30°×3° and versioned RIEGL 58°×16° separately, including turns. Create a derived `Continuous Terrain Survey` type with versioned source references, compatibility and provenance, **not** a new in-flight sensor/return stream.

### P05b — DEM/DSM post-flight completion and local-first processing

Populate corridor with genuine **compatible original raster elevation cells** from reused retained source data; preserve native source resolution, nodata and datum boundaries; never smooth across unsupported cells as observed. Offer **Review coverage → Prepare missing source → Download if explicitly approved → Process → Review**. Existing source reuse, per-source licensing/provenance, bounded download/preflight quotas, durable recoverable job receipts, offline states, cancellation, active-use protection, disk accounting and permanent deletion semantics remain authoritative. Do not automatically request an entire flight path or spend bandwidth without permission. A finished complete corridor is possible only where source/data and trajectory support exist; otherwise show partial/gaps.

### P05c — **Real LiDAR point-cloud discovery, import and corridor processing (REQUIRED)**

A high-value separate test-gated checkpoint:
- Discover public **USGS 3DEP LidarExplorer / EPT** projects by source footprint, dates, resolution/density, classification and CRS. Public EPT in `usgs-lidar-public` is streamable; the original raw LAZ `usgs-lidar` bucket is **Requester Pays**, must never be used automatically. Start with region/test project with known EPT availability, then generalize. Note public EPT coverage is not the same as complete raw 3DEP coverage.
- Import verified **local LAS/LAZ** source collections with original metadata and point attributes. Study direct **COPC LAZ** read support for spatially indexed local/remote source access; don't claim every LAS/LAZ can be read as COPC.
- Evaluate a bounded **PDAL EPT/COPC pipeline or equivalent proven decoder**, including license, runtime and installer support. Use spatially accelerated tile/chunk queries, then **clip points to the actual modeled swept corridor** (not merely its bounding box). Preserve XYZ, CRS/vertical datum, source measurement epoch, classification, return number/intensity and attributes **only if present**. For unsupported CRS, missing datum, corrupt/incomplete metadata or absent source, fail transparently; never guess numeric transforms.
- Chunk streaming/LOD, cache reuse and storage budget must bound entire-flight memory/network cost. New network downloads require separate informed permission. Persist resumable derived products and exact original source linkage. No new fake measured points, detector sample rates or yield credit.
- **Exit gate:** one genuine USGS EPT corridor and one imported LAS/LAZ (plus COPC path if supported) produce inspectable reproducible authentic source point records within the selected route; speed/altitude, pause and invalid path cases preserved. If supported native metadata/CRS cannot be verified, do not silently downgrade claims.

### P05d — Continuous terrain map, 3D cloud and Results/Library overhaul

Present default **Continuous Scan** with tabs/overlays **DEM surface**, **Actual historical LiDAR points (2D / 3D)**, **Original flight acquisitions**, **Flight path**, **Source-supported area / gaps**. Continuous-looking areas should only be colored where actual source data supports them. Optional class/height/intensity coloring and ground-only filter depend on real attributes. 3D viewer uses bounded progressive LOD, not millions of polygons/UI DOM nodes. Elevation-vs-ground-distance profile, terrain relief/hillshade and original native-cell inspection integrate issue **#29**. Results remain **Overview / Explore / Evidence** with original saved products and derived products clearly distinct. Unify **Scientific Library > Sources / Downloads / Storage**, including point-cloud project/coverage/download status and unambiguous deletion. Preserve all existing advanced scientific analysis and exports.

**Data exports:** source-true LAS/LAZ point subset export only if validated/native point precision and metadata are preserved; otherwise clearly labeled derived visualization format. Always distinguish historical source returns from simulated flight corridor and report source date/datum/quality. 2D/3D renderer must never mutate source evidence.

### P06 — Organizations and contextual help

Task-first assignments, campaigns, card attempts and reviews, consent for live monitoring, drafts and explicitly approved evidence submission. Include original and derived terrain deliverables as distinct evidence types only when approved/eligible. Contextual help explains real historical lidar returns versus DEM, modeled scan vs original acquisitions, and raw source versus after-flight processing.

### P07 — Five-language rollout and accessibility

Complete human-reviewed **English/Spanish/French/German/Brazilian Portuguese** for core dashboard, native toolbar, Windows companion, organization, scanner/data/cost/consent, error states, legend and point-cloud controls. Offline catalogs and English fallback for incomplete optional documentation; do not mark an unsupported locale full. Auto theme and display units remain independent of language; accessible keyboard, screen-reader, reduced motion, 390px dashboard/minimum native panel, 3D viewer usable alternative maps/tables and long-label tests.

### P08 — Release preparation / complete real acceptance

- Forward-port accepted v0.7 corrections into v0.8 with conflict review after P03b (not vice versa). Do not modify beta tester validator while it is being evaluated.
- Fast targeted tests per checkpoint, full CI for integration/release gates. Native installed x64 Windows+MSFS 2024 acceptance for toolbar, settings, recording/collection identity, panel drag/resize and locale glyphs.
- Geospatial integrity tests: real EPT, LAS/LAZ and DEM sources; horizontal/vertical transforms, missing datum/metadata, classification/intensity/return attributes, sample count and cutline exactness; no interpolation or unproved scanner returns; source dates explicit.
- Throughput/cost: CPU/RAM/storage/network bounded on realistic multi-leg long flights; interruption, resumability, partial/failed download, network disabled, no duplicate downloads, per-provider license and privacy; GPU/2D fallback for large point clouds, pause/cancel; deleting original files deletes data and invalidates derived dependent products as required.
- Scientific separation: historical lidar points in simulated swath vs in-flight original sample products vs source-backed DEM derived surface; derived products **not** converted into extra saved original acquisitions, mission success, science yield, or organization approval.
- User experience: ≥90% first-time success target in actual representative guided mission, processing, exploring point clouds and reviewing source quality; no release claims until observed.
- Release is gated on **real point cloud functionality** and readable continuous terrain visualization together, unless the owner explicitly revises scope. No invented launch date.

## Why this order

P03/P04 establish one coherent workflow and trustworthy in-flight controls. P05a–c create scientific/geospatial foundations **before** beautiful graphics. P05d integrates them into Results and Library. P06/P07 simplify participation and finish language coverage. P08 validates actual aircraft and data. Work on isolated experimental source-processing branches or separate worker modules only where the active P03b code and native flight controller remain untouched.
