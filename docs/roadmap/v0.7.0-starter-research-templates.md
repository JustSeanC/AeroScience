# AeroScience v0.7.0 — Worldwide Ready-to-Fly Personal Research Templates

**Status: proposed starter catalog, subject to owner confirmation; technical design research, not implemented or release accepted.** Created 2026-10-23 after Round 10. Related: [product decisions](v0.7.0-product-decisions.md), [technical research](v0.7.0-technical-research.md), [future science architecture](v0.7.0-future-science-architecture.md), [v0.9.0 science suites](v0.9.0-scope.md).

> **Reuse-first constraint:** The **existing mission planner** owns template editing; existing **preflight and in-flight automatic scientific data preparation** handles applicable sources; existing data library, science sessions, recorder and dashboard/toolbar supply the base workflow. v0.7.0 templates should be **configurations and integrations**, not replacements or independent data pipelines. New systems are allowed only when a current source audit demonstrates a missing capability. Current stable release v0.6.0; active implementation v0.7.0. See [mandatory reuse-first audit](v0.7.0-reuse-first-audit.md).

## Owner-confirmed requirements

AeroScience must support **independent pilots with no research-organization membership and no AeroScience-wide account**. Core starter templates should let an MSFS 2024 user **spawn anywhere in the world, select an experiment, activate cards and collect science, then view local reports**. No fixed airport, compulsory predownloaded satellite scene, region-only data collection, forced route-planning wizard, or server access for the basic research activity. Existing Universal and Realistic science modes remain, with flight recording independent of science sessions. The starter library is deliberately small but extensible.

Round 10 choices:
- Ship a **small curated core** with room for additional versioned templates.
- Independent pilots can **clone existing templates and author entirely new personal test cards from scratch**, using the same guided and advanced builder as organizational managers and the same validated evaluator.
- Permit **export/import of safe portable template definition files** and **proposing a personal template for publication by an organization** (subject to that organization's approval policy). Proposals share definitions, *not private mission history or source files*.
- **Personal research flights cannot retroactively count toward organization campaign test-card requirements.** Organizational card attempts must occur **after the pilot has claimed the published organization card**; don't auto-credit solo history or silently upload it. A solo pilot may use the same template later for a new, properly claimed experiment.

## Proposed six-template curated catalog — revised after Round 11; exact composition awaiting confirmation

Each template is **geographically portable** in its definition and mission-planning entrypoint. For scanning, a locally supported flight-level atmospheric-temperature variant can begin without a regional source, but **DEM-derived terrain and Landsat-derived surface-temperature outcomes require an actually available and compatible external dataset**. A missing source must never count as a successful terrain/thermal scan. Existing current source catalog in `develop/v0.6.0/src/AeroScience.Missions/ScienceCatalog.cs` has static templates General Research, Vertical Profile, Geographic Survey, Observation Flight, Cloud Structure Survey, Atmospheric Transect and instrument channels temperature, pressure, ambient wind and density from MSFS SimConnect; external-data thermal/multispectral/hyperspectral/DEM sources are different and not assumed globally available. Some below are new compositions/test-card definitions, **not existing shipped, functional templates**.

| ID | Starter template | Ready-anywhere goal | Base inputs | Honest local outcomes |
|---|---|---|---|---|
| CORE-01 | Scientific Observation Flight | Pick and fly: timestamped observations, point-of-interest annotations and optionally atmospheric samples | Local position/altitude/time and available reported atmospheric channels; pilot notes | Observations and flight path with data provenance; note categories and sample quality; no inferred phenomena |
| CORE-02 | Vertical Atmospheric Profile | Climb/descend to chosen attainable altitude bands and compare readings | MSFS local temperature, pressure, wind and density; altitude and time | Altitude-associated time series and profile graph; **no fabricated humidity/sonde readings** |
| CORE-03 | Atmospheric Transect | From current position, choose heading/distance or hand-drawn local route; compare atmospheres along path | Current lat/lon, time, available atmospheric channels and track samples | Location-indexed graph, observations and valid-segment comparisons; no claim of 3-D atmospheric field away from aircraft |
| CORE-04 | Flight-Regime Validation | Specify aircraft-appropriate speed/altitude/Mach (where supported) with durations/repeats; perform one/many test points | Recorded flight telemetry with units, quality and cadence, manual handling notes as needed | Pass/Fail/InsufficientEvidence per attempt; optional subjective report; not an aircraft certification |
| CORE-05 | Experimental Sensor Checkout | Configure a supported v0.7 modeled instrument template and test its simulated response in actual flown regimes | Supported model revision and genuinely available simulator inputs; explicit parameter/uncertainty/seed | Model-derived sensor response and limitations; source provenance distinct from actual simulator-reported observation; never invented physical hardware output |
| CORE-06 | **Terrain & Temperature Survey** (replaces the standalone Area Coverage starter) | Use existing mission planner's relative-location survey pattern; choose **DEM-based elevation**, **Landsat historical surface temperature**, or **simulator-reported ambient air temperature** as different sensor/source types | Local position/track/pattern; for terrain/thermal, compatible user-held or explicitly prepared regional external data; for ambient air temperature, supported local SimConnect readings | Source-qualified measurements and sampling/route coverage when available. Track coverage is not LiDAR coverage; DEM is **not aircraft LiDAR**, Landsat is **not onboard thermal imaging**, air temperature is **not surface temperature**. Missing DEM/thermal source => scanning objective unsupported/incomplete, never falsely passed |

**Regional data behavior:** for CORE-06 terrain and surface-thermal modes, compatible external imagery/DEM is a **required source for that selected objective**, though the **template, flight-track planning, local telemetry and air-temperature scan** are worldwide-accessible. Show coverage, source date, datum, estimated disk, quality and explicit acquisition consent. If absent, permit choosing an honestly labeled local-only alternative or an unsupported outcome, not a false scanner pass. Other starter templates have no mandatory region-specific external source. Always surface actual source coverage/quality and original observation dates. Some specialized v0.9.0 instruments are not available in v0.7.0 and must not be advertised as working now.

## Core user journey — no location picker forced

1. In MSFS anywhere, open local AeroScience dashboard or toolbar → **Personal Research → Templates**. No login, required internet, organization/server URL or regional remote-source download.
2. Choose a starter card (preview objective, estimated effort, required signals, compatibility, actual modeled-vs-measured labels). Offer both **Fly Now**, which loads defaults and performs a truthful readiness check, and **Customize**, which opens the **existing AeroScience mission planner**, prepopulated with instruments/payload profiles, current-position or free-flight patterns, test cards and analysis criteria. Do not duplicate the mission planner. “Fly Now” creates a **local instance** of a versioned definition, not an organization submission.
3. Detect aircraft's **current simulator position** when connected and relevant; generate local area/transect geometry relative to it without assuming North America or a preselected airport. Mission planning/flight recording and science start/pause/resume are separate controls; activating template cards must not turn on organizational streaming.
4. Perform a read-only readiness check: accessible SimConnect values, correct units, supported aircraft capability, modeled-sensor source availability and sampling interval. If prerequisites are unavailable, explain before launch or mark the affected objective unsupported, with user-selectable supported fallback only when scientifically justified. Don't silently reclassify impossible targets as passes.
5. Pilot explicitly enables one or several test cards; the in-sim toolbar shows locally computed progress and automatic distinct attempt records, alongside manual markers/observations. Existing flight recording remains unaffected by card activation.
6. End flight or science collection; review **private local detailed reports** with pass/fail/insufficient-evidence, objective/attempt timelines, charts, source/provenance, calibration/configuration revisions and recorded inputs. Support **comparisons across repeated experiments and multiple flights**; disclose changes in configuration, criteria, aircraft and data sources, and do not falsely merge incomparable data. Save a personal copy of the edited plan; export template separately from private research data.
7. Pilot can later connect to an organization and browse/claim a published campaign card; **previous standalone flights do not satisfy that card**. The pilot must claim first and conduct the organizational test afterward. Exporting/proposing a personal **template definition** does not export that personal history.

### Cross-cutting validation, interoperability and usability

- Versioned, typed template manifest independent of organization IDs/claims/review. `TemplateOrigin = BuiltIn | Personal | Imported | OrganizationPublished` metadata proposal; distinguish template **definition** from a runnable **local instance** and from submitted/approved **organization work**.
- The fixed `MissionTemplateKind` enum in current `ResearchModels.cs` should not be extended once per every new standalone/community template. Add additive compatible descriptors/references and migration gates, preserving old saved missions and mode semantics.
- Template import/export is **data only** (portable validated versioned JSON or equivalent); strict schema/source/unit/size/depth/version limits; content hashing, friendly preview, no executables/custom code, no arbitrary automatic URL fetches and no hidden system access. Import should preserve owner control and never overwrite saved templates without consent. No central public template store/cloud account required in v0.7.0.
- Publish/propose workflow creates a **copy** of the selected validated template definition in an organizational draft, checked against manager/reviewer approval policy. Explicitly exclude private local results, telemetry, original scientific source files, user location and personal scientific library.
- Unbounded personal template *count* limited only by actual storage and safe paginated indexing; repeated executions share immutable definition snapshot (copy-on-write) and refer to existing flight telemetry rather than duplicating entire recorded streams.
- Worldwide core onboarding and local-only **non-external-source scientific modes** should operate without regional datasets. Terrain scanner and surface-thermal variants are conditionally runnable only with scientifically valid source data; show source prerequisites and select ambient-temperature/flight-track alternatives explicitly. Compatible-source regional reuse and disk warnings apply; no hidden downloaded/cache copies after explicit deletion.
- Tests: start with an aircraft in North America, Europe and Oceania/southern hemisphere; **all six starter entrypoints** must open and create location-relative or free-flight plans regardless of geography. Scanner terrain/thermal variants must clearly reflect actual regional source coverage and missing-data states, while supported ambient air-temperature/track science can work locally. No hardcoded region or impossible parameters. Also test offline mode, missing instruments, small toolbar, auto attempts on multiple active cards, local privacy, file import warnings and no retroactive organization credit.

## Owner Round 11 — editable mission-planner templates and repeated-flight research (2026-10-23)

**Confirmed:** Keep approximately six starter experiments but **revise** their composition to include a meaningful **LiDAR-style elevation/terrain scanner or temperature scanning** research survey. Users choose **Fly Now or Customize**; the existing mission planner remains the full editor for instantiated template plans (routes, areas, patterns, instruments, test cards and scientific sessions), not a separate template-only planner. Routes may be generated relative to current location where helpful **or** be free-flight. Personal reports must be **detailed and compare repeated experiments across flights**. Exact six-template selection remains a proposal awaiting confirmation.

**Source boundaries:** `terrain-scanner` in develop/v0.6.0 is DEM-derived terrain elevation from USGS 3DEP / Copernicus DEM, **not airborne LiDAR returns**. `thermal-imager` is historical Landsat Collection 2 surface temperature, **not an onboard camera reading or ambient aircraft air temperature**. `ambient-temperature` is MSFS-reported aircraft air temperature. Their requirements should be visibly distinct. Base world-anywhere mission launching and offline sampling does not imply every region has cached or remotely accessible DEM/thermal scenes. Do not pass data-dependent scanner objectives without a genuine supporting source.

**Editing:** Built-in template definitions remain immutable and customizable copies inherit provenance/configuration/criteria. Selecting Customize should open the existing mission planner with prepopulated meaningful settings. Changing a future flight must not mutate frozen historic runs. Comparisons overlay compatible metrics over multiple sorties and show source/model version, aircraft, route/position/time, instrument settings, data gaps and qualification limits.

## Owner Round 12 — shared automatic source preparation and flexible comparison (2026-10-23)

**Confirmed:** Retain **one combined Terrain & Temperature Survey** starter with user-selectable scanning instruments. If a scientifically compatible terrain or historical land-surface temperature source is missing, use AeroScience's **existing** preflight source preparation to locate/download/select compatible data, which already supports **background preparation during flight** when permitted. The UI should describe these as existing capabilities and not propose a second manual download manager. The user has **not** required scientific data to be downloaded before every flight; source-prepared data may be reused and permitted background retrieval continues in flight. Missing or delayed source data must result in honest insufficient/unavailable science, not fake readings.

**Current code evidence:** `ScientificPlanData.Prepare` and progressive `Pump` in `ScientificPreparationWorker.cs` prepare selected plan cells; `ScientificFlightPrediction.Observe` queues near-future flight regions every 2 seconds when the flight and source instruments are active; `AutomaticScientificData.Prepare` reuses retained sources first and then retrieves via supported providers subject to independently consented scientific online access, background settings, limits, provider quality and storage. `RemoteAcquisition` samples validated retained grids, not new airborne LiDAR photons or true onboard thermal camera frames. No guaranteed worldwide scientific source availability; a globally portable template is **not** a guaranteed global data scene. Existing in-flight science transfer is **local scientific preparation**, not v0.7 organizational live streaming.

**Reports:** Provide both automatic suggestions for compatible previous research flights and an advanced/manual comparison builder. Display differing instruments, model revisions, data source mode, geography, temporal and spatial source coverage, calibration and quality. Avoid equating Landsat surface temperature with MSFS reported ambient air temperature.

**Exact starter roster remains provisional until screens are designed** (user's explicit Round 12 preference). Preserve editability through existing planner, Fly Now/Customize choice and worldwide local-only non-external starter capability.
