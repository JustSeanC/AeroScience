# AeroScience v0.7.0 — Worldwide Ready-to-Fly Personal Research Templates

**Status: proposed starter catalog, subject to owner confirmation; technical design research, not implemented or release accepted.** Created 2026-10-23 after Round 10. Related: [product decisions](v0.7.0-product-decisions.md), [technical research](v0.7.0-technical-research.md), [future science architecture](v0.7.0-future-science-architecture.md), [v0.9.0 science suites](v0.9.0-scope.md).

## Owner-confirmed requirements

AeroScience must support **independent pilots with no research-organization membership and no AeroScience-wide account**. Core starter templates should let an MSFS 2024 user **spawn anywhere in the world, select an experiment, activate cards and collect science, then view local reports**. No fixed airport, compulsory predownloaded satellite scene, region-only data collection, forced route-planning wizard, or server access for the basic research activity. Existing Universal and Realistic science modes remain, with flight recording independent of science sessions. The starter library is deliberately small but extensible.

Round 10 choices:
- Ship a **small curated core** with room for additional versioned templates.
- Independent pilots can **clone existing templates and author entirely new personal test cards from scratch**, using the same guided and advanced builder as organizational managers and the same validated evaluator.
- Permit **export/import of safe portable template definition files** and **proposing a personal template for publication by an organization** (subject to that organization's approval policy). Proposals share definitions, *not private mission history or source files*.
- **Personal research flights cannot retroactively count toward organization campaign test-card requirements.** Organizational card attempts must occur **after the pilot has claimed the published organization card**; don't auto-credit solo history or silently upload it. A solo pilot may use the same template later for a new, properly claimed experiment.

## Proposed six-template curated catalog — owner review needed

Each template is **geographically portable** and needs no regional external dataset to meet its *base* objectives. Existing current source catalog in `develop/v0.6.0/src/AeroScience.Missions/ScienceCatalog.cs` has static templates General Research, Vertical Profile, Geographic Survey, Observation Flight, Cloud Structure Survey, Atmospheric Transect and instrument channels temperature, pressure, ambient wind and density from MSFS SimConnect; external-data thermal/multispectral/hyperspectral/DEM sources are different and not assumed globally available. Some below are new compositions/test-card definitions, **not existing shipped, functional templates**.

| ID | Starter template | Ready-anywhere goal | Base inputs | Honest local outcomes |
|---|---|---|---|---|
| CORE-01 | Scientific Observation Flight | Pick and fly: timestamped observations, point-of-interest annotations and optionally atmospheric samples | Local position/altitude/time and available reported atmospheric channels; pilot notes | Observations and flight path with data provenance; note categories and sample quality; no inferred phenomena |
| CORE-02 | Vertical Atmospheric Profile | Climb/descend to chosen attainable altitude bands and compare readings | MSFS local temperature, pressure, wind and density; altitude and time | Altitude-associated time series and profile graph; **no fabricated humidity/sonde readings** |
| CORE-03 | Atmospheric Transect | From current position, choose heading/distance or hand-drawn local route; compare atmospheres along path | Current lat/lon, time, available atmospheric channels and track samples | Location-indexed graph, observations and valid-segment comparisons; no claim of 3-D atmospheric field away from aircraft |
| CORE-04 | Flight-Regime Validation | Specify aircraft-appropriate speed/altitude/Mach (where supported) with durations/repeats; perform one/many test points | Recorded flight telemetry with units, quality and cadence, manual handling notes as needed | Pass/Fail/InsufficientEvidence per attempt; optional subjective report; not an aircraft certification |
| CORE-05 | Experimental Sensor Checkout | Configure a supported v0.7 modeled instrument template and test its simulated response in actual flown regimes | Supported model revision and genuinely available simulator inputs; explicit parameter/uncertainty/seed | Model-derived sensor response and limitations; source provenance distinct from actual simulator-reported observation; never invented physical hardware output |
| CORE-06 | Area Coverage Survey | Define a box/circle/local transect generated relative to current location; fly lines or a simple pattern, mark coverage | Local geo track, time, planned region/route, optionally recorded sampling timestamps | **Flight-track/observation-route coverage only** unless an actual configured compatible sensor footprint exists. No claim of newly photographed ground or global external terrain/imagery data |

**Optional enrichment, not initial blocking requirements:** regional historical external imagery, terrain/DEM, remote datasets, more scientific instruments, richer plots or manually configured area boundaries. Always surface actual source coverage/quality and original observation dates. Some specialized v0.9.0 instruments are not available in v0.7.0 and must not be advertised as working now.

## Core user journey — no location picker forced

1. In MSFS anywhere, open local AeroScience dashboard or toolbar → **Personal Research → Templates**. No login, required internet, organization/server URL or regional remote-source download.
2. Choose a starter card (preview objective, estimated effort, required signals, compatibility, actual modeled-vs-measured labels). Offer **Fly Now** with sensible, editable nearby/local defaults; optionally **Customize** in guided/advanced editor. “Fly Now” creates a **local instance** of a versioned definition, not an organization submission.
3. Detect aircraft's **current simulator position** when connected and relevant; generate local area/transect geometry relative to it without assuming North America or a preselected airport. Mission planning/flight recording and science start/pause/resume are separate controls; activating template cards must not turn on organizational streaming.
4. Perform a read-only readiness check: accessible SimConnect values, correct units, supported aircraft capability, modeled-sensor source availability and sampling interval. If prerequisites are unavailable, explain before launch or mark the affected objective unsupported, with user-selectable supported fallback only when scientifically justified. Don't silently reclassify impossible targets as passes.
5. Pilot explicitly enables one or several test cards; the in-sim toolbar shows locally computed progress and automatic distinct attempt records, alongside manual markers/observations. Existing flight recording remains unaffected by card activation.
6. End flight or science collection; review **private local** pass/fail/insufficient-evidence, plots, provenance, attempt history and original inputs; optionally save/copy template configuration, export a safe template or make local report.
7. Pilot can later connect to an organization and browse/claim a published campaign card; **previous standalone flights do not satisfy that card**. The pilot must claim first and conduct the organizational test afterward. Exporting/proposing a personal **template definition** does not export that personal history.

### Cross-cutting validation, interoperability and usability

- Versioned, typed template manifest independent of organization IDs/claims/review. `TemplateOrigin = BuiltIn | Personal | Imported | OrganizationPublished` metadata proposal; distinguish template **definition** from a runnable **local instance** and from submitted/approved **organization work**.
- The fixed `MissionTemplateKind` enum in current `ResearchModels.cs` should not be extended once per every new standalone/community template. Add additive compatible descriptors/references and migration gates, preserving old saved missions and mode semantics.
- Template import/export is **data only** (portable validated versioned JSON or equivalent); strict schema/source/unit/size/depth/version limits; content hashing, friendly preview, no executables/custom code, no arbitrary automatic URL fetches and no hidden system access. Import should preserve owner control and never overwrite saved templates without consent. No central public template store/cloud account required in v0.7.0.
- Publish/propose workflow creates a **copy** of the selected validated template definition in an organizational draft, checked against manager/reviewer approval policy. Explicitly exclude private local results, telemetry, original scientific source files, user location and personal scientific library.
- Unbounded personal template *count* limited only by actual storage and safe paginated indexing; repeated executions share immutable definition snapshot (copy-on-write) and refer to existing flight telemetry rather than duplicating entire recorded streams.
- Base functionality should operate with no external scientific dataset. Later optional rich-data acquisition uses compatible-source regional reuse and space warnings; no hidden downloaded/cache copies after explicit deletion.
- Tests: start with an aircraft at several widely separated locations (North America, Europe, Oceania/southern hemisphere); **all six starter cards** should remain possible when their genuine sensor/aircraft prerequisites are available, with no reliance on hardcoded region or impossible parameters. Also test offline mode, missing instruments, small toolbar, auto attempts on multiple active cards, local privacy, file import warnings and no retroactive organization credit.
