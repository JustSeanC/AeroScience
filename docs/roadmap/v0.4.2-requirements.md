# AeroScience v0.4.2 — Comprehensive UI/UX Excellence Release

## Professional Research Workstation Redesign, Scientific Visualization, Accessibility & Usability

**Repository:** https://github.com/JustSeanC/AeroScience

**Target version:** v0.4.2

**Starting point:** Completed v0.4.1 development source

**Primary objective:** Raise AeroScience's overall user experience from approximately 5.9/10 toward a genuinely validated **9/10–10/10 professional standard**.

**Assignment:** Audit, design, implement, test, document and prepare the complete UI/UX improvement release.

---

# 1. Vision and Release Philosophy

AeroScience is a free, open-source, local-first scientific research companion for Microsoft Flight Simulator 2024.

It combines simulator telemetry, modeled scientific instruments, real-world historical Earth-observation datasets, mission recording, geographic sampling, and scientific analysis.

Its intended users include flight-simulation enthusiasts, aviation researchers, educators, scientific hobbyists and technically advanced users.

AeroScience should feel like a **professional airborne scientific research workstation**, not a developer dashboard or collection of loosely connected utilities.

v0.4.1 established much of the necessary scientific infrastructure and introduced dedicated workspaces. However, independent UI/UX inspection identified significant shortcomings in:

- Information hierarchy.
- Scientific visualization.
- Usability and discoverability.
- Excessive technical text.
- Dashboard organization.
- Scientific comparison interfaces.
- Responsive design.
- Tablet navigation.
- Accessibility.
- Download Activity presentation.
- Visual consistency.
- Scientific interpretation.

**v0.4.2 must address these problems comprehensively.**

The central user experience should be:

**Plan → Prepare → Fly → Review → Understand → Compare → Export**

A user should complete a research mission, open their scientific results, immediately see the most useful map or chart, understand what was measured, examine its quality, and compare it with other research.

That process should not require familiarity with software internals, GIS terminology, database structure or scientific download mechanisms.

## Defining success

The goal is not to make AeroScience look impressive in screenshots while leaving awkward workflows underneath.

The goal is to make it:

- Intuitive.
- Visually polished.
- Scientifically trustworthy.
- Consistent.
- Fast and responsive.
- Accessible.
- Efficient for frequent users.
- Understandable to first-time users.
- Suitable for complex scientific data.

**A working button is not sufficient. A feature is complete when users can discover, understand and use it successfully.**

# 3. Objective Evaluation Standards

Use these established professional references as the design and evaluation foundation:

### ISO 9241-11 and ISO 9241-210

Evaluate usability in terms of effectiveness, efficiency, user satisfaction and human-centered design.

### Nielsen's 10 Usability Heuristics

Emphasize:

- Visibility of system status.
- Match between system language and user language.
- User control and freedom.
- Consistency and standards.
- Error prevention.
- Recognition rather than recall.
- Flexibility and efficiency.
- Aesthetic and minimalist design.
- Helpful error recognition and recovery.
- Discoverable help.

### WCAG 2.2 Level AA

Treat WCAG 2.2 AA as the accessibility target for the browser interface.

Include keyboard navigation, focus visibility, sufficient contrast, semantic relationships, touch targets, labels, status announcements and nonvisual alternatives.

### Microsoft Fluent 2 and established desktop UX conventions

Use established practices for:

- Layout.
- Visual hierarchy.
- Spacing.
- Responsive behavior.
- Navigation.
- Dialogs.
- Control states.
- Typography.
- Forms.
- Desktop productivity interfaces.

AeroScience does not need to imitate Fluent's visual appearance, but its controls should meet comparable professional expectations.

### Professional scientific visualization

Use established practices for:

- Units and legends.
- Meaningful geographic scales.
- Consistent data color ranges.
- Scientific uncertainty.
- Missing-data representation.
- Source provenance.
- Comparable measurements.
- Chart selection.
- Nonmisleading visual encoding.

### Progressive disclosure

Show the information most useful to the current task first.

Advanced scientific details must remain accessible without overwhelming ordinary workflows.

# 4. AeroScience UI/UX Scoring Rubric

Use this exact weighted assessment.

| Category | Weight |
|---|---:|
| Navigation and workflow design | 20% |
| Scientific visualization and interpretation | 25% |
| Visual design and consistency | 15% |
| Status, feedback and error handling | 15% |
| Accessibility and responsive layouts | 10% |
| Performance and reliability | 10% |
| Discoverability and help | 5% |

**Previous independent preliminary evaluation: approximately 5.9/10.**

This is a reference point, not a guaranteed baseline measured through formal usability testing.

### Evaluation levels

**Standard — 5–6/10**

The application works and the essential features are available, but users experience confusion, unnecessary complexity, awkward layouts or inconsistent information.

**Good — 7–8/10**

The application is visually consistent, efficient and understandable. Common operations are straightforward, with clear feedback and useful defaults.

**Excellent — 9/10**

The application is polished, coherent and intuitive. Users can complete real research workflows with minimal confusion. Complex scientific results are easy to explore, compare and understand. Accessibility and responsiveness are demonstrably strong.

**Exceptional — 10/10**

The experience approaches best-in-class professional software, with exceptionally strong usability evidence, meaningful scientific visualization, accessible interactions, robust performance and very few material usability concerns.

A 10/10 score should be treated as aspirational, not assumed.

### Critical scoring rule

**Do not assign AeroScience a 9/10 or 10/10 merely because implementation tasks and automated tests pass.**

A high score requires evidence from:

- Actual completed user workflows.
- Realistic scientific datasets.
- Visual inspection.
- Accessibility testing.
- Desktop and tablet layouts.
- Error recovery.
- Performance measurements.
- Independent or representative user feedback.

Scientific correctness, data-integrity defects and serious accessibility failures must be independent release concerns even when the weighted score appears high.

The objective is to *earn* the score, not engineer the evaluation to produce it.

# 5. Design System and Application-Wide Visual Refinement

Implement a cohesive, maintainable visual design system.

Preserve the recognizable AeroScience identity and dark scientific-workstation aesthetic unless a specific change materially improves usability.

Do not simply redesign colors.

## Typography

Create clear, reusable typography tokens for:

- Page titles.
- Section headings.
- Instrument headings.
- Body text.
- Metadata.
- Labels.
- Scientific values.
- Numerical units.
- Captions.
- Error messages.
- Supporting text.

The current CSS sometimes reduces labels to **7–8 pixels** at responsive breakpoints. Eliminate those extremely small text styles.

Use readable, scalable text. Prefer approximately 14–16px or larger for ordinary interface content, with appropriately sized secondary labels rather than miniature text.

Support browser zoom and operating-system scaling without clipping important controls.

## Spacing and composition

Standardize:

- Page margins.
- Grid gaps.
- Card padding.
- Form spacing.
- Vertical rhythm.
- Section spacing.
- Panel nesting.
- Button grouping.
- Dialog layout.
- Map toolbars.

Avoid arbitrary spacing differences between screens.

Prioritize generous, purposeful whitespace rather than empty space that separates related actions.

## Buttons and controls

Establish consistent visual priority:

**Primary:** The main next action.

**Secondary:** Related useful actions.

**Tertiary:** Low-frequency or optional actions.

**Destructive:** Clearly differentiated operations that remove or permanently alter data.

A single workflow should generally have one clearly identifiable primary action.

Avoid rows of six or eight visually equivalent buttons.

Use concise, action-oriented names.

## Consistent states

Design reusable treatments for:

- Ready.
- Preparing.
- Downloading.
- Processing.
- Paused.
- Partial.
- Offline.
- Unavailable.
- Failed.
- Completed.
- Provisional.

Do not communicate state through color alone.

Use readable labels, icons and contextual explanations.

## Component architecture

Inspect and refactor the current frontend where necessary.

Existing implementation includes:

- `src/AeroScience.Engine/wwwroot/app.css`
- `src/AeroScience.Engine/wwwroot/app.js`
- `src/AeroScience.Engine/wwwroot/science-workspace.js`
- `src/AeroScience.Engine/wwwroot/science-display.js`
- `src/AeroScience.Engine/wwwroot/mission-selection.js`

Avoid adding an entirely new UI framework unless there is a compelling, documented technical justification.

Prefer reusable, accessible components integrated with AeroScience's existing frontend architecture.

# 6. Science Map — Flagship UX Priority

**This is the highest-priority page in v0.4.2.**

The Science Map should become AeroScience's most compelling scientific experience.

A user should open it and see meaningful scientific geographic data immediately, assuming valid data exists.

The map should occupy the majority of the available workspace.

## Current shortcomings

The v0.4.1 interface exposes several separate technical actions:

- Load More Acquired Science.
- Apply Filters / Fit Data.
- Search Visible Region.
- Fit Mission Track.
- Build Native Composite.
- Load Atmospheric Positions.

Although these actions have different internal meanings, ordinary users should not need to understand that processing workflow simply to visualize their science.

The existing map can show native geographic cells but requires additional interaction to build certain composite-image overlays.

## Required v0.4.2 behavior

### Automatic useful presentation

When opening the Science Map:

1. Determine the selected mission or mission scope.
2. Identify available scientific instruments and compatible measurements.
3. Choose a sensible initial view.
4. Load the available valid geographic results automatically.
5. Display the data with an appropriate scientific color scale or imagery representation.
6. Fit the map to the relevant scientific extent.
7. Show a concise data-quality summary.

Do not require users to manually press several loading and processing buttons to see the primary results.

### Default sensor visualization

Use appropriate starting presentations:

- Terrain: elevation map and suitable elevation legend.
- Thermal: temperature imagery with actual units.
- Multispectral: natural-color or supported vegetation-index layer.
- Hyperspectral: scientifically appropriate selected bands, with wavelength and provenance.
- Atmosphere: recorded geographic observations, tracks or profiles with the selected measured quantity.

Provide useful instrument-specific defaults.

These should be based on actual available source data.

### Map layout

Use a professional structure:

**Main map**
- Large geographic canvas.
- Actual scientific data.
- Route/track overlays when appropriate.
- Inspection and navigation controls.

**Compact layer panel**
- Mission selection.
- Instrument selection.
- Scientific measurement/layer selection.
- Layer visibility.
- Opacity.
- Legend.

**Contextual inspector**
- Selected location.
- Scientific value.
- Units.
- Instrument.
- Flight timestamp.
- Historical source observation date.
- Quality.
- Relevant source identity.
- Link to detailed analysis.

Avoid large permanent blocks of technical methodology below the map.

### Simplify user actions

Replace multiple technical workflow actions with a smaller, coherent set of meaningful controls.

Examples:

- Choose Science Layer.
- Choose Mission.
- Fit Data.
- Inspect Value.
- Show Flight Track.
- Compare.
- Export.

Move advanced processing, geographic paging, source diagnostics and manual composite generation into Advanced controls where appropriate.

Automatic processing must remain bounded and must never trigger surprise external downloads or consume unapproved network allowances.

### Combined geographic science imagery

Where compatible valid native scientific samples exist, show them coherently on the same map.

Use the existing verified native-grid compositing and raster infrastructure.

Do not blend:

- Incompatible units.
- Different wavelengths without an appropriate composite method.
- Incompatible geographic references.
- Incompatible vertical datums.
- Invalid pixels.
- Unrelated historical observation dates without a clear representation.

A scientifically valid mosaic may contain transparent holes where observations are missing.

That's preferable to inventing continuous coverage.

### Specific source-level fixes

Inspect `science-workspace.js` and correct these problems:

**Opacity control**

The current slider updates Leaflet geographic vector-layer opacity but does not consistently update generated composite-image overlays.

All visible scientific layers to which the control applies must respond appropriately.

**Coverage and acquisition counters**

Acquisition totals and valid-cell counts currently use different accumulation semantics during pagination.

Ensure counts remain accurate and understandable as more scientific data loads.

Explain whether a count represents:

- Acquisitions.
- Valid geographic cells.
- Measurement values.
- Unique sampled locations.
- Geographic coverage.

Do not present incompatible counts as equivalent.

**Constant-value color scale**

When minimum and maximum values are identical, do not imply a meaningful numeric gradient.

Display a constant-value legend or appropriately labeled single-color scale.

**Loading progress**

Distinguish:

- Loading saved scientific records.
- Rendering existing geographic data.
- Generating a derived visualization.
- Downloading external scientific data.

Show meaningful progress without exposing internal task mechanics.

**Map scale and legends**

Provide clear, usable numerical legends with units and source context.

Do not rely solely on color gradients or explanatory text.

### Performance

Support:

- Multiple missions.
- Large geographic collections.
- Progressive loading.
- Viewport-aware queries.
- Bounded client memory.
- Cancellation of stale requests.
- Responsive map navigation.
- Efficient layer switching.

Avoid loading every raw measurement into the browser simply to display a regional summary.

# 7. Scientific Comparison — Professional Analysis Experience

The current Compare interface provides synchronized maps and correct scientific compatibility checks, but it remains too technical and visually underdeveloped.

Make Compare a genuinely useful research-analysis workspace.

## Desired layout

Default to two primary comparison panels:

**Dataset A** | **Dataset B**

Each should display:

- Mission name.
- Instrument.
- Measurement type.
- Acquisition date.
- Historical source date.
- Map or chart.
- Scientific legend.
- Data-quality summary.

Allow additional comparisons when useful, but do not make an eight-column layout the standard user experience.

## Required improvements

### Easy dataset selection

Let users compare:

- Different missions.
- Different instruments.
- Repeated flight passes.
- Different acquisition periods.
- Different geographic regions.
- Compatible scientific datasets.

Filter available choices based on context.

Use understandable labels rather than raw acquisition IDs.

### Synchronized maps

Preserve synchronized geography and zoom.

Make it easy to inspect the same location in two datasets.

A user selecting a geographic point should be able to inspect corresponding data from both sources where available.

### Shared and independent scales

**Correct the current color-scale problem.**

For genuinely comparable quantities, provide an optional common numeric scale so the same color means the same value.

For incompatible quantities, retain independent scales with clearly visible separate legends.

Do not show visually misleading differences simply because each map independently normalized its data.

### Difference visualization

When scientifically valid, provide:

- Numeric delta.
- Difference map.
- Matched-position comparison.
- Shared geographic overlap.
- Descriptive statistics.
- Data-quality differences.

If a numeric difference cannot be justified, explain the reason in ordinary language.

Do not generate fake comparisons for incompatible units or data.

### Charts

Use meaningful charting where appropriate:

- Temperature versus altitude.
- Wind speed versus position.
- Atmospheric profile comparisons.
- Elevation profiles.
- Repeated-transect comparisons.
- Sampling completeness.
- Valid geographic coverage.

### Specific interaction defect

The current comparison implementation appears to construct the **Atmospheric / pass analysis** link using the originally selected mission ID.

Changing the selected mission can leave that link pointing to the wrong mission.

Investigate and correct this.

Test that every mission-dependent action follows the current selection.

### Comparison summary

Provide a concise, scientifically defensible summary:

- What was compared.
- Whether the data are compatible.
- How much common valid coverage exists.
- What the values indicate.
- What remains unknown.
- Important scientific limitations.

Keep raw source IDs and detailed comparison methodology accessible separately.

The primary scientific result should appear before verbose supporting explanations.

Use:

- Maps.
- Charts.
- Profiles.
- Scientific images.
- Clear statistics.
- Compact instrument result cards.

### What the data means

Implement concise plain-language interpretation grounded exclusively in the stored measurements.

Examples of appropriate interpretation types:

- An observed trend with actual numerical support.
- A meaningful minimum and maximum.
- Variation across a route.
- Variation across altitude.
- Missing or rejected observations.
- Source quality limitations.
- Why one instrument generated more values than another.

1. Readable instrument name.
2. Main scientific visualization.
3. Key measurements.
4. Data quality.
5. Short interpretation.

### Empty and partial results

A mission without valid measurements should have a useful explanation and next action.

A partially recovered mission should clearly indicate what is available and what remains pending.

Do not make incomplete scientific processing look like complete results.

# 15. Accessibility — WCAG 2.2 AA Target

Perform a genuine accessibility audit.

Do not rely solely on the presence of ARIA labels.

## Required areas

### Keyboard operation

All essential functionality must be keyboard-accessible, including:

- Navigation.
- Mission selection.
- Filters.
- Dialogs.
- Charts.
- Scientific value inspection.
- Comparisons.
- Advanced details.
- Exports.

### Geographic map accessibility

Leaflet's mouse-click inspection must not be the only way to inspect recorded scientific data.

Provide an alternative accessible interface such as:

- Keyboard-navigable observation list.
- Searchable scientific sample table.
- Selected-region details.
- Synchronized non-map inspection controls.

This interface must expose the same meaningful scientific values, units and source details.

### Focus

Ensure:

- Visible focus indicators.
- Logical tab order.
- Focus management when opening/closing dialogs.
- Restored focus after closing dialogs.
- Correct focus after page navigation.
- No inaccessible hidden controls.

### Contrast and text

Target WCAG 2.2 AA:

- Normal-text contrast at least 4.5:1.
- Large-text contrast at least 3:1.
- Nontext interface/graphical contrast at least 3:1 where applicable.
- Pointer-target requirements, using larger comfortable targets where feasible.
- Sufficient reflow at supported viewport sizes and zoom.

### Charts

Provide:

- Accessible chart names.
- Text summaries.
- Units.
- Keyboard-accessible alternatives.
- Downloadable or viewable tabular data.

Do not make understanding a scientific result dependent solely on visual color interpretation.

### Dynamic status

Appropriately announce:

- Download completion.
- Recording errors.
- Failed actions.
- Science-processing state transitions.
- Other important changes.

Avoid announcing frequent low-value telemetry or polling updates repeatedly to assistive technology.

### Motion
