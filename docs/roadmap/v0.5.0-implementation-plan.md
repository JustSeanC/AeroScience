# v0.5.0 phased development and PR plan

**Planning only.** Only `develop/v0.5.0` and `feature/v0.5.0-architecture` are established
by this task. The branches below are proposed future work, not feature implementations
or acceptance passes. Use the [scope](v0.5.0-scope.md),
[contracts](v0.5.0-architecture.md) and [acceptance matrix](v0.5.0-acceptance.md).

## Branch and review workflow

- Planning base: `main` at `8f510f02f4d9b41fba4e55fefa950b82e48c132d`, including
  v0.4.2 fixes and branding history. `develop/v0.5.0` starts at that exact commit.
- This documentation work uses `feature/v0.5.0-architecture`; open a **draft PR into
  `develop/v0.5.0`**, leave it unmerged. No source/test/version/installer changes.
- Create each future branch from the latest reviewed `develop/v0.5.0`; target that
  integration branch. Where stacked PRs are useful, state the dependency and retarget
  to development after the prerequisite merges. Never force-overwrite shared work.
- Review v0.4.2 QA corrections on `main` independently. Merge them forward into
  development with their original history, resolve conflicts and rerun affected checks.
  Do not bring unfinished v0.5.0 work back into `main` to obtain a QA fix.
- Keep source/contract, migration and scientific review explicit in each PR. No automatic
  merges or issue closure; record implemented versus unverified acceptance separately.
  A feature requiring physical MSFS/device results stays acceptance-pending until those exist.
- Recommend required review/status checks and no force-pushes for shared branches; this
  task does not change repository protection settings. If checks are required for a
  roadmap-only PR, arrange documentation review/status rather than modifying baseline CI
  or claiming a skipped test job passed. Current CI intentionally ignores `docs/roadmap/**`.

  and retain the QA file/path freeze. Do not implement cleanup in this architecture PR.
- After P01/P02, calibration/operating work (P03/P04) and catalog work (P10) can proceed

  identities rather than implementing calibration rules.
- After catalog contracts stabilize, NASA discovery P13 can proceed alongside Library
  jobs/UI P11/P12. P14 needs shared job/security boundaries, not a new downloader.
- Classic and NG adapters P15/P16 can be separate parallel PRs after common access and
  import contracts pass; validate genuine family-specific data independently.
- P17/P18 can develop against reviewed backend contracts in parallel, with actual integration
  tests before merge. They must not drive the state machine from UI polling or use a
  mocked score as completion evidence.
- Assign one owner to each schema-version allocation, shared DTO/API change and scheduler
  invariant. Parallel migrations must agree the next available version and forward-compatible
  application order; do not land two different meanings for schema 8/3.

## Per-PR evidence and integration gates

Each PR description should state the requirement/acceptance IDs it implements, exact
source baseline, changed ownership/API/schema, migration/legacy behavior, test commands
and actual results, genuine data identity/provenance where applicable, performance bounds,
and remaining installed verification. Use Pending/Blocked with a reason; compilation or
mocked provider responses are never hardware or genuine-source evidence.

1. Add meaningful unit/integration tests alongside feature code; keep existing v0.4.2
   behavioral assertions and canonical fixtures. Retain SDK ABI, offline assets, package,
   consent/security, recording recovery and independent storage deletion tests.
2. Re-run affected .NET/browser/helper checks per feature. Full Linux and Windows technical
   CI is required at integration; current roadmap-only work does not rerun all hardware-
   independent suites merely to relabel unchanged baseline behavior.
3. Validate numeric/provider changes with actual retained/downloaded originals and independent
   readers, retaining full provenance and separate synthetic-flight labels. Source-bound
   scientific evidence must be refreshed only for the exact changed implementation.
4. Run representative installed Windows/MSFS/offline/upgrade/iPad/Quest flights and collect
   logs/results against the exact candidate bytes. Open issues/acceptance entries remain
   open where these tests cannot be performed; no blanket close-on-build-success.
5. Only a later integration PR may propose merging `develop/v0.5.0` into `main`, after
   acceptance and owner review. Installer publication is a separate explicit action, using
   the existing official SDK/runtime authorization/checksum process. No self-hosted runner
   is required by this plan; retain manual Windows maintainer builds.

The first unresolved tasks are research/contract decisions in
[the decision register](v0.5.0-decisions.md), not reasons to stall the documentation PR.
