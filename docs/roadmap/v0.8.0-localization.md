# AeroScience v0.8.0 — Internationalization & Localization Contract

**Status:** design specification, not implemented or translated. Applies to dashboard, MSFS 2024 toolbar, Windows companion, organization portal, setup, help and errors.

## Scope and release languages

Initial candidate locales: `en-US` (canonical source/fallback), `es-ES`, `fr-FR`, `de-DE`, `pt-BR`. Additional later candidates: `ja-JP`, `zh-CN`, `it-IT`, `pl-PL`. Advertise a locale as fully supported only when critical commands, consent, user help and normal flows are reviewed. A partial beta locale must be explicitly labeled and use deterministic English fallback.

Use native language labels (English, Español, Français, Deutsch, Português (Brasil)), not national flags to represent languages. Avoid conflating translation language with nationality, measurement units, simulator locale or an organization membership.

## Cross-surface policy

- Local dashboard and MSFS toolbar use the same effective language preference when connected to a companion. Save it in the existing user settings system without changing mission/science artifacts.
- Provide a native Windows Setup/Settings picker and a browser Settings picker. If a tool lacks native dynamic reload, show an explicit restart/reopen notice; do not imply that it updated instantaneously.
- For organization browser portals, use signed-in member preference when available; otherwise browser preference; otherwise the product fallback. A local preference must not leak to or overwrite other organization users.
- Do not request a cloud account to select language or render local strings. Bundled translations available offline.
- Preserve original scientific identity, source labels in data files, recorded UTC, scientific numeric precision, acquisition dates, units, hashes and enum/API values. Translate **presentation**, not evidence or serialized stable contracts.
- Keep independent settings for displayed aviation/scientific units, time zone, coordinate style and numerical format. Display conversions must not mutate original data.
- Every scientific result must still distinguish simulator-reported vs historical dataset vs modeled vs pilot-reported vs unavailable vs synthetic. Translations may not change those claims.

## Catalog and API requirements

Propose a shared translation-key schema under a common contract such as `i18n/locales/en-US.json` and peer locale files, consumed by separate browser, toolbar and Windows adapters. Verify packaging and routing before choosing exact path. Avoid depending on a browser module import or `Intl` feature that is unsupported in Coherent GT / locked native simulator runtime. Use a tested ES2017-compatible fallback for missing internationalization functionality and a .NET-compatible resource wrapper for native dialogs.

- Keys are semantically scoped: `nav.home`, `mission.startRecording`, `science.startCollection`, `science.paused`, `results.savedObservations`, `consent.liveShare.description`.
- Use **parameterized messages** for values; never construct a translated phrase by concatenating English fragments. E.g. `science.observations.saved = "{count} saved observations"` with plural handling appropriate to the target language and verified runtime.
- Keep HTML/text content separate. Render translated content safely as text by default; no untrusted HTML injection, and no raw user-supplied interpolated markup.
- Include translation context/comment for ambiguous terms (`recording` vs `collection`, `arm` vs `start`, `card focus` vs `activate`, `submission` vs `approval`, `coverage` vs `flight path`).
- Implement explicit `language -> en-US -> visible source-key` fallback for development, with missing-key logging only in development/QA. A production missing key must resolve to a human-readable English fallback, never an empty safety warning.
- Version locale catalogs with application code; include a static consistency checker for missing/extra keys, unsupported placeholders, unreachable strings, invalid plural cases and unused ids.
- Persist locale across restart/offline use; check browser cache/version policy so a stale toolbar does not silently rely on a newer catalog key set.

## Priority order

1. **Safety/authorization:** delete, mission end, upload/share, source/operating invalid, offline/stale state, failed write/consent; human-reviewed before enabling locale as supported.
2. **Core workflow:** onboarding, Home, experiment, readiness, start/pause/resume/end, toolbar states, source status and beginner results.
3. **Organization:** invitations, live sharing consent, submissions, review and roles.
4. **Advanced scientific screens:** instrument settings, original evidence descriptions, importers, QA/detail/help, storage and diagnostics.
5. **Non-core guides:** longer examples and methodology references. These may visibly fall back to English during preview, never be represented as complete.

## Layout/font/accessibility policy

- Plan for expansion (~30–50% in stress testing) and wrapping, even in compact native MSFS toolbar. Primary status and dangerous buttons must remain visible and distinguishable in narrow panels.
- Support Unicode accents, punctuation and number glyphs; add Japanese/CJK font fallback only after inspecting licensing, bundle cost and Coherent/native rendering. Never package unlicensed font assets.
- Respect DOM `lang`, translated accessible names/alerts, keyboard focus, logical order, non-color status. Use direction metadata even though the initial locales are LTR; do not hard-code left/right into conceptual UI components.
- Protect proper names, airport codes, aircraft registration, units/standards, source names, exact files/keys and coordinates from inappropriate machine translation.
- Format dates/times/numbers via supported locale APIs, but maintain exact retained UTC and units in detailed evidence. Make date source distinct from display date and simulator time.
- Test all critical notifications at 390 px browser, the minimum supported MSFS panel width, high zoom, and large text sizes.

## Translation quality and workflow

- English source string owner provides description, placeholders and screenshots/context.
- First pass translation can be assisted, but review critical consent/operating/scientific terminology by fluent speakers before full locale release.
- Run key/placeholder/lint tests; simulate pseudo-locale and intentionally long strings; screenshot test all candidate locales and native panel layouts; check that no accidental English hardcoded strings remain in critical flow.
- A changed source message marks affected translations as needing review; do not silently inherit an outdated safety phrase.
- Document terminology choices and give contributors a translation guide with offline build instructions, catalog tests and testable screenshots.
- Record real device evidence from Windows and MSFS; browser synthetic tests are insufficient for native locale acceptance.

## Minimum QA examples

| State | String/context to test | Why |
|---|---|---|
| Armed | `Waiting for automatic collection trigger: {condition}` | No implied active science |
| Recording | `Flight recording is active; science collection has not started` | Independent state machines |
| Paused | `Science paused; flight recording continues` | Avoid misleading controls |
| Invalid | `No valid terrain intersection for this observation` | Missing must not seem valid |
| Historical | `Historical satellite observation, acquired {date}` | Historical vs live meaning |
| Consent | `Share live position with members of {organization}?` | Distinct opt-in |
| Delete | `Permanently delete {count} selected data items? This cannot be undone.` | Reversible UI cannot imply backup |
| Submission | `Submit {count} selected evidence files to {organization}?` | Explicit bounded destination |
| Offline | `Connection unavailable. Saved local data can still be reviewed.` | Clear recovery |
| Stale | `Flight status is out of date. Controls are temporarily disabled.` | Fail closed |

## Gate

P02 establishes architecture, English catalog and locale selector skeleton. P03–P06 ship new UI with externalized copy. P07 completes first-wave translation and human review. P08 proves native/desktop/browser behavior in installed environments. Never call v0.8 multilingual complete solely because a language menu exists.

## Approved initial locale commitment (November 10, 2026)

The owner has **approved** `en-US`, `es-ES`, `fr-FR`, `de-DE`, `pt-BR` as the v0.8.0 first-wave language target. These are no longer an unconfirmed priority proposal, although translation implementation, review, native-font/encoding proof and release acceptance remain outstanding. Do not substitute another locale without a new product decision. Prefer the display names **English, Español, Français, Deutsch, Português (Brasil)**, and continue using English as the fallback.

The dashboard's theme preference is `auto` by default; translation choice does not alter theme, scientific units, or original stored values.
