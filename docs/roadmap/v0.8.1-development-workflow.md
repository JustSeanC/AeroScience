# AeroScience v0.8.1 — Direct-commit development workflow

**Owner decision: 2026-11-25. Active development branch: `develop/v0.8.1`.**

This workflow supersedes P01's proposed short-lived branch / per-checkpoint pull-request strategy **for v0.8.1 only**. P01 documentation was merged via [PR #36](https://github.com/JustSeanC/AeroScience/pull/36) and is preserved as history; the permanent v0.8.1 development line starts from the resulting `main` commit `741e4a9de3484d24fb8e5886be8e3762d996ce84`. Existing v0.8.0 Beta 1 release artifacts, isolated profiles, stored research and tags are unaffected.

## Branch responsibilities

| Ref | Purpose | Allowed changes |
|---|---|---|
| `main` | Accepted/published source baseline | No routine v0.8.1 checkpoint commits; update only during explicitly owner-approved release integration or separately approved hotfix |
| `develop/v0.8.1` | Integration branch for all v0.8.1 work | Codex commits and pushes completed P02–P06 checkpoints **directly** to this branch |
| Historical P01 branch/PR | Audit record | No need to reopen, transplant, or replay the merged P01 changes |

**No per-checkpoint PRs, transient feature branches or automatic merges.** Do not create a new PR for P02–P06 as the normal workflow. A final integration PR from `develop/v0.8.1` to `main` may be used only when the owner authorizes release integration; do not assume the owner has authorized it by approving a development checkpoint.

## Required workflow for each Codex checkpoint

1. Fetch remote refs; confirm `origin/develop/v0.8.1` exists and review `main`/release context. If the local worktree has unrelated uncommitted changes, **do not overwrite or discard** them: stop and report the conflict.
2. Check out `develop/v0.8.1` (or create a local tracking branch for `origin/develop/v0.8.1`) and `git pull --ff-only origin develop/v0.8.1`. Reconfirm HEAD, status and any existing checkpoint progress; do not reset hard, force-push or recreate the branch.
3. Implement only the currently authorized checkpoint; use the accepted v0.8.1 scope, architecture, research and tracker. Reuse existing systems; preserve MSFS/SimConnect, original evidence, privacy and isolated beta profiles.
4. Run relevant focused tests first. For shared/risky changes expand regression tests as justified; preserve failures/receipts and do not claim actual X-Plane acceptance from synthetic fixtures. CI triggered on this branch is additional evidence, not a substitute for owner simulator validation.
5. Update the development tracker and checkpoint handoff with actual work, tests, limitations, source/build identity and next owner decision. Link `#14` without auto-closing it.
6. Review `git diff --check`, scope, new/modified files and destructive operations; commit the accepted checkpoint with a descriptive message (e.g., `feat(xplane): implement v0.8.1 P02 read-only telemetry adapter`).
7. **Push directly:** `git push origin develop/v0.8.1`. Verify remote commit equals the pushed commit; provide the commit URL and status in the owner-facing handoff. Do not create a PR or merge into `main`.
8. Stop at the end of the authorized checkpoint. The next checkpoint can start on the same development branch when the owner requests it, using the latest remote HEAD.

If the remote branch has moved during the work, fetch, inspect the divergence and reconcile normally before pushing. Never force-push, silently overwrite concurrent work, cherry-pick stale checkpoint commits without review or delete research history. If branch protections prevent direct pushes, report the exact blocker; don't bypass controls.

## Release and data boundaries

- Keep `main` and the accepted `v0.8.0-beta.1` tag/installer untouched during normal v0.8.1 development.
- No unapproved installation, packaging publication, production scientific migration or use of owner beta archives. Continue isolated development/acceptance profiles as planned in P05/P06.
- P02 is provider-only/fixture-first; no production X-Plane science or recorder activation before provenance-safe integration at P04.
- Use focused tests per checkpoint and full integrated CI before owner candidate acceptance. Record the true result, including pending/failed/unavailable checks.
- At P06, require genuine Windows/X-Plane and MSFS regression acceptance, an owner release decision and an explicit authorized integration of the tested source into `main`. Do not publish, tag, auto-merge or delete the development branch just because tests pass.

## Initial reference commands

```powershell
git fetch origin
git switch develop/v0.8.1
git pull --ff-only origin develop/v0.8.1
git status --short
git rev-parse HEAD

# After the current authorized checkpoint has been tested and reviewed:
git add <reviewed-files>
git commit -m "feat(xplane): v0.8.1 P02 telemetry adapter"
git push origin develop/v0.8.1
```

The `git add <reviewed-files>` placeholder is intentional: stage reviewed files only, not indiscriminately generated artifacts.
