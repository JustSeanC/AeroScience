# v0.4.0 Windows build, installed testing and publication

Status: cloud source tests and genuine external-source tests are separate from the **outstanding installed Windows/MSFS acceptance** below. No Windows setup EXE is produced or accepted by the Linux environment. Existing v0.3.x tags/installers are not replaced. A self-hosted Actions runner is not required.

## Build on the gaming PC

These commands are for the maintainer. Ordinary pilots only run Setup and AeroScience from Start.

1. Close AeroScience. Open **x64 Native Tools Command Prompt for Visual Studio**, enter `pwsh`, and use the PowerShell commands below. `Set-Location` does not work in ordinary Command Prompt. Keep the installed .NET SDK from `global.json`, Python, Node, official MSFS 2024 SDK and Inno Setup 6.3+ available. Inno 6.7.3 is supported; the build checks compiler output rather than unreliable Windows file-version fields.
2. Update the existing checkout. Inspect/preserve any local changes rather than discarding acceptance reports or unrelated edits:

```powershell
Set-Location 'C:\Dev\AeroScience-release'
git status --short
git pull --ff-only origin main
git log -1 --oneline
```

The release build requires a clean checkout. If a genuine provider rerun generated a changed tracked report, retain and commit that factual report; do not rename a failed/pending result to passed.

3. Build into a **new** output folder, keeping prior candidates/finals:

```powershell
pwsh -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\release\Build-ReleaseCandidate.ps1 -SdkRoot 'C:\MSFS 2024 SDK' -RuntimeApprovalRecord 'C:\AeroScience-Release-Records\runtime-approval.json' -RuntimeRedistributionConfirmed -InnoCompiler 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe' -OutputDirectory 'C:\AeroScience-Builds\Science040-1'
```

This retains locked dependency/asset checks, tests, current-source genuine scientific acceptance, actual official SDK ABI/package validation, native runtime loading/exports, the existing private-safe redistribution approval, signed Microsoft prerequisite validation, Inno compilation and payload checksums. The original permission correspondence stays private. It is not necessary to establish a new authorization or disclose correspondence for the already authorized DLL; a different runtime hash needs its corresponding truthful attestation.

**Run this primary installer candidate:**

`C:\AeroScience-Builds\Science040-1\installer-candidate\AeroScience-Setup-v0.4.0.exe`

The `AeroScience-v0.4.0-win-x64-CANDIDATE.zip` is an intermediate/optional portable payload, not the recommended installation. The v0.4.0 build stops at a candidate, because automated tests cannot supply installed-flight acceptance.

## Establish the exact installed build

Run that setup EXE. Confirm branding/version/path, shortcuts, dependencies, first-run storage/toolbar choices and browser startup. Default application installation is `%LOCALAPPDATA%\Programs\AeroScience`; data belongs outside the replaceable application directory. Keep your configured archive/library paths. Close MSFS before approving a Community package change; choose the correct Community directory and avoid duplicate old AeroScience packages. Other add-ons must survive. Start MSFS afterwards and open AeroScience normally; no terminal/server is needed to operate it.

The maintainer can compare installed bytes with the candidate receipt:

```powershell
python .\scripts\release\installer_release.py verify-installed --folder 'C:\AeroScience-Builds\Science040-1\installer-candidate' --installed "$env:LOCALAPPDATA\Programs\AeroScience"
```

If you chose another application path, substitute it. A missing/changed file means this exact install is not established; do not mark that check passed. Do not rebuild after testing, because that creates different bytes.

## Required installed missions A–E

| Test | Procedure and evidence to record |
|---|---|
| A — Multispectral | Choose RedEdge-P reference, draw a polygon, set AGL/groundspeed/overlap, fit scan lines and prepare genuine Sentinel coverage. Fly/record, end, replay actual acquisitions, compare geometric and valid support, generate NDVI/RGB, inspect nodata and export GeoTIFF/research ZIP. Record scene/source/date, mission ID and actual limitations. |
| B — Terrain | Choose RIEGL reference; plan AGL/swath and fly varied terrain. Check independent simulator ground altitude, AGL, pitch/bank and actual cached timestamps. Compare external DEM/DSM only with explicit vertical-reference limits. Review modeled density/swath and genuine elevation products. Confirm there is no manufactured point cloud. |
| C — Vertical profile | Use the atmospheric template, climb/descend through a selected MSL range, inspect temperature/pressure/density/wind and optional visibility/cloud readings. Review altitude bins, actual packet times, gaps, candidate local lapse findings and exports. Test optional-variable unavailability without loss of core telemetry. |
| D — Cloud survey | Enter/exit different MSFS cloud conditions. Check actual local SimVar returns, observed/unknown entry/exit boundaries and replay. Pause science, create a real connection gap and verify that raw environment context is not mislabeled as a missing acquisition. No regional cloud map should appear. |
| E — Reliability | Record for **30–60 minutes** with supported science enabled. Analyze a completed archive concurrently (coverage/composite/cancel/retry). Inspect actual sampling diagnostics, product hashes, cadence/gaps/reconnect and CPU/memory. End/reopen/restart offline and review/export. Record measured duration and any lost intervals; do not infer a clean long flight from a short logical-clock test. |

Also test at least a default fixed-wing, another third-party aircraft and a rotary-wing configuration where available; unsupported fields must remain missing rather than disabling recording. Compare grounded/moving/paused/loading states. The native toolbar must still drag/resize/scroll correctly and preserve payload settings when changing enable/interval. Verify toolbar mission synchronization and real Mach. Test Quest 3/VR controls/performance and a **physical iPad Safari** on the local network, including archive tabs and analysis controls. Desktop tablet emulation does not establish these passes.

## Save actual results without editing JSON

After performing the checks, open the guided maintainer checklist:

```powershell
pwsh -STA -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\release\Complete-ReleaseAcceptance.ps1 -AcceptanceRecord 'C:\AeroScience-Builds\Science040-1\installer-candidate\ACCEPTANCE.json'
```

It shows all checks, instructions, tester identity, exact source and installer hash together. Select only the results you actually obtained and add brief evidence notes. Pending/failed results can be saved and revisited; original records are backed up. This helper itself still needs Windows UI testing. Finalization reports **all** missing results together, not one at a time. The additional gate comes from the explicit v0.4.0 requirement for real installed missions/devices; it does not repeat tests that you already recorded for this exact candidate.

Finalize unchanged tested bytes:

```powershell
pwsh -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\release\New-Release.ps1 -AcceptanceRecord 'C:\AeroScience-Builds\Science040-1\installer-candidate\ACCEPTANCE.json' -OutputDirectory 'C:\AeroScience-Builds\Science040-1'
```

Final outputs, **only after successful actual acceptance**:

- `C:\AeroScience-Builds\Science040-1\AeroScience-Setup-v0.4.0.exe`
- The matching `.exe.sha256` and `AeroScience-Setup-v0.4.0.release.json`.
- `RELEASE-NOTES.md`; optional portable ZIP/checksum.

If final files already exist, preserve them and verify them; do not delete/rebuild a tested release just to rerun a command.

## Manual GitHub prerelease

1. Open [AeroScience Releases](https://github.com/JustSeanC/AeroScience/releases) → **Draft a new release**.
2. Create tag `v0.4.0` targeting the **exact tested source commit printed by finalization**, not a newer untested main. If that tag already exists, verify its commit instead of moving it.
3. Use the generated release title/`RELEASE-NOTES.md` and select **Set as a pre-release**. Keep older releases/tags/assets intact.
4. Upload the final **setup EXE**, its **SHA-256 file** and public **release evidence JSON**. The portable ZIP is optional secondary. Do not upload private runtime correspondence, developer source datasets, mission databases or unfinished candidate acceptance files.
5. Check filenames/hash/source and release text, then publish. Download the published EXE/checksum once and compare the SHA-256 with the tested artifact. Pilots run the EXE, complete guided setup and open AeroScience from Start.

No upload/tag/publication is performed by the cloud implementation. Optional Actions preparation can retain candidates for later manual acceptance; its unaccepted v0.4.0 automatic publication path is explicitly blocked.
