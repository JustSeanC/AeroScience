# v0.4.2 usability evaluation and scorecard

No representative participants were available in this development environment.
Automated tasks, developer visual review and genuine-data validation are separate
from independent usability results. **The 9/10 goal and 90% independent task-completion
target remain unverified.** No human results or satisfaction scores are invented.

## Weighted rubric

| Category | Weight | Previous category score | Current assessment and evidence |
|---|---:|---|---|
| Navigation and workflow design | 20% | Not supplied | Not scored; deep links, back/forward, mission identity, drawer and explicit recording covered by browser tests |
| Scientific visualization and interpretation | 25% | Not supplied | Not scored; native-value tests, whole-scope fixture, source dates, masks, independent GIS comparison and values tables |
| Visual design and consistency | 15% | Not supplied | Not scored; ten labeled before/after views and developer visual inspection |
| Status, feedback and error handling | 15% | Not supplied | Not scored; scoped commands, empty replies, partial states, retry, cancellation and stable download polling tests |
| Accessibility and responsive layouts | 10% | Not supplied | Not scored; axe, keyboard/drawer, table alternatives and seven viewport widths; assistive technology pending |
| Performance and reliability | 10% | Not supplied | Not scored; defined load fixture, bounded rendering/cache, recovery, genuine workloads; long live flight pending |
| Discoverability and help | 5% | Not supplied | Not scored; task search, contextual/offline guides, support actions and guide safety tests |

The prior **approximately 5.9/10** is an external preliminary overall reference from
the assignment, not a formal baseline study. No category breakdown was supplied.
A new weighted score is withheld until each category has evidence from representative
users. When scored, use `sum(category score × weight)`; preserve missing values rather
than treating them as zero or substituting developer opinions for participants.

## Representative-user protocol

Recruit ordinary MSFS pilots who have not developed AeroScience, including keyboard
and tablet users. Use the same archive/data tasks for comparative assessment, record
software/OS/device/zoom, avoid coaching, and collect consent before recording screens
or personally identifying/geographic material. Use at least these scenarios:

| Scenario | Independent task and successful outcome |
|---|---|
| A — First mission | Install, select/prepare a saved plan, explicitly start/end; confirm the expected snapshot and recording |
| B — Find results | Find a completed flight, open its scientific review and identify an actual instrument result |
| C — Interpret map | Explain value/units, flight versus source date, valid versus missing support, overview versus native cells |
| D — Compare | Pick two records, inspect matching locations, explain shared/independent scales and whether subtraction is supported |
| E — Partial preparation | Identify what is ready and still pending; pause/resume the selected mission without confusing global controls |
| F — Recover | Recognize offline/provider/drive failure, find a safe next action and return without losing saved data |
| G — Tablet | Navigate, inspect a saved scientific value and export using physical iPad Safari/touch and back/forward |

For every attempt record unassisted success/failure, elapsed time, wrong turns,
requests for help, critical errors, participant explanation of the science and a
short satisfaction rating. Track partial completion and assistance separately.
Report the denominator, participant characteristics, limitations and failures. Aim
for at least 90% independent completion on core tasks; do not count automated tests
as participants. Fix serious scientific, data-loss and accessibility defects before
using an average score to describe release readiness.

Developer automated workflow coverage is documented in the completion report. Installed
Windows/MSFS, representative pilots, physical devices and a long flight remain separate
acceptance, regardless of how many automated checks pass.
