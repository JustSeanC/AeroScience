## Preserve these decisions and working components

- Keep the existing engine, mission coordinator, SQLite/history/recovery, shared state, web dashboard, toolbar protocol and build/package validation. Inspect and extend them before proposing replacements.
- Support compatible aircraft without a rigid whitelist, including default and third-party fixed/rotary-wing aircraft. NASA aircraft are future research examples. Unknown/nonstandard aircraft data needs graceful fallback; individual aircraft compatibility still requires tests.
- Universal is the default mission mode. Preserve mode selection, safe legacy defaults, database persistence, restart behavior and synchronization across dashboard/toolbar/history. Realistic currently records identically and identifies advanced science features as future work.
- Compact VR is completely removed. Keep one responsive Mission/Payload interface. Preserve native title dragging, edge/corner resizing, close/minimize/pop-out controls and bounded content scrolling. VR-specific acceptance is performance measurement only.
- Preserve the earlier installed-header ABI offset correction, three/four-component SDK minimum-game-version acceptance, case-insensitive layout matching with collision/missing-file rejection, official package compilation, build receipts and release gates.
- Keep user data outside the install folder. Existing engine: `C:\Windows-Companion-unverified-in-MSFS`; existing data/history: `%LOCALAPPDATA%\AeroScience`. Updates must retain data and safely handle existing mission modes/schema.
- Known local SDK root: `C:\MSFS 2024 SDK`; personal native runtime: `SimConnect SDK\lib\SimConnect.dll` beneath that root. Reported game version `1.9.18.0` and package-validator version `1.0.7.0` are not the SDK installer version; the latter remains unreported. Use the installed official SDK/docs and record exact versions for reproducibility.

## Second milestone: make the alpha easy to obtain and install

- Testers should download usable Windows companion and Community package assets. They should not compile the project or install Visual Studio/Python merely to run it. Resolve and document the supported SimConnect runtime installation/licensing route; do not promise a dependency-free live setup while it remains unresolved.
- Provide clear novice Windows instructions for download, extraction, simulated launch, live launch, Community installation, updating and feedback. State which assets are source versus executable. Workspace editor links and GitHub source ZIPs are not companion downloads.
- Verify on a clean Windows account/machine, using only documented runtime prerequisites. Confirm the package root/layout, only one installed toolbar variant, preserved data and an upgrade from the existing preview. Document the actual supported Community folder; test Community2024 separately before claiming support.
- Ship simple launchers that make telemetry source, toolbar bridge and optional LAN behavior clear. Reuse existing scripts where possible. Keep localhost as the default and private-LAN pairing optional; do not require firewall changes for local operation.

## Third milestone: automated GitHub prereleases and feedback

- Build versioned Windows companion assets and produce checksums, release notes, commit/version identification and clear alpha labels. Keep engine/UI/package/diagnostic versions consistent with the release scheme and SDK manifest rules.
- Build the Community package using the official installed MSFS 2024 SDK in a suitable Windows build environment, or incorporate a genuine locally SDK-built package with its receipt. Ordinary hosted runners must not be assumed to have the SDK. Preserve validation, provenance and acceptance checks; do not fabricate SPB files, rewrite generated manifests to bypass checks, include diagnostic variants as the full package, or disable gates to make automation green.
- Resolve native SDK runtime redistribution rights before bundling proprietary DLLs. Release artifacts must exclude personal databases/logs, pairing information, SDK source and credentials.
- Friends-only access must be real: a prerelease on this public repository is still public. Choose an access-controlled distribution location if the binaries must be private; do not make source-repository visibility changes silently.
- Include a simple local feedback collection path, building on the existing collector. Reports should identify app/commit/MSFS/runtime versions, aircraft, telemetry source, science mode, reproduction steps and relevant reviewed logs. No automatic uploads or personal database inclusion.
- Document a repeatable maintainer build/release procedure and a short tester checklist. Keep unfinished hardware checks and known limitations visible in release notes.

## Scope and completion criteria

Do not add scientific instruments/sensors, calibration, aircraft restrictions, data-quality penalties, NASA-specific systems, mapping or full replay in this stabilization alpha. Preserve extension points for later work. An installer, tray app or auto-updater is not an assumed requirement; choose only work needed for an installable, testable alpha.

The development prompt should require: a review of the current repository; a small prioritized implementation plan; focused changes and meaningful regression checks; honest separation of automated and actual hardware evidence; updated documentation/changelog; source commits backed up to GitHub; real downloadable alpha assets with supported dependencies; and a final report covering changes, tests, installation, remaining issues and tester feedback instructions. Do not mark hardware-dependent behavior verified before actual testing.
