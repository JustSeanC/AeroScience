# AeroScience v0.1.1 — live aircraft telemetry and mission recording alpha

Date: 2026-10-16. Repository: https://github.com/JustSeanC/AeroScience, branch `main`.

**Implementation update:** the attached development prompt is now being implemented. See [the current alpha guide and acceptance](alpha-testing.md); the requirements below are retained planning context and must not be mistaken for unimplemented work or completed hardware tests.

Use this brief to understand the development scope. The primary v0.1.1 deliverable is reliable live telemetry from the aircraft being flown in MSFS 2024, displayed in the toolbar/dashboard and saved as a real flight mission. The user also requires tidy packaging and **at most one user-facing executable to launch for a simulator session, with no PowerShell/terminal commands**. The released app should use live aircraft data only; remove the production simulation feature. Continue the existing codebase and verify/harden its implemented SimConnect provider. Do not treat implemented features as hardware-tested.

Suggested release theme: **Live Flight Recording Alpha**. A tester should be able to load an MSFS aircraft, connect AeroScience, see that aircraft's changing telemetry, record a flight, end it and inspect its saved history after restarting the companion. Initial live connection/display now works on the gaming PC with `T-38N WSSP Late`, and an active Universal mission reports 16 samples. Completed-mission retrieval, restart persistence, wider compatibility and robustness still need testing. Build on this working integration; v0.1.1 must make the complete workflow reliable and accessible through the single app entry point.

## Required user experience

- Provide one obvious entry point, `AeroScience.exe`. The user double-clicks it for a simulator session; it starts the engine, enables toolbar communication and connects/reconnects to MSFS automatically. Users must not separately launch the engine, bridge, scripts or a terminal.
- Provide an app window or tray/status surface with connection state, access to the existing dashboard, settings and a clear exit action. Open the dashboard through the app rather than requiring users to type localhost URLs. Reuse the engine/web interface; choose only the Windows shell needed for this workflow. Normal use must not depend on a console window, command-line arguments, environment-variable edits or batch/PowerShell launchers.
- Handle first-run prerequisites and Community installation through understandable UI: detect the configured folder where possible, allow browsing, install/update the ready-built toolbar with MSFS closed, and report actionable errors. Do not require testers to compile the toolbar or edit manifests/config files. Preserve other add-ons and existing mission data.
- Package a tidy Windows download with clear installation/update instructions. One executable to operate does not require every runtime DLL/asset to be physically merged into a single file; support files may accompany it. SDK compilation and build scripts remain maintainer tasks. Testers must not need Visual Studio, Python, PowerShell 7 or a .NET/MSFS SDK to build the product.
- Resolve the supported SimConnect runtime/prerequisite installation route through permitted bundling or an official graphical installer. Do not silently shift unresolved developer prerequisites onto testers or require DLL-copy commands. Keep licensing constraints explicit until resolved.
- Validate the complete ordinary-user flow on a clean Windows account/machine, including first run, MSFS not yet running, launch/automatic connection, recording, exit and update with retained history. A developer's working command-line launch is insufficient acceptance for this requirement.

## Live-data-only production behavior

- Remove the generated ER-2 trajectory, production `SimulatedTelemetryProvider`/startup selection, demo controls and simulated-mode launchers from the v0.1.1 release. Update current user instructions and diagnostics so they do not direct users to synthetic mode. Default normal startup to the real SimConnect provider through the one app entry point.
- When MSFS is absent, loading, paused without fresh data or disconnected, show the actual waiting/disconnected state and retry appropriately. Never generate substitute readings, display stale values as current or record invented samples to make the interface appear active.
- Universal and Realistic remain science mission modes; removing synthetic data does not remove either mode or change persistence/defaults. Both record actual MSFS aircraft telemetry, with advanced Realistic science features still deferred.
- Preserve existing mission history, including old simulated recordings and their source labels. Do not delete data or relabel historical samples as live.
- Keep deterministic synthetic samples/mocks only within automated tests or a separate test-only host, excluded from shipped production functionality. Adapt current tests that start the simulated engine so meaningful storage/UI/protocol coverage remains; do not remove tests or expose a hidden user demo mode to keep the suites green.
