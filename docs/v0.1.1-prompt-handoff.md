# AeroScience v0.1.1 — live aircraft telemetry and mission recording alpha

Date: 2026-10-16. Repository: https://github.com/JustSeanC/AeroScience, branch `main`.

Use this brief to create the next development prompt. The primary v0.1.1 deliverable is reliable live telemetry from the aircraft being flown in MSFS 2024, displayed in the toolbar/dashboard and saved as a real flight mission. Installation and friends-only distribution support that deliverable. Continue the existing codebase and verify/harden its implemented SimConnect provider; do not frame this release primarily as packaging, UI cleanup or synthetic-data testing. Do not treat implemented features as hardware-tested.

Suggested release theme: **Live Flight Recording Alpha**. A tester should be able to load an MSFS aircraft, connect AeroScience, see that aircraft's changing telemetry, record a flight, end it and inspect its saved history after restarting the companion. This workflow is the central release acceptance scenario. Real aircraft telemetry is currently implemented but not yet verified on the gaming PC; do not assume it already works or rewrite it without reviewing the existing code.

## Preserve these decisions and working components

- Keep the existing engine, mission coordinator, SQLite/history/recovery, shared state, web dashboard, toolbar protocol and build/package validation. Inspect and extend them before proposing replacements.
- Support compatible aircraft without a rigid whitelist, including default and third-party fixed/rotary-wing aircraft. NASA aircraft are future research examples. Unknown/nonstandard aircraft data needs graceful fallback; individual aircraft compatibility still requires tests.
- Universal is the default mission mode. Preserve mode selection, safe legacy defaults, database persistence, restart behavior and synchronization across dashboard/toolbar/history. Realistic currently records identically and identifies advanced science features as future work.
- Compact VR is completely removed. Keep one responsive Mission/Payload interface. Preserve native title dragging, edge/corner resizing, close/minimize/pop-out controls and bounded content scrolling. VR-specific acceptance is performance measurement only.
- Preserve the earlier installed-header ABI offset correction, three/four-component SDK minimum-game-version acceptance, case-insensitive layout matching with collision/missing-file rejection, official package compilation, build receipts and release gates.
- Keep user data outside the install folder. Existing engine: `C:\Windows-Companion-unverified-in-MSFS`; existing data/history: `%LOCALAPPDATA%\AeroScience`. Updates must retain data and safely handle existing mission modes/schema.
- Known local SDK root: `C:\MSFS 2024 SDK`; personal native runtime: `SimConnect SDK\lib\SimConnect.dll` beneath that root. Reported game version `1.9.18.0` and package-validator version `1.0.7.0` are not the SDK installer version; the latter remains unreported. Use the installed official SDK/docs and record exact versions for reproducibility.

## Primary milestone: live aircraft data and recorded flights

Record each result as passed, failed, blocked or not yet tested, with build revision and evidence. Ask for Windows hardware results when cloud execution cannot establish them.

1. Review and test the existing native SimConnect implementation, runtime loading and configuration. Connect to a loaded cockpit and show the actual aircraft identity, a connected/fresh state and telemetry responding to flight changes. A source selection/badge alone is insufficient evidence. Keep generated telemetry available only as an explicitly labeled test source; do not silently substitute it when MSFS is disconnected.
2. Compare position, MSL/AGL, IAS/TAS/groundspeed, true heading/ground track, pitch/bank and vertical speed with MSFS using appropriate units and reference conventions. Use the existing appropriate display/export surfaces rather than crowding every field into the toolbar. Fix demonstrated decoding, lifecycle or unit errors. No real aircraft compatibility pass is currently established.
3. Record actual Universal and Realistic flights on the gaming PC. Start in the toolbar/end in the browser, then reverse. Check synchronized mission ID/mode/sample counts, actual-aircraft identity, simulator source, UTC samples and changing flight values. Verify saved history/telemetry and preservation across companion restarts. Closing a display must not end recording.
4. Test representative default fixed-wing, an owned third-party aircraft and rotary-wing/hover behavior. Preserve aircraft-independent standard telemetry and graceful missing/nonstandard-data handling. Do not introduce a rigid whitelist or claim all add-ons tested from a few examples.
5. Exercise pause/loading, aircraft changes, simulator exit/restart, connection loss and companion interruption. Check explicit recording gaps, reconnects, retained data, no stale/invented samples and no duplicate missions/engine ownership.

Core acceptance is a real MSFS flight with meaningful changing telemetry, a completed persisted mission and retained history after a companion restart. Repeat both mission modes and the lifecycle/aircraft scenarios above with evidence. A successful synthetic demo or an uploaded ZIP does not establish this milestone. Repair the existing integration where required and keep hardware tests pending until actually run.

Preserve extension points for later work. An installer, tray app or auto-updater is not an assumed requirement; choose only work needed for an installable, testable live-telemetry/recording alpha.
