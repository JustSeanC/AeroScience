# Optional program progression and authorized exceptions

P21 extends the existing organization service. Scientific evaluators, published criteria, received evidence and simulator controls keep their existing meaning. This is organization workflow for fictional/simulated research, not aircraft certification or a safety determination. The [development tracker](roadmap/v0.7.0-development-tracker.md) records exact accepted source and validation results.

## Version 1 contracts and storage

`ProgramWorkflowModels` defines program policy, phases, exact-revision requirements, exception commands, immutable snapshots and privacy-safe views. Organization migrations `20261028133040_ProgramWorkflowExceptionsAndPhases` and `20261028134356_VerifiedPhaseRequirementApprovals` are additive. Local mission/science formats and P17 originals are unchanged.

- Policy starts with phase gates, campaign waivers, campaign exceptions and partial-contributor credit disabled. Campaign dispositions work without phases. `Revision` provides command concurrency; `RulesRevision` changes with authorization rules. Administrative holds change only the command revision.
- Each phase has a stable ID, independent definition revision, title/objective, sequence, prerequisites and enabled state. Its requirements bind exact opportunity ID, publication revision/SHA-256, optional original requirement key, distinct-pilot minimum and explicit waiver/exception/partial-credit permissions. Manager release is the UI default.
- Index rows reference existing append-only `DefinitionRevision` snapshots and `OrganizationAudit` events. Release proofs retain exact publication/requirement, receipt, local card, claim, pilot, review revision/head and applicable exception revision or waiver snapshot hash. There are no scientific payload copies.
- A rebuildable index of verified current P18 requirement approvals stores finding IDs/hashes. It reuses existing received-document, selected-evidence and approval checks, without changing P19 whole-card semantics.

Processing bounds: 16 active phases per program, eight requirements per phase, 1–1,000 required pilots and never fewer than the publication requires. Prerequisites must be enabled phases earlier in sequence. Cycles, missing prerequisites and duplicate sequences are rejected. One card belongs to one active phase; its named requirements can share that phase. Disabled phases and unlimited retained history remain inspectable through 20-record pages.

## Scientific versus administrative meaning

**Requirement Waiver** fulfills one exact requirement for its campaign or phase purpose. It may have no evidence. An evidence-free waiver adds zero pilots, attempts, observations or scientific coverage.

**Approved With Exceptions** requires an actual received result with supporting original telemetry/observations/documentation, the issued definition, actual claim/pilot identity and current review revision/head. It retains original outcomes, receipt references, evidence hashes, unmet criteria, justification and explicit manager authorization. An unreceived draft is insufficient. Fail and Insufficient Evidence remain unchanged.

Views separate scientific contributors, authorized partial contributors, their distinct union, waivers and administrative fulfillment. Partial credit needs both exact-purpose policy and an explicit decision. The same pilot counts once despite repeated attempts/uploads/authorizations. Requirement, whole-card, campaign and phase scopes never silently substitute for one another.

P19 scientific contributor counts and P20 measurements, dates, altitude bands and geographic samples do not read exception tables. An individually approved P18 point plus a separately waived point may fulfill a phase while the original incomplete card and P19/P20 science remain incomplete.

## Readiness and durable decisions

Readiness requires current fulfilled requirements, authorized prerequisites and no program hold. It is separate from release. Explicit automatic advancement appends a `system-policy` event after current organizational requirements are fulfilled; it does not forge a human scientific approval.

Hold/Reopen cancels authorization and requires manager release. Lost readiness cancels dependent releases while retaining prior decisions and frozen support. Automatic phases may release again after readiness returns; manager-release phases need another decision.

An exception is effective only for its original rules revision, publication/purpose and phase definition revision. Same-card finding changes invalidate a received-result disposition until reauthorized; unrelated-card findings and general comments do not rewrite its source. Revocation/supersession append decisions. New publications never inherit old waivers. Phase edits cancel release and preserve history.

The existing transactional claim service enforces holds/prerequisites on new manager assignments and volunteer claims. A publication newer than the linked phase rule blocks new claims pending explicit managerial review. Existing claims, reservations, flights and science remain preserved. Nothing changes an issued card or active sortie.

## Authorization, privacy and recovery

Managers/administrators alone change policies/phases, authorize/revoke/supersede dispositions or inspect private proof snapshots. Reviewer access alone grants no such authority; reviewers can recommend exceptions through existing comments. Membership and Identity security stamp are rechecked after the existing PostgreSQL membership lock, including before idempotent receipt replay. Expected revisions, unique active scope hashes and command receipts reject stale/concurrent duplicates and changed retries.

Active members and scoped desktop reads receive sanitized statuses/history and organization-scoped contributor pseudonyms. They receive no private receipt/claim/pilot IDs, raw evidence, credentials or proof snapshots through these views. Private proof links reuse protected P18 review. Desktop connections gain no write permission or new credential scope. Existing origin, CSRF, request/rate bounds and revocation remain enforced. Cross-organization resources remain isolated.

No source archive, science cache, upload or new delivery approval is introduced. P17 retention, permanent deletion and local/offline Personal Research keep existing ownership contracts. Disconnected organization reads report unavailable rather than inventing authorization. Startup rebuild uses existing retained originals in bounded batches before reconciling phase release; unchanged restart retains proof hashes.

## Validation and limits

Tests use real isolated PostgreSQL, Kestrel, desktop Engine and browser fixtures with explicitly synthetic recordings. Cases cover actual received Fail/Insufficient Evidence; exact point/card scope; distinct partial credit; unchanged P19/P20; prerequisites and auto/manual release; holds/reopening; new assignment/claim gates and old-claim recording; immutable proofs/history/restart; revocation/supersession; concurrent commands; reviewer/read-only isolation; and manager authority revoked while waiting on the real database lock. Browser workflows cover original outcomes, manager actions, member privacy and narrow-screen accessibility. Exact totals and failed diagnostics are recorded in the tracker.

Unrestricted scripts, certification rules, generalized scheduling, new science types, pilot uploads, aircraft control and production hosting/backups remain outside P21. Installed Windows/MSFS/SDK, physical iPad/Quest and genuine NASA originals remain separate gates. P22 is not started.
