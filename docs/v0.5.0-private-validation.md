# Private AeroScience 0.5.0 validation on Windows

This build is for private testing from `develop/v0.5.0`. **0.4.2 remains the public/QA
release. Do not upload the validation ZIP to GitHub Releases.** No merge, release tag,
installer registration or production shortcut is created by this workflow.

## Build once, launch graphically

Install Git, the .NET SDK pinned in `global.json`, Node.js 22, Python 3, PowerShell 7,
Visual Studio C++ x64 Build Tools and the **official MSFS 2024 SDK** with SU5+ SimConnect
CommBus headers/runtime. Install the official Microsoft Visual C++ v14 x64 runtime.
The existing native DLL permission attestation must match the DLL actually bundled;
keep the original authorization correspondence private. Inno Setup is required for a
future production installer, **not** this private portable profile.

Open **x64 Native Tools Command Prompt for Visual Studio**, enter `pwsh -NoProfile`,
then run these PowerShell commands:

```powershell
Set-Location 'C:\Dev\AeroScience-release'
git status --short
git fetch origin
git switch develop/v0.5.0
git pull --ff-only origin develop/v0.5.0
git log -1 --oneline
$build = 'C:\AeroScience-Builds\Validation050-' + (Get-Date -Format 'yyyyMMdd-HHmmss')
pwsh -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\release\Build-PrivateValidation.ps1 -SdkRoot 'C:\MSFS 2024 SDK' -RuntimeApprovalRecord 'C:\AeroScience-Release-Records\runtime-approval.json' -RuntimeRedistributionConfirmed -OutputDirectory $build
```

Stop and preserve any local changes reported by `git status`; never reset your work
or an earlier candidate to get past the clean-source check. The build requires the
actual development branch and a new output directory. It compiles/tests the companion,
publishes a separate compiled validation profile, performs the real SDK ABI/package
build, loads/checks the authorized runtime and preserves exact source/file hashes.
A failed step leaves diagnostics and does not approve a candidate.

The usable application is:

```text
<the printed build directory>\AeroScience-0.5.0-Validation\AeroScience.exe
```

Double-click that EXE. It opens the native setup wizard, starts its own local server
and opens the browser. No terminal or server command is needed to use the built app.
The private archive is `AeroScience-v0.5.0-Validation-<source-short-hash>.zip`, beside
its `.sha256` file. Extract an archive completely before launching; do not run inside
Explorer's ZIP view. The archive is optional local transport, not a public installer.

| Configuration/default mission folder | `%LOCALAPPDATA%\AeroScience` | `%LOCALAPPDATA%\AeroScience-Validation-v0.5.0` |
| Default Library | Production selected Library | Validation root + `\ScienceLibrary` |

| Installed Apps/shortcuts | Existing production entries | None created |

**Only one desktop version may run at a time.** Both honor the existing production
mutex. Close 0.4.2 through its Exit button, then launch Validation; do the reverse to
return. Two simultaneously active engines are not a supported test configuration.
The separate toolbar channels also prevent an older panel controlling the validation
engine. The inactive version's toolbar may show disconnected; open the clearly named
Validation panel when testing 0.5.0. No automatic toolbar swapping or production repair
is performed. Close MSFS before any toolbar change.

The native title and dashboard banner say **AeroScience 0.5.0 Validation**. The banner
and authenticated `/api/build` show the compiled source identity and port; `/api/health`
reports version `0.5.0`. `build-info.json` and `VALIDATION-RECEIPT.json` bind the packaged
bytes to that commit. Production release verifiers reject this profile. Public-update
checks are disabled in it; rebuild from development instead.

All selected validation data paths must remain inside its profile root. Shared
production paths, escaping migration journals and symlinks/junctions are rejected.
This intentionally limits private storage testing to disposable data in that root;
external-drive and production independent-root migration acceptance remains a separate
controlled installed test. Do not rename a production data root to resemble Validation.

## Toolbar and first setup

Run the wizard with the suggested isolated storage folders. Consent independently to
online basemaps and online scientific access, or select offline-only. Approve the
**validation** toolbar installation into the detected Community folder (Browse is
available), or Skip for Now. Later use Settings → Toolbar → Install / Update / Repair.
It uses the existing verified atomic installer, with its separate package and backup
namespace `.aeroscience-validation-backups`. The production package and production
backups remain untouched. MSFS must be closed. Start MSFS afterward and choose
**AeroScience 0.5.0 Validation**, not the ordinary AeroScience panel.

Confirm real requests/replies in Settings → Toolbar → Refresh Bridge Diagnostics.
Telemetry connection alone is not proof of toolbar connection. A disconnected wrong
panel is not permission to change production channels or overwrite its package.

## Test an archive copy, never the only original

Start with new disposable missions. To test existing history, first exit production
AeroScience and stop tools that write those archives. In the native Validation window,
choose **Copy archives for validation**. Select the original mission folder, then its
corresponding Science Library, and explicitly confirm. AeroScience uses the existing
WAL-aware SQLite backup/fingerprint checks and verifies copied original source files.
It creates a new `Copies/<timestamp-id>` directory inside the validation profile and
selects that copy with online scientific access disabled, so inherited approved jobs
cannot silently resume network transfers. Enable access later in Settings when ready.
Subsequent upgrades/migrations affect the copy only. Settings and
production registry locations are not copied or changed. The original Library ID and
portable dataset references are retained inside the disposable pair.

If the original contains an interrupted/recording mission, recover it in its original
version before copying. If copying fails, originals stay selected in production; an
incomplete `.partial-*` test copy is retained for diagnosis and is not selected.
Never open the live production database directly from a development build.

Use the [A–J acceptance workbook](v0.5.0-acceptance-workbook.md) and retain the receipt
and ZIP checksum. Unexecuted checks stay Not Tested; protected NASA imports stay Pending.

## Logs, later builds, return and removal

Collect Feedback in the native Validation window; review the ZIP for private data
before sharing through GitHub or [Discord](https://discord.gg/mpYyazCqvJ). Include the
source commit, private ZIP checksum, test ID, aircraft/MSFS version and reproduction
steps. Logs and diagnostics use the selected validation profile/storage only.
Do not share pairing codes, Earthdata credentials or original permission correspondence.

For a later candidate, exit Validation, pull development and run the same command with
a **new timestamped output folder**. Earlier archives/receipts remain unchanged.
The validation profile persists across candidates; make a copy before testing another
schema change. Installed acceptance binds to the tested bytes, not a later rebuild.

To return to 0.4.2: exit Validation, start your existing production shortcut, verify
`http://127.0.0.1:5080/api/health` says `0.4.2`, then open the ordinary AeroScience panel.
Check original history/settings/Library. Nothing must have been migrated in place.

To remove Validation: close MSFS; use Validation Settings → Toolbar → Remove and
confirm **the validation package**. Its separate backup is retained outside Community.
Exit Validation. Delete only that candidate's application folder/ZIP when no longer
needed. There is no validation Windows uninstaller or Installed Apps entry. Profile
settings, copied data and toolbar backups are preserved by default; remove that exact
validation root separately through Explorer only after checking you need none of it.
Never delete `%LOCALAPPDATA%\AeroScience`, production shortcuts, production toolbar or
production backups. No automatic recursive profile cleanup is provided.

## Remaining acceptance and future release — not authorized

Cloud CI can compile Windows and check profile/namespace isolation, but cannot build
an official SDK package without the installed SDK or establish physical Windows/MSFS,
iPad Safari, Quest 3, sustained flight or authorized NASA original-file acceptance.
No genuine Windows private candidate has been produced in the cloud. Your successful
SDK/runtime build and executed workbook supply those additional results.

Public release gates remain unchanged and may correctly refuse finalization. A private
build does not satisfy the exact production-installer acceptance requirement.
After validation, reconcile newer reviewed 0.4.2 fixes, inspect the complete development
→ main diff, obtain owner approval to open **one** final integration PR, require owner
approval to merge, then separately approve and build/test the exact production installer
and separately approve its GitHub publication. Merging must not automatically publish.
No final PR, merge, release or public asset update is authorized now.
