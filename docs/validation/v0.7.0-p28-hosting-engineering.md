## Controlled provider update and failed update

The compiled-schema runner and isolated restore verifier are working bounded components. **A beginner provider rollout/restore-promotion flow and general protected Identity-certificate/key rollover are not implemented by this protocol.** Current certificate pinning deliberately refuses an unexplained replacement. Those are engineering prerequisites after a supported hosting/owner-control contract is established, not tasks the owner should work around manually. The new private PostgreSQL certificate-regeneration test is not Data Protection key rollover.

Use only an exact accepted signed image/schema distribution, an administrator-approved paired restore checkpoint and an explicit maintenance boundary. Never treat reverting an image as schema rollback. Test compatible app/schema promotion and refusal of unsigned, stale, wrong-source or wrong-schema distributions.

Inject a failed candidate image/startup and a genuine compiled migration failure in disposable infrastructure. Restore or roll back the approved image/schema pair using the declared procedure. Compare original received evidence, immutable review/claim/event history, protected credentials, MFA and permissions; recheck consent and notification reconciliation before reopening. Record interruption/data-loss boundaries honestly. Test protected certificate/key rotation with the paired recovery dependency retained; never silently replace missing identity material.

Local PostgreSQL rollback and restored-key tests establish the implemented transaction checks, not provider maintenance, failed-image promotion or account-loss recovery.
