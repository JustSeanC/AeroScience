# v0.7.0 focused native toolbar repair

Baseline: `1c101fb43636508e3f591dc44d26a8eba4d49652`, preserved on `develop/v0.7.0`.
This corrective pass uses targeted checks. It does not establish Full integration,
genuine SDK compilation or installed Windows/MSFS acceptance.

## Reproduced causes and corrections

The compiled baseline reproduces the reported combination of changing altitude,
a matching engine reply, and **Invalid engine reply** when `Element.replaceChildren`
is unavailable. The exact exception is **TypeError: select.replaceChildren is not a
function**, in `receiveMap("map-plans")`. `receive()` caught that display exception
and mislabeled the valid reply. Research rendering also used `replaceChildren` and
`append`; ES2017 syntax compilation does not supply these DOM methods. The controlled
fixture proves the source defect, not the precise capabilities of the owner's
installed Coherent runtime. Its console/runtime confirmation remains outstanding.

The repair uses `textContent`/`appendChild`, separates bounded JSON/envelope checks
from independently guarded flight, payload, science, research and map rendering,
and records fixed component/exception-class diagnostics in Connection & Build
Details. It never records payloads, exception messages/stacks, observation notes or
credentials. A secondary display failure does not discard valid flight state or
prevent saved-plan requests. Invalid replies retain the prior valid state, subject
to the original freshness limits. Source mismatches still fail closed. Telemetry
without a fresh aircraft timestamp is not displayed as current telemetry.

Saved-plan list construction failed at the same unsupported DOM call. There were
additional synchronization defects: refreshing a selected plan called its change
handler and resent `select-plan`; a dashboard-selected ID outside the current page
could inherit the previous plan's name/mode; route chunks depended on `isConnected`;
and rebuilding dropdown options during every poll could disrupt interaction.
The repaired list keeps stable options, explicit acknowledged selection, Previous /
Next pages, empty/missing-plan explanations and a disabled Start while selected-plan
details are unavailable. Reopening uses the companion's persisted selection rather
than replaying browser storage. No refresh or navigation selects a plan or starts
recording. The optional `selectedPlan` field on `map-plans` replies supplies the
current selection's bounded summary even outside the ten-plan page. The ordinary
`map` array and protocol version remain compatible. Late pages for another selection
or engine are ignored. Active selection restrictions and immutable recorded route /
research snapshots remain authoritative in the existing coordinator.

The text pipeline already declares UTF-8 and transports JSON through UTF-8 CommBus.
The defects included decorative Unicode separators with no dependable native font
coverage, raw enum labels, and UTF-16 substring clipping that could split a Unicode
character. Native presentation now uses ASCII separators, readable status labels,
whole-character display clipping and explicit unit equivalents such as `degC` and
`kg/m^3`. Saved names, scientific values, stored units and original evidence are
unchanged. Generated validation assets preserve Unicode research names in the
fixture. Actual font/glyph coverage must still be checked in MSFS. Unknown science
is shown as unavailable; only a known armed state without a session says science
has not started. Live score bounds remain distinct from a final grade.

`ToolbarWorker` and `CommBusTransport` were inspected; neither needed a transport
change. The panel still uses native CommBus. No production HTTP/iframe path, extra
mission store or planner was added. Exact-source authorization, versioned validation
channels, request/session identity checks and 8000-byte reply checks remain intact.
The client now also applies the existing 1024-byte command limit to UTF-8 bytes.
Private staging verifies that the explicit source-rejection handler exists instead
of injecting it into a particular JSON-parse statement. The genuine SDK asset-hash
receipt and ES2017 compiler/parser proof requirements remain unchanged.

## Build the next private candidate on Windows x64

Use a clean checkout of the final source SHA supplied with this repair report, the
genuine installed MSFS 2024 SDK and the existing hash-bound runtime authorization.
From the repository in PowerShell 7:

```powershell
git fetch origin develop/v0.7.0
git switch develop/v0.7.0
git pull --ff-only origin develop/v0.7.0
$validatorSource = (git rev-parse HEAD).Trim()
$validatorOutput = 'C:\AeroScience-Builds\Validation070-Toolbar-' + $validatorSource.Substring(0,7) + '-' + (Get-Date -Format 'yyyyMMdd-HHmmss')
pwsh -NoProfile -File .\scripts\release\Build-PrivateValidation.ps1 `
  -SdkRoot 'C:\MSFS 2024 SDK' `
  -RuntimeApprovalRecord 'C:\AeroScience-Release-Records\runtime-approval.json' `
  -RuntimeRedistributionConfirmed `
  -OutputDirectory $validatorOutput
```

Compare `$validatorSource` to the final task report before building. Use the path
to your existing authorization record if different. The builder requires a new
output folder and does not install the candidate. A new output folder is not a new
data profile: the v0.7.0 Validation profile still uses port 5086 and its fixed data
root. Keep the earlier candidate and all owner data intact; a strictly isolated
side-by-side retest uses a separate Windows test profile.
