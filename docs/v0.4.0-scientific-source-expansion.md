# v0.4.0 expanded scientific sources: findings and decisions

Investigation date: 2026-10-19. This addendum complements the core planning/replay/coverage/composite implementation. An accessible catalog or decoded sample is not an implemented application provider. [Machine-readable reference receipts](research/v0.4.0-provider-investigation.json) preserve hashes/findings without redistributing reference documents, dataset archives or credentials.

## What the application actually supports

The existing USGS 3DEP numeric terrain, Copernicus GLO-30 DSM, Landsat Collection 2 Level-2 surface temperature and Sentinel-2 L2A workflows remain concrete automatic providers. Their separate consent, bounded regional reads, retained-source reuse, masks, date/quality policy, quotas, cancellation and source hashes are preserved. Supported guided ENVI hyperspectral imports remain available, including original channel/wavelength/bad-band handling. No new provider silently replaces these paths.

The minimal extension describes actual retained source capabilities independently of hardware profiles: elevation, surface model, LiDAR points, multispectral reflectance, hyperspectral radiance/reflectance, surface temperature, land cover, atmospheric state and radar. Only capabilities backed by the current verified source manifest are advertised. Current raster sources do not advertise point clouds, radar or classification products merely because enum values exist. Source selection checks profile-compatible capabilities, geographic coverage, source availability and existing scientific validation. The Source Library displays actual capabilities alongside original metadata.

**Provider** identifies the access organization/service; **collection** identifies an archive/product family; **source** is an immutable retained scene/window/import; **capability** states what its numeric measurements genuinely provide; **instrument** is a modeled hardware configuration; **acquisition** is the saved flight-time geographic selection. Existing manifests stay compatible. No speculative plugin framework, central download server, shared credentials or new mandatory account was added.

## NOAA Digital Coast LiDAR — investigated, not integrated

[Digital Coast](https://coast.noaa.gov/digitalcoast/), [Data Access Viewer](https://coast.noaa.gov/dataviewer/) and the [NOAA coastal LiDAR public-data registry](https://registry.opendata.aws/noaa-coastal-lidar/) expose historical LAS/LAZ/EPT collections. Anonymous public S3 EPT metadata and hierarchy nodes are accessible directly from the user/developer environment; they do not require an AeroScience server.

A genuine bounded investigation read three `ept.json` records and one root node:

- Public endpoint `https://noaa-nos-coastal-lidar-pds.s3.amazonaws.com/entwine/geoid18/1/ept.json` describes 35,127,417 points and `laszip` node encoding.
- Dataset 1 declares NAD83(2011) UTM 18N (EPSG:6347), NAVD88 height (EPSG:5703); another inspected collection uses EPSG:6346 and another NAD83(HARN) EPSG:3747. These are not interchangeable WGS84 coordinates or simulator MSL heights.
- `ept-data/0-0-0-0.laz` transferred 7,578 bytes, SHA-256 `f6b3dbb09b23d55a3451944e9f8c7cdadf1cd4837e7a34e72ca696f6efc78ada`. Independent laspy 2.6.1/lazrs 0.7.0 decoding found LAS 1.2 point format 1, 410 actual points and classifications 0 (unclassified) / 7 (noise). This sparse root is not a representative ground-only cloud or a usable DEM acceptance sample.

EPT offers a promising bounded hierarchy/region approach instead of downloading a whole archive, but safe application support needs a packaged and license-reviewed LAZ reader, validated classification/return filtering, bounded hierarchy traversal, original point-date metadata, appropriate NAD83/vertical-reference handling, point-footprint selection, point rendering and point exports. The current validated reader is raster/ENVI based. Relabeling these points as EPSG:4326 or rasterizing the sparse root would violate the scientific requirements.

The preferred guided LiDAR slice is therefore **not implemented** in this release. The technical investigation supports further work but does not establish a production decoder/coordinate pipeline. A candidate `laszip.net` package was inspected; it was not added or distributed. LGPL obligations need an actual packaging/source-compliance design if that option is selected, not an assumption that public data licenses cover dependencies. Dataset-specific NOAA metadata/licensing must be reviewed as part of import. The main replay/coverage release is not held open for a broad point-cloud engine. Terrain scanner outputs remain clearly identified DEM/DSM samples and modeled density, never fabricated laser returns.

## USGS EO-1 Hyperion — historical compatibility research

The [official USGS Hyperion archive description](https://www.usgs.gov/centers/eros/science/usgs-eros-archive-earth-observing-one-eo-1-hyperion) documents 2000–2017 observations and the March 2017 end of EO-1 operations. Current archive descriptions offer Level-1Gst terrain-corrected radiance in individual 16-bit GeoTIFF bands, accessed through EarthExplorer/GloVis. Public-domain USGS products remain subject to their metadata/citation and access terms; account/API authorization requirements must be checked for the actual archive service. No personal USGS credentials or authorized original Hyperion scene were available in this implementation environment, and no unsupported login scraping was attempted.

The application’s guided importer validates ENVI headers/data. A raw multi-file Hyperion GeoTIFF product is **not** a validated guided-import format. A production adapter must preserve exact scene time, per-band radiometric interpretation, original wavelengths/channel indices, unusable bands, fill values, CRS and product metadata. Approximately 220 channels does not mean 220 scientifically usable measurements. No wavelength table, scale or spectral response may be copied from AVIRIS-NG.

Accordingly direct Hyperion guided import/download is **not implemented**. The genuine Cuprite AVIRIS ENVI demonstration proves the existing supported ENVI workflow, not Hyperion acceptance. Advanced users may supply already compatible genuine ENVI sources with truthful original metadata; the ordinary pilot workflow is not advertised as automatic Hyperion acquisition. A separately validated product-specific adapter is the next useful slice.

## WorldCover — optional classification evaluation

[Official access](https://esa-worldcover.org/en/data-access) documents 10 m, 11-class land-cover maps in 3° × 3° EPSG:4326 Cloud Optimized GeoTIFFs, with CC BY 4.0 attribution/citation. The 2020 v100 and 2021 v200 releases use different algorithms: a comparison is not automatically defensible land-cover change detection. Their reference years, source nodata/class legend and original classification semantics must remain visible.

The COG format fits retained numeric reading, but current remote instruments do not implement a categorical-class importer/legend or validated polygon class proportions. No class IDs are treated as continuous reflectance or interpolated elevation. This optional analysis layer is **not integrated**; it should be a separately validated classification capability, not a new sensor or a replacement for multispectral observations.

## NASA Earthdata / Worldview / GIBS — visualization evaluation

[Earthdata Search](https://search.earthdata.nasa.gov/), [Worldview](https://worldview.earthdata.nasa.gov/) and [GIBS documentation](https://nasa-gibs.github.io/gibs-api-docs/) distinguish discovery, rendered geographic imagery and original numeric datasets. GIBS WMTS capabilities are publicly accessible; this investigation retained only a bounded prefix of the large capabilities response, **not a validated complete layer catalog**. No GIBS layer is added by this release.

A future small optional cloud/aerosol/fire/snow/vegetation layer selection must show original layer date/attribution, follow provider access/caching rules, request only visible maps after appropriate consent, and handle offline/provider failure. RGB tile colors cannot become calibrated numerical atmospheric or thermal measurements. Numeric analysis requires the corresponding original product and its QA/scaling. Protected Earthdata collections may need official user authorization; no shared credentials/proxy are bundled.

## NOAA GOES — feasibility only

The [GOES open-data registry](https://registry.opendata.aws/noaa-goes/) documents anonymous public GOES-16/18/19 buckets. ABI atmospheric/cloud/moisture products commonly use NetCDF with product-specific fixed-grid navigation, calibration and quality flags; other instrument products can use different formats. NetCDF chunking/range reads and bounded regional subsetting must be measured against actual access products before claiming bandwidth-efficient numeric acquisition.

Current raster readers do not implement GOES projection/calibration/QA or atmospheric retrievals. GOES numeric products and overlays are **not implemented**. Any future real satellite cloud product must retain its own timestamp and source, distinct from the MSFS atmosphere. No regional meteorological engine is introduced for this feasibility item.

## Other sources: bounded desk evaluation, not integration

| Candidate | Potential value and work required |
|---|---|
| Sentinel-1 SAR | Radar backscatter/polarization/coherence; requires product-specific orbit, calibration, speckle/terrain handling and QA. Not optical multispectral processing. |
| JAXA AW3D30 | Additional global DSM; inspect current registration/license, void flags, product version and vertical datum. Never imply bare-earth or new acquisition date. |
| Maxar Open Data | Disaster-specific high-resolution scenes; coverage/collection licenses vary. Check each event’s permission, calibration and provenance before import. |
| INPE CBERS/Amazonia | Regional optical archive; verify supported catalog/account access, bands, scaling, georeferencing and per-product terms. |
| NOAA CLASS | Authoritative multi-instrument archive; account/order/subset methods and original scientific formats are collection specific. |
| EarthScope/UNAVCO SAR | Research radar archives with account/eligibility and product-specific processing requirements; no generic optical adapter. |
| Airbus samples | Limited commercial examples; sample access is not general redistribution or processing authorization. |
| ISRO Bhuvan | Regional geographic/thematic resources; verify official supported APIs, download permissions, resolution and terms without scraping restricted endpoints. |
| PROBA-V | Historical vegetation observations; collection/date/quality and original reflectance scaling matter; does not confer current global imagery. |
| Other land-cover catalogs | Require a categorical capability and exact version/reference period, legend and nodata treatment. |

These are opportunity/access assessments, not claims that every remote endpoint or license was independently exercised. No paid keys, cloud resources, unsupported scraping or broad provider framework were introduced.

## Acceptance boundary

Core genuine-data acceptance covers four existing automatic providers, genuine guided ENVI, saved native pixels, multi-region reuse, coverage/composites, independent GDAL comparisons and hashed research exports. NOAA node decoding is an **independent investigation**, not an application import/visualization pass. Hyperion/WorldCover/GIBS/GOES have no application acceptance claim. Windows/MSFS, physical iPad, Quest 3 and long-flight acceptance remain pending on the gaming PC. See [completion](v0.4.0-completion.md).
